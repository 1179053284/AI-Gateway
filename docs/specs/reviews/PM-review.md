## 1. 审核结论

**有条件通过。**

设计的**克制程度整体达标**——§14.2「不建四表」、§15.3「不做画像随机化」、§20「14 条不做清单」这几处是教科书级的过度设计防御，方向正确，Q27-⑤「初期独立」也落实准确。

但**三处硬伤必须先补**：① 文件下发路径（`mgw setup` 写 `models.json`）与 PRD Q25-⑨ 的目录解析规则在 §12–§20 **零落点**，而 §12 唯一落地的 API 下发路径恰是调研里标注「待验证」的那条（`08:626`），§12 的实测依据 WorkBuddy CLI 只读文件、根本不调 `/v1/models`（`08:625`）——**按现方案实施，首期对 WorkBuddy 无效**；② PRD Q27-④ 明确要求的批量执行器「双层互斥」（`prd.md:681`）在 §16.4 被漏掉；③ 用户已接受的「验证码自动求解」及其硬依赖「住宅代理」在 §12–§20 无任何落点与风险披露。

另有一处**自相矛盾**（§15.2 定义跨产品 `Protocol` vs §20 #14「不预先抽象」；§14.1 新增 UI vs §20 #12「首期不做 UI」）需裁决。补完这 3 处硬伤 + 8 处中等问题后可通过。

## 3. 问题清单（按严重度）

### 严重

#### S1 · 文件下发路径与 `mgw setup` 规则整体缺失，首期方案对 WorkBuddy 无效

- **证据**：`tech-design.md:666-723`（§12 只做 `/v1/models` 加字段 = 调研里的**路径 B**）；`08:625` 明确「WorkBuddy CLI **只读文件，不调 `/v1/models`**」且标「✅ 已验证」，`08:626` 把路径 B 标「⏳ 待验证」；`08:599` 与 §12.1 的实测依据正是这个 WorkBuddy CLI。PRD 侧：`prd.md:592`（Q25-⑨ 目录解析规则）在整个 `tech-design.md` **零命中**（`mgw setup` / `dataFolderName` / `WORKBUDDY_CONFIG_DIR` 均无）。
- **影响**：§12 的交付判据「工具实测工具调用不再被剥离」（`tech-design.md:943`）在 WorkBuddy CLI 上**不可达**——它读的是 `~/.workbuddy/models.json`，不看 `/v1/models`。Q25-⑨ 这条已确认需求（含 `WORKBUDDY_CONFIG_DIR` 劫持坑，`08:636`）会漏出首期。
- **建议改法（最小）**：§12 增补一节「路径 A · 文件下发」：`mgw setup` 生成 `models.json`，目标目录按「产品标识 → `dataFolderName`」解析并处理 `WORKBUDDY_CONFIG_DIR`（直接搬 `08:636` 的 D3），写入前**先备份/合并已有文件**（`08:654` U7 记录过原文件被清空的事故）；并把 §19 M3 补一格 M3-4。若坚持首期只做路径 B，则必须显式写明「路径 A 另立阶段」，不能默认它不存在。

#### S2 · 批量执行器漏掉 PRD 明确要求的「双层互斥」

- **证据**：`prd.md:681` 原文要求「cron + **双层互斥** + 随机抖动 + 逐账号失败隔离 + 四类结果」；`11:94` / `19:307` 均写明双层互斥 =「plan 级 `TryLock` + 账号级 `claimLockFor`」。§16.4（`tech-design.md:867`）只列「串行 + 间隔 + 随机抖动 + 逐账号失败隔离 + 空跑算成功」，**全 tech-design 无「双层互斥」**（grep 零命中）。
- **影响**：缺互斥时，cron 分钟 tick 与手动触发/多实例重叠会重复 `claim`。而 §16.3 教训 2（`tech-design.md:862`）本身就在警告「判错会重试 → 触发频控」——重复领取正是同一类风险。
- **建议改法（最小）**：§16.4 执行策略补一条「**双层互斥**：plan 级 TryLock + 账号级 claimLockFor」，与 `19:307` 逐字对齐；M5-1 判据补「重复触发不重复领取」。

#### S3 · 「验证码自动求解」及其硬依赖「住宅代理」无落点、无风险披露

- **证据**：`prd.md:660`（Q27-① 第 3 项，用户已接受「验证码自动求解」）、`prd.md:678`（Q27-④ 三段式第 2 步即验证码）。但 §12–§20 中「验证码」仅出现在降级链名称里（`tech-design.md:903`），无实现落点、无依赖说明。其硬依赖见 `19:316`「⚠️ 数据中心 IP 会被风控 `F001` 拒绝，**需住宅代理**」、`11:166`「验证码需真实 Chrome + 住宅代理，**部署成本高**」——§12–§20 中「住宅代理」**零命中**，§19 排期与风险栏也未列。
- **影响**：M5-1「批量领取可跑」的判据（`tech-design.md:950`）在无住宅代理时**必然失败**，且这是需要外购/额外部署的**外部依赖**，未披露等于把交付风险留到实施期才发现。
- **建议改法（最小）**：§16 或 §17 增一小节「验证码求解：Playwright（同 `zcode2api` 栈）+ **住宅代理（外部依赖）**」，并在 §19 M5-1 的交付判据与风险栏显式写出；若不想引入住宅代理，则在 §20 增加一条「首期不做验证码求解，领取能力降级为手动」——**二者必居其一，不能悬空**。

### 中等

#### M1 · §12 输出字段名与 PRD Q25-② 不一致，且未标注「以工具契约为准」

- **证据**：PRD 写 snake_case + 独立 `effort_levels`（`prd.md:570`）；设计输出 camelCase 且不发 `effort_levels`（`tech-design.md:713-715`）。经核对工具真实契约（`08:286-295` 字段全集、`08:304` caps 子结构、`08:599` 的 8 项）**确实是 camelCase，且要的是 `caps.thinkingLevelMap` 而非顶层 `effort_levels`**。
- **影响**：设计技术上是对的，但**未说明它推翻了 PRD 字面**。验收若按 PRD 字面核对，会判「字段缺失 / 命名不符」。
- **建议改法（最小）**：§12.2 表下加一行注：「字段名以工具契约（`08` §4.4/§6.4）为准 = camelCase；`effort_levels` 由 `caps.thinkingLevelMap` 承载，PRD Q25-② 的 snake_case 与顶层 `effort_levels` 需回填修正」。

#### M2 · `thinkingLevelMap` 必须 7 键齐全、不支持档写 `null`——设计只说「组装」

- **证据**：§12.2 写 `caps.thinkingLevelMap ← effort_levels + 方言表`「组装」（`tech-design.md:697`），未要求补齐键。但工具逻辑是 `v !== null && ((lv!=="xhigh"&&lv!=="max") || v!==undefined)`（`08:341-347`）→ **键缺失（`undefined`）≠ `null`**，对 `minimal`/`medium` 这类非高阶档，缺失键会被判为「支持」；`08:304` 明确 `null` = 不支持，`08:351` 明确 `xhigh`/`max` 必须显式出现。
- **影响**：若只按 `effort_levels` 的键组装，工具会把 `minimal`/`medium` 当成可用档发出去 → 上游静默忽略（`08:319` M2）→ **正是 §12 要消灭的「静默降级」**。
- **建议改法（最小）**：§12.2 或 §13.3 加一句：「输出必须是规范序 7 键齐全的映射，不支持的档**显式写 `null`**（不得省略键）」。

#### M3 · §15.2 的 `DeviceIdentity(Protocol)` 与 §20 #14 自相矛盾

- **证据**：§15.2 定义 `class DeviceIdentity(Protocol)`（`tech-design.md:821`），§17 又列 `upstream/base.py 产品适配器接口`（`tech-design.md:884`）；而 §20 #14 写「**不做**：预先把『各产品设备身份』抽象成公共层 —— 等真有第 2、3 个产品时再抽象」（`tech-design.md:975`）。当前只有 ZCode **一个**实现。
- **影响**：文档自我否定；且为 1 个实现建抽象层，正是用户点名要避免的「为 1 个场景建通用框架」。
- **建议改法（最小）**：删 `upstream/device.py` 的 Protocol 与 `upstream/base.py`，把 `ensure()` / `is_unique()` 作为普通函数直接放 `upstream/zcode/dataroot.py`；§20 #14 保留不动（等第 2 个产品再抽）。

#### M4 · §14.1「新增 UI」与 §20 #12「首期不做 UI」直接冲突，且撞 Q25-⑩

- **证据**：§14.1 写「UI 唯一净新增 = 默认折叠的『高级 · 能力覆盖』」（`tech-design.md:785`）；§20 #12 写「**不做**：首期前端 UI（ZCode 账号管理页）」（`tech-design.md:973`）。同时 Q25-⑩ 明确「**不做** L-B/L-C 的用户录入界面」（`prd.md:595`），而 `caps_overrides` 正属 L-B/L-C 覆盖。
- **影响**：同一份文档里 UI 既「新增」又「不做」，实现时无从判断；且若真做，直接违反 Q25-⑩。
- **建议改法（最小）**：§14.1 改为「仅新增 `caps_overrides` **配置字段**（YAML 可改，供目录/探测不准时覆盖）；其界面随二期前端补」——字段保留、界面砍掉，与 §20 #12、Q25-⑩ 一致。

#### M5 · ZCode 签到/领取的模块落点冲突（§17 vs doc 19 D27）

- **证据**：§17 架构树把签到/领取放在 `upstream/zcode/claim.py`（`tech-design.md:892`）；`19:444` 的 D27 放在 `ops/builtin/zcode_claim.py`；§16 又说 `ops/` 是「批量执行器」（`tech-design.md:950`）。
- **影响**：同一功能两处落点 → 实现时易重复实现或职责割裂（HTTP 交互在 upstream、调度在 ops，边界没写清）。
- **建议改法（最小）**：在 §16.1 或 §17 加一句归属：「ZCode 领取的 HTTP 交互在 `upstream/zcode/claim.py`；`ops/` 只做调度与四类结果分类（薄适配器调用 upstream）」。

#### M6 · 排期存在两处依赖倒置

- **证据 1**：M3-1「能力位下发 + caps_overrides」`tech-design.md:943` 排在 M3-2「方言表探测」`:944` 之前，但 §12.2 明确 `caps.thinkingLevelMap` 的厂商值来自方言表（`:697`）→ **先做的拿不到 caps 内容**。
- **证据 2**：M4-3「额度三通道 + 联网兜底」`:948` 排在 M4-4「双通道鉴权」`:949` 之前，但联网通道需 `Bearer <jwt>` + `X-Device-Mid`（`19:279`）→ **额度联网依赖鉴权**。
- **建议改法（最小）**：M3-1 判据拆为「先出 7 字段（caps 暂空）→ M3-2 后补 caps」；M4-4 提到 M4-3 前，或注明「M4-3 首期仅日志通道（`19:278`），联网兜底随 M4-4」。

#### M7 · Q26-①「全新自洽画像」与 §20 #8「不做画像随机化」字面冲突

- **证据**：Q26-① 要求新账号「生成**一整套全新自洽画像**」（`prd.md:615`，`10:110` 进一步解释画像含品牌/系统版本）；§20 #8 写「**不做**：设备画像随机化」（`tech-design.md:969`），§15.3 理由为「参考项目都用本机真实值」（`:835`）。
- **影响**：ZCode 的设备身份只有 `--device-id` + `dataRoot`、**无 persona 字段**，所以「不做随机化」对 ZCode 是对的；但 §20 #8 的措辞是**全局**的，会与 Q26-① 及 `10:306`（D10 per-product 字段字典）冲突。
- **建议改法（最小）**：§20 #8 措辞限定为「**ZCode 首期**不做设备画像随机化（ZCode 无 persona 字段）」；§15.3 补一句「Q26-① 的『画像』适用于 trae/qoder 类产品（D10 保留），ZCode 不涉及」。

#### M8 · 首期不做 UI 成立，但缺「替代操作入口」，功能会「能跑但没法用」

- **证据**：§20 #12 延后前端 UI（`tech-design.md:973`）；但 §12–§20 未给出任何 ZCode 账号管理 / 签到触发的**非 UI 入口**（全 tech-design 只有 `mgw probe` 一个 CLI，`tech-design.md:745`）。doc 19 也仅说「登录由用户手动完成」（`19:48`）。
- **影响**：用户（一个开发者）在首期无法添加账号、查看额度、触发领取——M4/M5 的交付物缺少使用入口，产品上不闭环。
- **建议改法（最小）**：§19 补一句最小入口约定，如 `mgw zcode login / list / claim`（复用已有 `mgw` CLI 形态），并在 M4-2 / M5-1 判据中写明「通过 CLI 操作」。**不需要做 UI**。

### 轻微
