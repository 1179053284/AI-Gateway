## 1. 审核结论

**有条件通过。**

**核心交互决策「首期不做前端 UI」在交互上成立**——单用户、自用、开发者工具，用 CLI 打通链路、二期再补界面，是符合「避免过度设计」的正确取舍；且项目已有成熟的管理端 + 组件库 + 一个**现成的需求预演模板**可承接二期界面。这一条**不推翻**。

但本设计存在一个**贯穿性的交互缺口**：**它把多处「用户会直接看到的输出」当作纯后端行为来写，只定义了内部状态（日志、字段、退出码），没定义用户看到什么**。这与 §12.1 自己立的军令状（「消灭静默降级」）直接冲突——本次设计新增的告警与失败路径，有三处实际仍是**用户不可见**的：

1. **零映射启动告警**（§19 M3-1）判据是「断言日志含告警」，而当前启动脚本是 `nohup` 后台拉起 + **自动关闭终端窗口**（`启动网关.command:6-7,71-88`）→ 告警只落 `data/gateway.log`，用户**看不见**。而 Q25-⑧ 的立项理由恰恰是「启动时无任何提示」（`prd.md:590`）——**改完仍然没提示**。
2. **运营四类结果**（§16.2）在 §12–§20 中**没有任何用户可见出口**（无端点、无页面、无 CLI 命令）→ cron 后台领取失败**静默**。
3. **设备冲突「报由用户决策」**（§15.1 #3）只写了结论，**报什么 / 在哪报 / 怎么决策**全部未定义；且承载该决策的 `mgw zcode import` 子命令**根本不在 M5-0 的三个命令里**。

补完 §3 的 2 条严重 + 7 条中等（改动均为一句话到几行），即可进入 M3。

## 3. 问题清单

### 🔴 严重

#### S-IX-1 · 零映射启动告警是「用户看不见的告警」——Q25-⑧ 的立项问题没被真正修掉

**问题**：§19 M3-1 的交付判据只写「**断言日志含告警**」（`tech-design.md:1245`），全篇未定义告警**文案**、未定义**给到哪里**、未定义用户看到后**怎么办**。而当前启动脚本的正常路径是：`nohup` 后台拉起 → 日志重定向到 `data/gateway.log` → 就绪后打开管理页并**自动关闭终端窗口**（`启动网关.command:6-7`、`:71-88`，日志路径 `:21`）。即：**告警写进日志 = 用户看不到**（只有启动失败时才保留窗口并打印日志末尾，`:111`）。

Q25-⑧ 的立项理由正是「本次实测中网关 7 个系统模型 `resources: []` 全空，导致全部模型静默不可用（503 NO_RESOURCE），**而启动时无任何提示**」（`prd.md:590`）。按现设计实施，**问题原样存在**。

**证据**：`tech-design.md:1245`（判据 = 日志）、`prd.md:590`（立项理由 = 启动无提示）、`启动网关.command:6-7,21,71-88,111`。

**建议改法（最小，二选一）**
- **A（推荐，复用既有空态文案，零新组件）**：把告警同时写入 `/admin/api/status` 或 `/admin/api/overview` 的返回体（一个 `warnings: []` 字段），管理端**总览页**用既有 `.alert-warn` 组件（`frontend-spec.md:473`）渲染一条横幅，文案直接复用项目已有的空态话术：「**N 个系统模型未配置任何资源，调用将返回 503 —— 到『模型资源』页编辑资源添加映射**」（原文见 `design-spec.md:251`）。启动日志同时打印同一句。
- **B（纯 CLI，零 UI）**：`启动网关.command` 在就绪后**grep 本次会话日志**（脚本已有 `LOG_OFFSET` 与 `SESSION_LOG` 机制，`:74,97`），命中告警则在关窗前多停留一次回车并打印该行。

**同时必须补**：告警**文案**（一句话，含数量 + 影响 + 修复入口）与**两类分别的措辞**（① 资源已启用但无模型引用；② 模型已启用但 `resources` 为空——`prd.md:589` 明确是**两类**，现判据只写「告警」未区分）。

#### S-IX-2 · 运营四类结果没有任何用户可见出口——cron 后台失败静默

**问题**：§16.2 定义了 `success / already_done / inactive / failed` 四类，并声明「**只有 `failed` 需用户关注**」（`tech-design.md:1017-1024`）。但 §12–§20 中**找不到 `failed` 被用户看到的任何路径**：
- §16.4 只定义执行策略（串行 / 互斥 / 隔离 / 重试），无结果出口（`:1036-1046`）；
- §16.6 只定义模块归属，`ops/runner.py` 的产出无消费方（`:1071-1078`）；
- §19 M5-1 判据只断言「分类正确」，未断言「用户可见」（`:1255`）；
- §17 唯一的「管理端点」是额度刷新手动触发（`:1154`），不是结果查询。

**后果**：cron 每分钟跑，某个账号领取连续失败（验证码超时 / 熔断 / 额度耗尽），用户**永远不知道**——这正是 §12.1 要消灭的「没有报错，只有能力静默降级」（`:703`）的同类问题，只是换到了运营侧。

**证据**：`tech-design.md:1017-1024,1036-1046,1071-1078,1255,1154`。

**建议改法（最小）**：在 §16.6 末尾加一句归属——「`ops/runner.py` 每 tick 把四类结果写入 `data/ops-results-<date>.jsonl`（与现有 `data/usage/events-*.jsonl` 同形态）；**只把 `failed` 暴露给用户**：① `mgw zcode claim` 直接打印；② 后台 tick 的 `failed` 累计进 `/admin/api/status`（顶栏 5s 轮询已在跑，`design-spec.md:181`）→ 有未读失败时顶栏状态区显示红点」。不新建页面、不新建轮询。

### 🟠 中等

#### M-IX-1 · 设备冲突「报由用户决策」未定义，且承载它的 `import` 子命令缺失

**问题（两处，同一根因）**
1. §15.1 #3 写「**冲突 → 拒绝 + 报由用户决策** / **不自动替换**」（`tech-design.md:960`），但**报什么、在哪报、给用户几个选项、用户如何决策**全部未定义；§15.2 的函数 docstring 又写「冲突则**调用方重新生成**」（`:976`），与 #3「不自动替换」字面冲突——实现者无法判断「拒绝」是硬报错还是给选项。
2. §15.1 #2 的「**导入已有账号缓存 → 复用原设备 ID**」（`:959`）是 Q26-① 的复用规则（`prd.md:613`），但 **M5-0 的三个子命令只有 `login / list / claim`**（`:1254`），**没有 `import`**。而 M4-2 的判据却在测「冲突**输入**返回拒绝而非静默重生成」（`:1251`）——**测了一条用户无法触发的路径**。

**证据**：`tech-design.md:959-960,976,1251,1254`；`prd.md:613-614`。

**建议改法（最小）**
- M5-0 子命令改为 `mgw zcode login / import / list / claim`（加 `import`），并在 §15.1 #3 补一句交互契约：
  > 冲突时**不写盘**，打印：`设备 ID 冲突：账号「X」的 device_id 已被账号「Y」占用。可选：① --reuse Y 的设备 ID（两者共享设备，上游可能风控）② --regenerate（为 X 生成新 ID，上游会视为换设备）③ 取消（默认）`；**默认行为 = 取消，退出码非 0**。
- §15.2 docstring 的「调用方重新生成」限定为「**生成新账号时**」，导入路径明确为「拒绝 + 交用户决策」。

#### M-IX-2 · `mgw setup` 的破坏性写盘缺「解析路径确认」交互，而设计自己记录了路径被劫持的坑

**问题**：§12.4.1 明确记录了「本机 `WORKBUDDY_CONFIG_DIR=/Users/w/.workbuddy-ai` 由另一个产品注入，导致 CLI **跑到了 WorkBuddy AI 的目录**」（`tech-design.md:805-807`），并要求「不要只看日志里的 `productName`，要看 `userConfigPath` 的实际路径」。但 §12.4.1 的写入纪律（备份 / 合并 / 原子写 / 读回校验，`:816-820`）与「实现：`mgw setup <tool>`」（`:822`）**没有任何一步让用户先看到解析结果**。该文件还存在**外部并发写**且历史上被清空过（`:817`）。

**后果**：用户敲一条命令，网关就把 `models.json` 写进一个**用户没机会核对**的目录；写错产品目录后虽然会备份，但用户要自己去发现问题。

**证据**：`tech-design.md:805-807,816-822`。

**建议改法（最小）**：在 §12.4.1「写入纪律」前加第 0 条——
> 0. **写前打印解析结果并等待确认**：`目标目录：/Users/w/.workbuddy-ai（来源：环境变量 WORKBUDDY_CONFIG_DIR）`；交互式需回车确认，非交互需 `--yes`；**`--dry-run` 只打印不写**。
写完打印：`已写入 <绝对路径>；原文件备份为 models.json.bak-<ts>`；失败打印回滚结果。

#### M-IX-3 · 额度聚合端点：消费者与信息架构落点未定义，且 §17 / §19 用词冲突

**问题**：§19 M5-2 只有一行「**额度聚合对外端点**」，判据「接口断言」（`tech-design.md:1256`）——**没写路径、没写响应形状、没写给谁看**。而 §17 在同一件事上写的是「③ **管理端点** 支持手动触发」（`:1154`）。两处用词不同（「对外」vs「管理」），语义指向两个不同的暴露面。

更关键的是 IA：`prd.md` 的 Q27 全篇没有「对外暴露额度」的需求；§16.1 反而明确「运营接口是产品专属业务接口，**不是 OpenAI 兼容 API 的组成部分**」（`tech-design.md:1011`）。若 M5-2 真做成 `/v1/*` 上的「对外端点」，与 §16.1 的边界冲突；若做成 `/admin/api/*`，则**必须回答「管理端哪个页面显示」**——现设计未答。

**证据**：`tech-design.md:1154,1256,1011`。

**建议改法（最小）**：§19 M5-2 改写为一行具体落点——
> **M5-2 · 额度聚合（管理端点）**：`GET /admin/api/zcode/quota` 返回 `{accounts:[{account, plan, used, total, reset_at, status}], aggregated:{used, total}}`；**消费者 = 二期「ZCode 账号管理」页的「用量」面板**（形态已由 `template-vendor-accounts.html` 预演，见 M-IX-7）。**不做对外端点**（与 §16.1 边界一致）。

#### M-IX-4 · 熔断 / 额度耗尽回写资源状态后，用户无法分辨「风控熔断」与「普通失败冷却」

**问题**：§17 要求「熔断 / 额度耗尽时**回写该账号对应 `ResourceState.status`**（复用现有 `bench` / `disable`）」（`tech-design.md:1137`）。但现有资源健康卡只呈现 `状态 / 连续失败 C / 在途 / 冷却剩余 / 最近错误`（`design-spec.md:192-193`），状态点只有 active / cooldown / disabled 三态。回写后：
- 用户**看不出**这个 cooldown 是「ZCode 3012 风控熔断 30 分钟」还是「模型调用连续失败 y 次冷却」——两者同色同文案，但**处置方式完全不同**（前者等 30 分钟，后者该去查 Key）；
- `bench` 与 `disable` 二选一未指定，两者对用户的心理预期差别很大（临时 vs 停用）。

另有一处范围口径不一致：`:1127` 写「3012 风控 → **全局**熔断 30 分钟」，`:1137` 写「回写**该账号**对应 ResourceState」——**全局熔断 = 所有 ZCode 资源一起变红**，这是一个很显眼的用户可见事件，更需要一句解释。

**证据**：`tech-design.md:1127,1132-1138,1253`；`design-spec.md:192-193`。

**建议改法（最小）**：§17 该段补两句——
> ① 熔断统一回写 **`bench`**（临时冷却，非 `disable`），并**同时写 `last_error`**（既有字段）为 `ZCode 风控熔断（30min，至 HH:MM）` / `ZCode 额度耗尽`；② 若为全局熔断，对全部 ZCode 账号一并回写，`last_error` 注明「全局熔断」。

这样无需给 `available()` 加维度，也无需改前端——**总览资源健康卡的「最近错误」列直接可见原因**。

#### M-IX-5 · 验证码 / 住宅代理：无配置入口、无启动自检、无用户提示

**问题**：§16.5 在文档内披露了外部依赖（「🔴 外部依赖必须显式披露……住宅代理需外购/额外部署」，`tech-design.md:1065-1069`），并要求「无住宅代理时的降级行为」进 M5-1 判据（`:1255`）。但从**用户视角**看，§12–§20 没有回答：**我怎么知道我需要配住宅代理？在哪配？**——无配置项、无环境变量、无启动自检、无失败文案。

**证据**：`tech-design.md:1062,1065-1069,1255`。

**建议改法（最小）**：§16.5 表内「硬依赖」一行后补一句——
> **用户侧落点**：住宅代理地址读 `config.yaml` 的 `gateway.zcode.proxy`（无则回退环境变量 `MGW_ZCODE_PROXY`）；`mgw zcode claim` 在未配置时**不静默失败**，直接提示「未配置住宅代理，验证码求解不可用 —— 在系统设置或 `config.yaml` 的 `gateway.zcode.proxy` 填入住宅代理地址；也可 `--manual` 手动完成」。后台 tick 命中同类失败时记入 S-IX-2 的 failed 通道。

#### M-IX-6 · `mgw probe` 无交互设计：长耗时 + 触发频控，却无确认、无进度、无结果输出

**问题**：§13.3 定义了三步探测的算法（`tech-design.md:866-872`），§13.4 定义了串行 + 间隔 + 退避，并给出关键事实「实测探测中约 **1/3 请求触发 429**」（`:897`）。但 CLI 交互层面：**探测哪些模型**（全量？指定？）、**耗时多久**、**是否有进度**、**结果给用户看什么**——全部未定义。§19 M3-3 判据也只到「方言表落盘可断言 / 逻辑可确定性验证」（`:1247`），没有一条是用户可见的。

**后果**：一个会持续几十秒到几分钟、且会触发上游频控的命令，用户敲下去后**没有任何反馈**，只能等——这是 CLI 工具最典型的可用性缺陷。

**证据**：`tech-design.md:866-872,894-898,1247`。

**建议改法（最小）**：§13.3 末尾补一行交互契约——
> `mgw probe [--model <name>|--all]`：默认探测当前启用且**尚无方言记录**的模型；执行前打印「将探测 N 个模型，预计 M 次请求（可能触发上游频控），继续？[y/N]」；逐个模型打印 `✓ <model> → 写入位 reasoning_effort（档位 none/low/…）` 或 `✗ <model> → 探测失败，保留硬编码 fallback`；结束打印成功/失败计数。

## 5. 过度设计专项（交互层面该砍 / 该简化）

> **结论：交互层面没有发现过度设计。** §12–§20 在交互上总体是「少做」而非「多做」——不做 UI、不做 CRUD 界面、不做导入向导、不做通知中心，方向正确。以下逐项确认。

| 项 | 判定 | 理由 |
|---|---|---|
| §20 #12 首期不做前端 UI | ✅ **该砍，砍得对** | 单用户自用 + 开发者工具，先通链路。**但前提条件（CLI 入口）尚未定义完整**（S-IX-3 / A 维度），属「砍对了但没补上替代品」 |
| §20 #15 不做 L-B / L-C 用户录入界面 | ✅ **该砍** | 目录自动带入 + 探测得出；YAML 逃生口（`design-spec.md:104` 支持手改热重载）。仅需补示例（L-IX-2） |
| 是否需要为 ZCode 账号管理设计完整 CRUD 界面 | ✅ **不需要，且设计已正确回避** | 二期直接用已预演的 T-17 形态即可，**零新增设计**（M-IX-7） |
| §16 只做 2 个 operation、不做「运营 DSL」 | ✅ **克制正确** | 各产品接口形态不同，硬编码适配器更可靠（`:1090`） |
| §13.3 三步探测 + §13.4 串行 / 退避 / 缓存 | ✅ **必要复杂度，不是过度设计** | Q25-⑤ 强制要求含 S2（`prd.md:579`）；且 §13.3 已把原「逐档比数值」收敛为**单锚点**（`:884-890`），这是主动减负 |
| §15.2 删抽象层、§14.2 不建四表 | ✅ **正确的减法** | 只有 1 个产品 / 1 个实现（`:946-948,964-968`） |
| **反向：有没有该做的交互被省掉** | ⚠️ **有 3 处** | ① 零映射告警的用户出口（S-IX-1）；② 运营 failed 的出口（S-IX-2）；③ 设备冲突的决策交互（M-IX-1）。三者都不是「要 UI」，而是「**要一句文案 + 一个出口**」，成本极低 |

**结论**：不需要砍任何东西；需要**补 3 个最小出口**（合计约 5 处一句话改动），否则「能跑但没法用 / 出问题不知道」。
