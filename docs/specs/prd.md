## 1. 产品概述

### 1.1 定位
面向**个人开发者**的本地 LLM 网关（模型聚合网关）：将**多供应商、同供应商多账号多 Key** 的模型权益（含各家活动资源/免费额度/订阅套餐）汇总接入，构建**自己的模型资源池**；对外暴露**统一 API**，供本地及局域网内 AI 开发工具（Trae / Cursor / Cherry Studio / Claude Code 等）调用。

### 1.2 核心价值
1. **聚合资源池**：一处配置全部供应商资源（供应商 + Key）与模型映射，工具端只连网关一个地址。
2. **可靠**：失败自动重试（m 次）与资源切换续跑（同模型多资源池），调用不因单 Key/单供应商故障中断——有可用资源即不向工具端报错；冷却后自动恢复；工具中断调用可透传取消上游。
3. **可视**：接入信息统一管理（资源列表 + API 接入指引）+ 统一模型名自动匹配 + 调用量/token/费用多维度统计与健康看板。

### 1.3 设计原则（宪法级约束）
- **全明文**：配置与统计数据全部本地明文文件（YAML / JSON / JSONL），可读可改可备份。
- **纯本地**：无遥测、无远程配置、无自动更新、无任何远端依赖；局域网监听仅服务用户自己的设备。
- **密钥本地**：供应商凭据（API Key / 订阅 Token）仅存本地明文配置（或环境变量引用），不入 git、不硬编码进源码。
- **单用户**：无多用户/注册/登录体系；网关 `/v1/*` 调用以访问令牌（access token）保护，**管理界面与 `/admin/api/*` 免鉴权**（本机自用，Q18-①）。

## 2. 术语与核心概念

> 🔴 **本节是全仓术语的唯一定义源**（2026-10-04 用户定版）。其余文档、代码注释、界面文案、规则文件一律与此对齐；
> 冲突以本节为准。四个核心词：**厂商 / 供应商 / 网关模型 / 资源**。旧文档里把"接入方"叫作「厂商」的写法（如
> 「资源 = 厂商 + Key」「厂商侧资源」「厂商名称」）**均已作废**，读作**供应商**；历史台账/评审记录（`docs/changes/`）
> 按当时措辞保留、不改写，读法见该目录顶部说明。

| 术语 | 定义 | 代码与配置对应 |
|------|------|---|
| **厂商 Producer** | **模型的生产公司**（DeepSeek、月之暗面 Moonshot、智谱、Anthropic、OpenAI、商汤、Google、MiniMax…）。一个模型只有一个厂商；**同一家厂商可以被多个供应商转售**（`deepseek-v4-flash` 可同时来自商汤 API Key 与 CodeBuddy 账号） | 内置目录条目的 `vendor` 字段（`enums/matcher.py::EnumEntry.vendor`，官网取证得来）；「网关模型管理」左栏按它分组 |
| **供应商 Supplier** | **向我们提供模型能力的接入方**，两类：① 「接入模型资源」里的每一个接入（按量 API Key、订阅套餐 Key，如商汤、DeepSeek 直连、OpenRouter）；② 「接入账号资源」里的每个接入产品/账号（CodeBuddy、WorkBuddy、Trae、Qoder、Cline、ZCode…）。供应商 ≠ 厂商：商汤既是厂商（自研 SenseNova）也是供应商（它卖 DeepSeek/GLM 的量）；OpenRouter/Cline 只是供应商 | ① 类 = `Resource`（`product` 为空，字段 `vendor` 存**供应商名称**）；② 类 = `Resource`（`product` 非空）+ 账号 meta。旧文档的「厂商名称 / 厂商预设 / 厂商侧资源 / 接入商 / 接入方」全部改称 **供应商名称 / 供应商预设 / 按 Key 接入的供应商 / 供应商** |
| **资源 Resource（= 模型资源）** | **供应商名下的一个可调用模型接入单元**，由「接入模型资源」与「接入账号资源」两个页面共同维护；系统生成全局唯一 ID（`res-xxxxxxxx`）。账号类供应商的资源是**派生资源**（由账号 + 产品位派生，不落 Key） | `Resource`（`schemas.py`）；账号类由 `accounts/materialize.py` 派生。资源本身**不表示模型**，模型来自资源上的映射条目 |
| **供应商模型名 Supplier Model ID** | 某供应商目录里那个模型标识字符串（如 `sensenova-6.8-flash-lite`、`cline-pass/glm-5.3`、`sn-glm-5-3`、`gfmodel`）。**同一厂商模型在不同供应商处可以长得不一样**，所以这个名字是"条目级事实"，不是网关模型名 | 映射条目的 `model`（`ModelResourceEntry.model`）；账号侧 = 产品位 `product_models[].model` |
| **网关模型 Gateway Model** | **把各供应商的同一个厂商模型标准化成一个名字并统一规格**（上下文/输出/推理档位/图片·视频·音频/工具、参数默认、调度与能力位）。工具端只认这个名字 | `SystemModel` + `models[]`（🔴 **旧名「系统模型 / System Model」作废，与"网关模型"同义**；类名与配置键 `models[]` 保留不改，以免打断已存在的实盘配置文件） |
| **厂商模型 Producer Model** | 厂商生产的那个模型本体（标准名 + 官方规格），是网关模型标准化的依据；内置目录就是它的取证清单 | `BUILTIN_ENTRIES`（官网取证）；合并后的对外承诺 = `core/model_spec.py` |
| **统一模型名枚举池 Model Enum** | 内置规范模型名清单（含别名/分组）：主流厂商模型收录，可扩展；用于自动匹配与手动纠错 | `enums/matcher.py`；`load_enum_pool()` |
| **映射条目 Model-Resource Entry** | 网关模型资源池中的一项：**资源 + 供应商模型名**（+ 可选资源级推理默认）；调度最小单元，拥有优先级（池内顺序）、状态、失败计数 | 类 `ModelResource`（`config/schemas.py:209`，= `models[].resources[]`）；账号侧真相 = 产品位 `product_models[]`（类 `ProductModelMapping`，`(Resource.product, 供应商模型名) → 网关模型 + enabled`） |
| **接入模式 Access Mode** | 供应商的接入形式：`api`（普通按量 API Key）与 `plan`（订阅套餐：TokenPlan / CodingPlan 等，积分/额度制，常含滚动周期额度与专用 base_url）；账号类供应商另走 `product` + `account_ref` | `Resource.access_mode` / `product` |
| **接入形态 Access Form** | 资源的两大类，界面与判据的分界就画在这里：**Key 接入** = 「接入模型资源」页维护、用户自己填 Key（`Resource.product` 为空）；**账号接入** = 「接入账号资源」页维护、由产品账号派生（`product` 非空）。🔴 旧文里与「账号侧」对举、表示 Key 接入那一类时写的**「供应商侧」作废**，读作 **Key 接入侧**；表示「上游那一头」的「供应商侧」（如「供应商侧返回 408」「供应商侧并发不管理」）= **供应商通道**，属工程义、保留 | `Resource.product` 是否为空 |
| **供应商通道默认 Supplier-channel Default** | 参数优先级链的**最后一档**：网关什么都不注入时，那个值由**承接这条请求的那条供应商通道**自己决定（第一方端点即该厂商模型的内置默认；第三方转售同一模型时默认值归通道）。🔴 旧称「厂商内置（默认）」在规范文本与界面文案里作废（PRD §9 归档行与台账存证原文按当时措辞保留） | `core/ir.py::apply_model_params` / `apply_spec_defaults` |
| 账号备注 Account | 供应商资源的可选次要字段，标注该 Key 归属哪个账号（如「主账号」「活动账号」），仅用于区分与统计，**不构成管理层级**（Q18-② 推翻「接入实例→账号→Key 三层管理」） | `Resource.account` |
| 资源池 Pool | 映射到同一**网关模型**的全部资源（有序，按优先级排列） | `SystemModel.resources[]` |
| 生效集 Active Set | 某**网关模型**当前承接流量的那批资源（≤ x 个，Q33-③ 实现为"活跃组"）：成员被移出时由游标方向的下一个可用资源补位；请求打到组内**在途最少**的资源（平局取轮转方向近者）——**串行逐号轮转、并发限在组内**（Q13 的 x 上限 + Q33 的号间轮转，两条同真） | `core/scheduler.py` |
| 切换 Failover | 生效资源因故障被移出生效集（进入冷却），由待命资源补位的过程 | `core/scheduler.py` |
| **重试 Retry** | 网关调用**供应商**失败后，在**同一资源**上重新发起；单次请求重试上限 **m 次**（全局可配，Q18-④ 取消按模型覆盖） | `gateway.retry_per_request`（= m） |
| **切换续跑 Failover-Continue** | 重试耗尽后，当次请求自动切换到**下一个可用资源**重新调用并继续执行任务（对工具端透明） | `core/scheduler.py` |
| 冷却 Cooldown | 资源被移出后静置 N 秒，期满自动恢复进入可用范围 | `gateway.cooldown_seconds` |
| 取消透传 Cancel-Propagation | 工具端中断请求 → 网关检测并主动断开对应的**供应商上游**请求 | `core/scheduler.py` |
| 访问令牌 Access Token | 客户端工具调用网关 `/v1/*` 所需的鉴权凭据（多个、可命名区分工具、可启用/停用/删除）；在 **API 接入页**统一管理（Q18-③） | `gateway.access_tokens[]` |

**术语三条判则（遇到拿不准就这么判）**：
1. 问"**它是谁生产的**" ⇒ **厂商**；问"**我从哪儿调到它**" ⇒ **供应商**；问"**工具管它叫什么**" ⇒ **网关模型**；
   问"**哪一条可调用接入**" ⇒ **资源**。
2. 「上游」是工程层措辞（= 被网关调用的那一端），**指对象时就是供应商**；文档正文一律用"供应商"，
   代码/日志里 `upstream` 与「上游」保留不改（它不承载管理层级语义）。
3. **供应商模型名 ≠ 网关模型名**。凡是描述"资源上填的那个字符串"，一律写**供应商模型名**，
   禁止再写成"厂商模型 ID"（那是本轮作废的旧措辞）。

## 4. 功能需求

> 优先级：P0 = 首版必须；P1 = 首版后尽快；P2 = 可选增强。

### FR-1 资源管理（P0 · Q18-② 扁平化重整）
> **架构定论（2026-09-03 Q18-②）**：资源 = **厂商 + Key**，扁平一层管理；**推翻** v1.0「接入实例（Provider Instance）→ 账号 → Key」三层结构——原因：系统重点是**厂商资源**本身，账号仅是「区分、备注、识别是哪个账号下的」**次要信息**，不值得为其建立管理层级；三层嵌套导致界面层级深、操作繁琐、信息不直观。厂商维度由**厂商预设**（preset）承载，统计维度由事件行冗余 `provider` / `account` 字段承载（FR-6.1），管理对象收敛为**资源列表**。
1. **资源管理（P0 · 扁平模型）**：
   - 新增资源时选择**供应商预设**（预设自动填充协议/base_url/接入模式等模板信息）或 `custom` 空白自定义；填写名称、API Key、可选**账号备注**（区分同供应商不同账号，次要信息）；
   - **资源 ID 系统自动生成**（全局唯一 `res-xxxxxxxx`，Q18-②：ID 属于系统内部标识，用户不关心、不需要手填）；新建时 ID 留空由服务端补齐；
   - 同一供应商可添加任意多个资源（同供应商多账号多 Key 天然支持——每个 Key 一条资源，各自标注账号备注）；
   - **资源字段**：`id`（自动生成）/ `name`（名称备注）/ `preset`（供应商预设，custom 则空）/ `access_mode`（`api` | `plan`，随预设带入可改）/ `protocol`（`openai` / `anthropic` / `gemini`）/ `base_url` / `api_key`（明文，界面脱敏显示）/ `account`（账号备注，可选）/ `enabled`（停用开关）；
   - **Plan 模式差异**：预设含套餐类型标注（如 TokenPlan / CodingPlan）、计费口径（积分制/订阅内不计费）、额度周期说明（如商汤：滚动 5 小时 + 滚动周两层额度）——仅作配置项展示，额度感知暂不做（见 FR-1.9）。
2. **内置供应商预设（P0，首发：商汤）**：
   | 预设 | 模式 | 协议 | base_url | 说明 |
   |---|---|---|---|---|
   | **商汤 SenseNova API（按量）· 本期首发** | api | openai 兼容 | `https://api.sensenova.cn/compatible-mode/v2` | 按量付费 API，OpenAI 全端点兼容（chat/multimodal 均此端点）；Key 为 ModelStudio API Key（console.sensecore.cn 创建）；**模型清单以 `GET /models` 实测为准**（见 §9-附注） |

### FR-3 调度、重试与自动切换（P0 · 核心机制）
1. **资源池**：每个网关模型映射一个有序资源池（N 个资源，按优先级排列）。
2. **生效上限 x（Q13 定调 · 2026-09-03 Q18-④ 全局唯一 · 2026-10-02 Q33-③ 补语义）**：一个网关模型**最多同时有 x 个资源承接流量**——x 的含义由用户指令 1 定为 **「接入资源 + 接入账号（产品维度）两类合计的、每种网关模型最多开启并可并行承接的资源数」**（低负载时这 x 条按轮转逐号换位，并发时超出的请求复用组内最闲者，承接者数恒 ≤ x；选路规则见 FR-3.3）。**x 为全局参数**（`scheduling.max_active_per_model`），对所有网关模型统一生效，**不支持按模型覆盖**（调度机制只有一套，Q18-④）；x=1 时=一次只开一个号，串行请求即逐号轮转（Q33 后不再是"纯顺序集中打最高优先级"）。
3. **活跃组 + 排空换位（号间轮转 · 2026-10-02 Q33-③ 推翻原「并发溢出生效集（不轮询）」）**：每个请求打到**活跃组**（= 从轮转游标起按池序的 x 条可用资源）内**在途最少**的资源，平局取轮转方向近者；**整组排空**才把游标后移、下一组上位。示例：资源池 [A, B, C, D]，x=2 → 第 1 组 {A, B}：顺序两条各走 A、B；A、B 都排空后换位为 {C, D}，再排空回到 {A, B} ⇒ **四个号都被用到**（"开 4 个号就 4 个号轮流"，收益 = 额度与风控分摊）；并发压进来时超出 x 的请求复用组内最闲者 ⇒ **任意时刻 ≤ x 个资源承接流量**（Q13 的上限这一半保持不变）。A 故障 → A 移出并由游标方向下一个可用资源补位。🔴 原文「顺序请求全部走 A（A 在途归零后新请求回 A）」已作废——它是"永远只用最前面 x 个号"的根源，与用户指令 1 直接冲突；推翻理由与实测取证见 §9-Q33 与 `docs/research/26-桌面端依赖与多账号并发-结论.md`。切换轮（同一条请求找替补）**不参与轮转**，按池序优先级找替补（Q33 评审 R1-③）。
4. **请求级重试（P0 · 2026-09-02 新增；Q18-④ 全局唯一）**：网关调用供应商失败（可重试类错误，见错误分类表）→ 在**同一资源**上自动重新发起，最多 **m 次**（m 为全局参数，**默认 3**，不支持按模型覆盖，Q18-④）。重试间隔可配（默认 0 = 立即重试；429 类按官方建议采用**指数退避**）。请求内每次失败**同时累计**到该资源的连续失败计数（参与 y 判定）。
5. **切换续跑（P0 · 2026-09-02 新增 · 端到端不中断）**：单次请求在当前资源上重试耗尽（m 次）仍失败 → 系统自动切换到**下一个可用资源**（按 FR-3.3 同一选路规则取目标，排除本请求已尝试过的资源），用新资源**重新发起同一请求并继续执行任务**（仅针对当次失败的请求，不影响其它请求/会话）；新资源同样适用「重试 ≤ m 次 → 仍失败再切换」规则，如此往复，直到某资源成功或全部资源不可用。**只要还有可用资源，绝不向工具端返回错误**。
6. **流式边界与中途失败策略（P0 · 2026-09-02 确认）**：
   - **首 token 输出前**失败（绝大多数故障发生点）：重试 + 换资源续跑，工具端**无感**——主通道；
   - **已向工具端输出部分内容后**失败：网关**不无感重放**（重发会造成内容重复错乱），处理策略：
     a. 依据供应商**明确错误码**判断：属可重试类稳定性错误（网络中断/超时/5xx 等，且工具端支持重新发起时）→ 按错误分类表重试规则处理；
     b. 不可重试/无法判断的：**把已收到的供应商输出内容与错误信息原封透传给工具端**（SSE 按协议以 error/结束帧收尾），**不吞内容**，由用户判断是否重新触发让模型继续处理；
   - 依据：供应商有明确错误返回码（商汤错误码表见 FR-1.8）；正常情况下（非稳定性问题）供应商不会输出一半才报错，中途失败为小概率场景。
7. **失败阈值 y（资源故障判定）**：某资源**连续 y 次调用失败**（跨请求累计，含请求内重试计数）→ 判定故障，移出生效集进入冷却，触发待命资源补位。y 为全局参数（**默认 2**，不支持按模型覆盖，Q18-④）。
   - **m 与 y 的关系（2026-09-02 确认；生效顺序 2026-09-03 定论：y 先判定，Q14）**：m 管单次请求的重试上限（请求级，默认 3，重试耗尽即切换），y 管资源移出冷却的故障判定（资源级，默认 2，连续失败即切换）；**y 先执行判定**——默认参数下每资源每请求实际尝试 y=2 次即冷却 + 当次请求立即切换，m 的余量仅在 y > m+1 或 429 退避场景生效；失败判定按**供应商资源维度**计数，命中条件即更换资源；两参数独立可配、均为全局参数（Q18-④ 取消按模型覆盖）。
8. **触发切换/移出的条件**：
   - 可重试错误重试耗尽 → 当次请求切换续跑 + 累计失败计数（达 y 判定故障移出冷却）；
   - **供应商明确返回资源不足**（HTTP 429、配额/余额/积分不足错误码与错误信息，规则表可扩展）→ 先**短指数退避重试**（官方建议口径，如商汤 `quota_exceeded_error`；次数少、间隔短，默认 2 次），仍失败 → 立即移出 + 当次请求切换续跑。plan 模式下 429 常为滚动窗口额度耗尽（如商汤 5 小时窗口），冷却时长按接入模式单独配置（默认更长对齐滚动窗口；api 模式用全局默认冷却）。
9. **全部不可用兜底**：资源池内所有资源均不可用（含冷却中、重试与切换续跑全部耗尽）→ 才向调用方返回统一错误信息（各协议标准 error 格式，含「无可用资源」与原因摘要），禁止无限挂起。
10. **冷却自动恢复（P0）**：被移出的资源冷却 N 秒（可配，支持按模式区分默认值）后自动恢复进入可用范围（按原优先级归位）。
11. **取消透传（P0 · 终止转发）**：工具端中断调用（断连/停止生成）→ 网关检测后**主动取消并断开对应的供应商上游请求**（停止上游生成、止损）：
    - 流式：检测客户端断连后立即关闭/取消上游 httpx 请求；
    - 非流式：检测到客户端断连后取消仍在上游途中的请求；
    - **SSE 心跳**：上游长时间无数据时定时发送 keep-alive 注释块，尽早发现断连。
12. **取消语义（不计失败）**：客户端主动中断导致的半途请求**不计入失败计数、不触发切换、不影响冷却**；日志/统计中标记 `aborted`（含已产生的 token）。供应商侧返回 408 `canceled_error`（如商汤）同此语义。
13. **错误分类表**（调度依据；「请求级重试」指是否参与 FR-3.4 同资源重试；规则可配可扩展，供应商特殊语义由适配器校准——商汤实例见 FR-1.8 错误码表）：

    | 错误类型 | 请求级重试 | 失败计数 | 处理 |
    |---|---|---|---|
    | 网络错误 / 连接超时 / 5xx（商汤 `internal_server_error`） | 重试 ≤ m 次，耗尽后当次请求切新资源续跑 | 计入（达 y 移出冷却） | 请求内逐次累计 |
    | HTTP 429 / 配额、余额、积分不足（商汤 `quota_exceeded_error`，官方建议指数退避） | 短指数退避重试（默认 2 次） | 退避耗尽立即判定 | 移出 + 冷却（plan 模式冷却默认对齐滚动额度窗口，可配）+ 当次请求切换续跑 |
    | HTTP 401（Key 无效/鉴权失败） | 不重试 | 不计次 | 立即停用该资源 + 界面告警 + 当次请求切换续跑 |
    | HTTP 403（凭据/权限类；注意商汤 403 `permission_denied_error` = 不支持当前语言，属请求属性 → 透传不切换） | 不重试 | 不计次（凭据类） | 通用凭据类：停用 + 切换续跑；商汤语言类：透传调用方（适配器按错误 type 区分） |
    | HTTP 403（**资源级不可承接**：未订阅该模型计划 / 地域封锁；与上面两类靠**响应体文案**区分） | 不重试（确定性否认，同资源重试无意义） | 不计次 | **换号续跑** + 冷却该条 `(资源, 模型)`（自动恢复）；**不 disable 账号**（其别的模型照常可用）。取证见 `docs/changes/e2e-records/E2E-20261008-cline-403-resource-unavailable.md` |
    | HTTP 404（模型不存在/已下线，商汤 `not_found_error`） | 不重试 | — | 资源无效标记 + 告警（模型层面问题）+ 当次请求切换续跑 |
    | HTTP 408 / 供应商取消类（商汤 `canceled_error`） | — | 不计次、不切换 | 取消语义，标记 aborted |
    | HTTP 4xx 其它（400 参数错等，商汤 `invalid_request_error` / `failed_precondition_error` / `permission_denied_error` 语言类） | 不重试 | 不计数 | 错误透传给调用方（调用方请求本身的问题，换资源同样失败） |
    | 内容审核拦截（`finish_reason: content_filter`） | — | — | 正常结束，不算失败，不计切换 |
    | 客户端主动中断（取消透传） | — | 不计次、不切换 | 标记 aborted |

14. **切换与重试事件记录**：每次重试（资源、第几次、错误类型）与每次切换（时间、网关模型、从哪个资源 → 到哪个资源、原因）均记录落盘（`data/usage/switch-events-YYYYMM.jsonl`）；看板统计（切换/重试次数指标）与请求日志页「切换事件」tab 可查，排查可由 AI 直查明文文件（Q17）。
15. **超时与总预算（P1 · 2026-09-03 终审调小；Q18-④ 全局唯一）**：全局**单次尝试超时**默认 **60s**（原 120s，终审调小；思考型模型首字节慢若被误杀，实测后可调回；全局参数，不支持按模型/资源覆盖，Q18-④）；另有**请求总预算 300s**（单请求全部尝试+重试+退避的总时长上限，**不管成功任务本身的执行时长**——流式输出开始后不受限，耗尽即返回统一错误防挂起；语义详见技术方案 §5.5）。
16. **推理参数：开启与强度（P0 · 2026-09-03 确认，Q15）**：
    - 支持对支持推理的模型设定**推理开启**（thinking 开关，按供应商通道参数形态）与**推理强度**（`reasoning_effort`，取值以该供应商通道为准，如商汤 V4 系 `low/high/max`，网关按 opaque 字符串透传不强校验枚举）；
    - **合并优先级**：**请求级（调用接口时指定）> 资源级默认（接入配置，按资源维度）> 该供应商通道默认（不注入字段）**；
    - 🔴 **与 Q24-⑥ 参数卡的排序（v1.15 / Q28-③ 定稿）**：`SystemModel.params` 里的 `reasoning_effort` / `thinking` 属**模型级网关设置**，**低于资源级默认**（否则本条「不同资源配不同默认」的 P0 能力在任何配了参数卡的模型上都会失效）；该遮蔽由总览横幅 `param_shadowed` 明示，**不留静默**；请求方**显式关闭**同样优先于资源默认开启（区分「未指定」与「显式关闭」）；
    - **资源级默认**：同一网关模型下不同资源可配不同默认（如「免费活动资源默认 low 省额度、主力资源默认 max」）；仅 chat 类资源有效，images 类资源不适用（配置校验警告并忽略）；
    - **请求级**：OpenAI 兼容端点请求体中的 `reasoning_effort` / `thinking` 等字段原样透传（FR-5.1 既有原则），作为显式值参与合并；
    - **切换续跑**：换资源后按**新资源的默认**重新合并推理参数（每次尝试独立构造出站请求，FR-3.5 交互）；
    - 响应侧：思考内容按供应商流式字段差异归一化透传（`reasoning_content` / `thinking_content`，FR-1.8），不受本条影响。

### FR-4 多工具并发稳定运行（P0）
1. 全异步架构：**多个 AI 工具同时调用网关**互不阻塞；**流式（SSE）长连接不阻塞其它请求**；取消透传不阻塞其它连接。
2. 网关整体并发上限可配（保护本机资源，可选项）。
3. 稳定性验收：多工具并发混合场景（流式+非流式+中途取消）长时间运行无内存泄漏、无请求堆积（具体数值验收标准实施阶段定）。

### FR-5 统一 API（P0）
1. **OpenAI 兼容端点（主）**：
   - `GET /v1/models`：返回网关模型列表（OpenAI 格式，仅 enabled=true 的启用模型，FR-2.3）；**且仅返回"可服务"的模型**（至少一条已启用、未失效的资源映射）—— 调用必返 `NO_RESOURCE` 的模型不得对外声明，工具选中即"无报错的失败"（Q28-②）；被隐藏的数量与原因经总览页横幅告知。
   - `POST /v1/chat/completions`：`stream: true/false` 全支持（SSE 逐 chunk 透传）；**工具调用（tool calls / function calling）透传**；请求体其余字段原样透传给供应商（含 `thinking` / `reasoning_effort` 等供应商通道扩展参数，推理参数按 FR-3.16 三级合并：请求指定优先、未指定走资源级默认）；配合 FR-3.10 取消透传。
2. **Anthropic 原生端点（P0）**：`/v1/messages`（含流式），供 Claude Code 等只认 Anthropic 格式的工具直连；内部同样走网关模型调度、重试与取消透传。
3. **图像生成端点（P0 · 首版支持）**：`POST /v1/images/generations`（OpenAI images 格式）：
   - `model` 填「图像生成」分组的网关模型名（如 `sensenova-u1-fast`）；请求参数（prompt、数量、尺寸/宽高比等）透传或映射至供应商端点；响应（b64/url 形式）透传返回；
   - 内部同样走网关模型调度、请求级重试与切换续跑、取消透传；
   - `/v1/images/edits`（图生图/编辑，U1.5 Lite 参考图能力）：P1。
4. Gemini 原生入站端点：P2。
5. **鉴权**：全部入站端点均要求访问令牌（`Authorization: Bearer <token>` 或 `x-api-key`，按各协议惯例）。
6. 错误响应统一为各协议对应的标准 error 格式。
7. **兼容性验收**：curl + 真实 AI 工具实测通过（首发以商汤按量 API 模型为实测对象，参考商汤官方工具接入指引：Trae / Cline / Claude Code / Cherry Studio 等），含中途停止场景的取消行为验证、**单资源连续失败自动切换续跑（工具端无感）**、图像生成调用。
8. 统计口径：流式请求的 token 统计优先读供应商 usage 字段（`stream_options.include_usage`，商汤各模型均支持），无则本地估算并标注口径；aborted 请求按已完成部分计入；图像生成请求计**调用次数与生成张数**（无 token 概念）。

### FR-6 调用量统计与数据看板（P0）
1. **统计维度**：
   - 网关维度（按**网关模型**）：调用次数、token 输入量、token 输出量；
   - 资源维度（按**资源**：资源 ID/名称）：调用次数、token 输入/输出量；
   - 令牌维度（按**访问令牌**）：调用次数、token 输入/输出量；
   - 派生维度（自动聚合；机制口径 2026-09-03 落实，Q17；Q18-② 扁平化后口径更新）：按**供应商**、按**账号**汇总——事件行冗余 `provider` / `account` 字段（写入时由配置快照解析：`provider` = 资源供应商口径——预设资源取预设展示名（如「商汤按量 API」）、无预设资源取资源名称备注；`account` = 资源的账号备注字段，未标注为空），聚合层据此提供 `by_provider` / `by_account`；admin 统计接口返回可用维度键，看板维度 tab 由后端维度键数据驱动生成（FR-7.6）；
   - 图像生成调用：调用次数、生成张数（无 token 概念，单独口径）。
2. **指标**：调用次数（成功/失败/客户端中断分别计）、token 输入/输出、**重试次数**、失败原因分布、切换次数、**平均耗时 / 首 token 时间（TTFT）**、**费用/积分估算**。
3. **成本估算（P0 · 双口径）**：
   - **API 模式**：按单价表估算费用（按供应商 + 模型：输入/输出每百万 token 单价，图像生成按张单价；货币可配；供应商 `/models` 返回 pricing 元数据时可辅助预填）；
   - **Plan 模式**：按积分口径统计（积分系数可配，如商汤按模型积分扣减），或标记「订阅内不计费」；
   - 纯本地算术，非计费系统；未配置口径的模型不计费。
4. **时段与视图**：今日 / 近 7 天 / 近 30 天 / 自定义区间；天 / 周 / 月聚合；**日维度调用趋势图**；模型占比、资源占比等图表。
5. **存储**：本地明文（事件 JSONL 追加 + 日聚合 JSON 快照），看板查询聚合快照，不引入数据库。

### FR-10 网关访问与安全（P0）
1. **监听**：默认监听 `0.0.0.0:<port>`（可配）；API 接入页同时展示本机与局域网两种调用地址。

5. 无任何遥测/远程上报/自动更新机制（宪法级）。

### FR-12 系统运行控制（P0 · 2026-09-03 确认，Q17/D2-D4）

1. **界面重启/停止（P0）**：系统设置页提供「重启网关 / 停止网关」操作（**管理端免鉴权**，Q18-① 修订——原 v1.4 要求 admin 令牌 `allow_admin`，随管理鉴权整体移除而取消）：
   - `POST /admin/api/system/stop`：**优雅停机**——在途请求收尾后退出进程，并释放单实例锁（FR-12.3）；
   - `POST /admin/api/system/restart`：优雅停机 + 释放锁后，经 `os.execv` **进程映像替换自重启**（D3）——**PID 不变、同端口重绑、配置重读、锁重新登记**。
2. **双击启动脚本（P0）**：项目根提供 `启动网关.command`（macOS 双击启动，`chmod +x`）：
   - 脚本流程：cd 到脚本自身所在目录 → 检测 `.venv`（缺失时打印环境搭建指引、**窗口不关闭**）→ **前台启动网关**（日志可见、Ctrl+C 可停）；
   - 已有实例运行时：窗口显示已有实例的后台地址并保持窗口开启（不重复启动，联动 FR-12.3 检测）。
3. **单实例运行限制（P0 · 用户定论：暂不考虑多套并行，同一时刻仅允许一套实例运行）**：
   - 锁文件 `data/gateway.lock`，**明文 JSON**（可查可删，D2），字段：`pid` / `port` / `base_url`（后台地址）/ `started_at`（启动时间）；
   - 启动检测流程：锁不存在 → 写锁启动；锁中 pid 为**自身**（`execv` 重启场景）→ 覆盖重写锁后启动；锁中 pid **存活**（其它实例运行中）→ 打印「已有实例运行中：后台地址 `http://127.0.0.1:<port>/`（PID、启动时间）」并以**退出码 3** 退出——不启动、不换端口、不询问，交互/非交互行为一致（D4）；锁中 pid **已死**（陈旧锁）→ 自动清理后正常启动；
   - **锁释放**：正常退出（stop / restart / Ctrl+C / 信号）经 atexit + 信号处理释放锁；锁检测遗漏的极端场景由端口绑定失败兜底——明确报错退出，不静默换端口。

### 已确认 · Q26 设备身份隔离与批量运营（2026-09-24 需求增补归档）

> 依据：`docs/research/10-设备身份隔离与批量运营机制.md`（含 DSH 源码取证）。本节为**需求真相归档**，详细设计见 `10`。

**Q26-① 虚拟设备身份（每账号一套，全局互异）**

| 项 | 结论 |
|---|---|
| 需求 | 接入不同产品 + 多账号时，**每账号必须对应一个虚拟设备信息**；**不允许多个账号绑定到同一设备 ID** |
| 动机 | 产品风控：一个设备信息登录多个账号会提示异常；同一账号在多个设备上也异常 |
| **证据** | DSH `trae.ts:116-119`「每个账号必须有自己的 `device_id`」；`trae.ts` 头注释「同一天两个账号共用同一 device_id 会被『该设备已签到』拦截」；`trae.ts:108-112`「同一账号用不同 `machine_id` 可能触发风控或要求重新登录」 |
| 定案 | 新增**设备档案表** `device_profiles`（`{id, product, account_id, fingerprint{}, persona{}, created_at, source}`），`(product, fingerprint_key)` **全局唯一**，与 `account_id` **一对一** |
| 复用规则 | 识别本地已登录账号缓存时，若缓存内已有设备标识 → **原样复用，绝不重新生成** |
| 冲突规则 | 缓存 ID 与已有账号冲突 → **拒绝导入 + 报冲突由用户决策**（自动替换会让已登录账号在上游眼里"换设备"，触发风控） |
| 新账号 | 生成**一整套全新自洽画像**（不复用任何已有指纹） |

**Q26-② 设备指纹持久化与轮换**

| 项 | 结论 |
|---|---|
| 不可重新生成 | 设备指纹一经绑定**永不变更**（除非用户显式轮换） |
| 续期不动 | 凭据续期**只改 token/expiresAt，设备字段完全不动**（DSH `trae-auth.ts:10-14`） |
| 轮换方式 | **只存整数代次**，由 `(fingerprint, generation)` 派生新值，**不改写本体**；代次**只增不减**（DSH `types.ts:61-74`、`account-pool.ts:691-692`） |
| per-product 差异 | 只有部分产品需要设备指纹（trae `machine_id`+`device_id` / qoder `machine_id` / lobsterai `uuid`+`keyfrom`；codearts、buddy **无**）→ **必须是 per-product 字段字典，不做通用单一字段** |

**Q26-③ 批量 / 单账号运营操作**

| 项 | 结论 |
|---|---|
| 需求 | 后期增加针对不同产品账号的批量及单账号操作（批量领礼包、批量签到等） |
| 抽象 | `AccountOperation`：`name` / `supported_products` / `execute(ctx, account, device) -> OpResult` |
| **结果四类** | `success` / `already_done`（幂等命中）/ `inactive`（无资格·活动结束）/ `failed`（真错）—— 前三类是正常业务态，**只有 `failed` 需用户关注** |
| 幂等判定 | **以响应体 code 为准，不能只看 HTTP 状态**（DSH 实证：重复签到返回 HTTP 400 + code 10001「今天已签到」，属 `already_done` 而非失败） |
| 执行策略 | **串行 + 间隔**（不并发）；**单账号失败不影响其他账号**；仅网络/5xx 退避重试，业务码不重试 |
| 参与范围 | **运营类跳过 `enabled=false` 账号**；**续期类不看 `enabled`**（两者是独立开关，不可合并——否则停用账号的 `refresh_token` 过期后无法自动恢复） |
| 产品差异 | 能力必须 **per-operation 声明**（DSH 实证：签到只有 CodeBuddy 中国版有，积分余额查询两产品通用） |

**Q26-④ 架构边界（必须显式确认）**

- 运营操作是**产品专属业务接口**，非 OpenAI 兼容 API 组成部分 → **做成与核心调度链路解耦的可插拔模块**（独立 `model_gateway/ops/`，不进 `core/scheduler.py`、不进 `Resource` 主流程）
- **不违反铁律 1**（纯本地 / 无远程更新）：批量运营是**本地主动发起的出站请求**，与调用模型接口性质相同
- **但扩大了网关职责边界**（从"模型转发"扩展到"账号运营"）→ **在 PRD 显式归档，不默默加入**

**Q26-⑤ 落地与排期**

- `D9–D11`（设备档案表 / per-product 字段字典 / 导入复用与冲突拒绝）→ **现在做**（数据结构事后补需迁移凭据，代价大）
- `D12–D15`（轮换代次 / 操作抽象 / 批量执行器 / 首批 operation）→ **等真接入 trae/qoder 类产品时再做**（行为事后加只是加代码，代价小）
- 网关当前为**静态 Key 的 OpenAI 兼容接入**，不实现 OAuth 登录 → 设备身份**现阶段先建数据结构**，出站注入等行为待接入具体产品时开启

### 已确认 · Q28 实现期需求定稿（2026-09-27，v2.0 M3–M5 验收过程中由用户裁决）

> 背景：tech-design v2.0 §12–§21 实施后三角色验收，发现 **PRD 内部两处定级未打通** 与 **两处行为口径需明确**。
> 以下四条为本次裁决，并已回写技术方案 / 代码 / 测试。

**Q28-① 回填 Q25 的两处字面（技术方案 §19 M3-2 判据要求）**

- Q25-②：能力位字段名按**工具契约 camelCase**（`maxInputTokens` / `supportsToolCall` …），推理档位表在 **`caps.thinkingLevelMap`**，不用顶层 `effort_levels`。
- Q25-①：`caps_overrides` **保留字段、砍掉界面**（首期 YAML 手改 + 既有热重载），界面归二期。

**Q28-② `/v1/models` 与 `mgw setup` 只下发「可服务」模型（🔴 行为变更，用户批准）**

- 判据：`enabled` **且** 至少一条**已启用、未失效**的资源映射。冷却中/额度暂时为 0 **仍算可服务**（临时态不该让模型在工具里凭空消失）。
- 理由：把"调用必返 `NO_RESOURCE`"的模型声明出去 = §12.1 要消灭的**无报错失败**。
- 配套可见性：被隐藏模型必须出现在总览横幅（告警新增 `model_unservable`），**不允许只过滤不解释**。

**Q28-③ 推理参数三级优先级的定序（用户裁决「按 Q15」）**

- 冲突来源：**FR-3.16（Q15，P0，已验收）** 写「请求级 > **资源级默认** > 厂商默认」；**Q24-⑥ 参数卡** 写「工具传参 > **网关设置(`SystemModel.params`)** > 厂商内置」。`reasoning_effort` 两边都能配，两条clause 未互相排序。
- **裁决：以 FR-3.16 为准，优先级不动** → 实际生效序 = **请求级 > 资源级默认 > 参数卡（网关设置）> 供应商通道默认**（末档 2026-10-04 定名，旧称「厂商内置默认」作废、同义，见 §2）。
  理由：资源级默认是更具体的一层（"免费资源默认 low 省额度、主力资源默认 max"），若被模型级参数卡盖掉，Q15 这条 P0 特性即失效。
- 参数卡若在**同名字段**上被资源级默认盖住 → 新增告警 `param_shadowed` 明示（覆盖是允许的，**静默是不允许的**）。

**Q28-④ 跨进程出口与调度时机（实现期发现的口径补齐）**

- CLI 与网关是**两个进程**：凡是"要改运行中网关内存态"的动作都必须有管理端点出口 ——
  方言表重载、运营失败红点清零、**风控熔断回写**（`POST /admin/api/zcode/bench`）。缺一个就等于"只在 cron 生效"。
- 运营批量互斥必须**跨进程**成立（锁文件 + pid 判活），纯内存 `set` 不满足 §16.4 判据。
- **运营调度器不得在启动瞬间跑第一轮**：先等一个周期再 tick（否则每次重启都立即发起一次真实领取，重启风暴会对着上游连打）。

**Q28-⑤ `supportsToolCall` 的默认值与适用面（🔴 对技术方案 §12.3 字面的**有意背离**，实现期定稿）**

- 方案 §12.3 写「`EnumEntry` 加 `tool_call: bool = **False**`」。**实测**：工具侧判定是 `supportsToolCall !== true` → **字段缺失与 `false` 行为相同**（都会把 `tools` 从请求里删掉）。
  照字面默认 `False`，§12.1 立项要消灭的"静默删 tools"会**原样保留**（目录未逐条标注的模型全部中招）；
  默认 `True` 后若某模型确实不支持工具，失败是**上游可见的 400**（可发现、可归因），而不是无报错降级。
  → **采用默认 `True`**，并补两条约束：
  ① **非对话端点恒为 `false`**（`images` 等没有 tools 参数可言，声称支持会让工具把文生图模型列进"可用于 Agent"）——
  该不变量写在 `EnumEntry.__post_init__`，内置目录与用户 YAML 两条入口都受约束；
  ② **覆写通道 = `data/model-enums.yaml` 的 `tool_call` 键**（§12.3 的"可按模型覆写"），
  且 `GET/PUT /admin/api/enums` 必须**双向透传**该字段（只导出不读回 = 用户编辑一次枚举池就把 `false` 抹回默认值）。
- 同轮补齐的两处"谎报"型缺陷（属 §21.3 原则 1 的同一类）：
  `mgw setup` 取运行态时**必须带接入密钥**（`/v1/*` 在鉴权中间件后），
  且"未运行 / 超时 / 401 密钥失效"**三态可分辨** —— 把 401 打印成"网关未运行"会让用户永远查不出真因；
  `mgw zcode claim` 在全局风控熔断中**不得**打印"全部正常"（改判退出码 `3` 并给出状态文件路径）。

**Q28-⑥ 运行态状态机与红点事实源（第五轮面板后的定稿，2026-09-28）**

**Q28-⑦ 时刻文案与互斥失败的呈现（第六轮面板后的两项用户裁决，2026-09-28）**

| # | 定稿 | 为什么（实测缺陷） |
|---|---|---|
| ① | 熔断恢复时刻**按读取时刻**渲染：同日写 `…，至 HH:MM`，跨午夜写 `…，至 明日 HH:MM`；`circuit.json` 里只存**裸原因**，不落死时刻串。CLI 的 ⚠ 块、`last_error`、日志同用 `quota.until_label()` 一份口径 | 23:50 熔 30 分钟若烘死成「至 明日 00:20」，用户 00:05 再读界面仍显示「明日」，而那其实是 15 分钟后 —— **同一条落盘状态在午夜前后必须各自说得对**，只有读时渲染成立；反过来跨午夜只写 `至 00:20` 又会把「还要等到过午夜」读成「马上就好」。裁决：跨日才加「明日」，不写日期（熔断最长 30 分钟，跨不过两天，写日期是增加解析成本） |
| ② | 运营互斥锁 **fail closed**：锁目录不可写（或创建不出来）= **整轮拒跑**，参与方逐个记 `failed` 并写明「未对任何账号发起操作 + 请检查数据目录权限」；**取消 `/tmp` 退路**。plan 锁同样要区分「别人正持有」（设计内静默跳过）与「锁建不起来」（计错误 + 留日志） | 第四轮为堵「目录不可写就 `return True` 放行双领」改成退 `/tmp`。退路的毛病不是会失败，而是**成功得可疑**：`/tmp` 本机人人可写、重启即清，而「数据目录不可写」本身已经说明这一轮的状态落不下去（熔断文件、`ops-results` 同样会失败）—— 在这种环境里交付一次「互斥成立、领取正常」的结果就是谎报。且退路一旦也失败，cron 会**每个 tick 静默跳过** = 运营停摆而进程看着正常（最难查的那类故障） |

**Q28-⑧ 熔断"读不动"这一档的口径与呈现（第十二轮面板后的定稿，2026-09-29）**

第十二轮四方面板共同打穿的是同一件事：**"状态读不动"被实现成了"没有熔断"**，并且界面/CLI/红点三处说法互相打脸。逐条定稿（判据与红证见 `docs/changes/e2e-records/E2E-20260928-round5-fixes.md` 第十二轮续节）：

| # | 定稿 | 为什么（实测缺陷） |
|---|---|---|
| ① | `circuit.json` **读不动 = fail closed**：整轮按熔断拒跑，**绝不**把"读不懂"翻译成"没熔断"放行；且这一档**不给恢复钟点、不许诺自动恢复**，唯一出口是删除该文件（须打印绝对路径）。落盘的合并**只延长不缩短** | 面板把 `until_ms` 写成数字串 `"1770000000000"`：`float()` 无差别强转把它收编成合法时间戳 → 熔断在**所有进程里当场消失**，`mark_called()` 也不再受"未知拒写"保护 → 整盘覆盖销毁跨进程凭据，**全程零日志** |
| ② | 拒跑分**两档且不得互相聚合**：读得动的熔断 = 正常业务态 → 记 `inactive`、**不点红点**；读不动 = 原因在用户侧、不删文件永不放开 → 记 `failed`、**必须点亮顶栏红点**并写明"未发起" | 面板实测未知档记 `inactive` 时 `ops_failed_unread=0`：整轮拒跑了但没有任何人知道；反过来把可信熔断也记 `failed` 会让用户每次正常风控都要去查一遍红点 |
| ③ | **界面同屏不得自相矛盾**：未知档的冷却徽章说"需人工确认"并指向「最近错误」列，**不许**一边给它拼钟点、一边在同行写"无需处理"；徽章文案必须是 `status`（+剩余时长）的纯函数 | 面板实测未知档徽章仍印「，至 19:42」而同一行状态说明写"无需处理，自动回池"—— 一个说"等着就好"一个说"要动手"，用户按后者理解就站等 |

| ⑤ | 判坏口径：`until_ms` **只接受 `int/float` 且非 `bool`**；字符串一律算读不动（归因里带截断原值，不同写法不并成一条日志）；JSON **重复键**也算读不动（不许静默"后者顶掉前者"）；缺键 / `null` / 非有限值同样按未知拒跑 | `float(True)==1.0` 是合法数值 → 最常见的"把数字改成 true"会把正熔着的熔断清零；`json.loads` 对重复键默认丢弃前者，等于给了一个静默的覆盖入口 |
| ⑥ | 这一方向必须**写进用户能读到的地方**：README 双语各一条（可信档 vs 读不动档的不同处置，明说"不会自动恢复、需删除状态文件"），PRD/tech-design 归档本节 | 面板核对结果：实现与判据都在，README/PRD/tech-design **零条款** —— 用户只能从 CLI 的一次性输出里知道这件事，而文档暗示"熔断 30 分钟自动恢复" |
| ⑦ | **未决（不自创）**：用户删掉 `circuit.json` 后，界面上那一行仍按旧冷却冻结至多 30 分钟、无反馈。要定的是"**读时重判**（每次渲染回查状态文件是否存在）"还是"**进程间通知**（常驻进程感知删除事件）"——这是产品口径，需用户裁决 | 面板 B-12-4 提出；两种实现代价与语义不同（后者要跨进程信号，前者要定义"谁的状态为准"），不在无裁决情况下挑一个 |

**Q32-① 两条指令与它们的验收口径**

1. **zcode 额度必须有真实数值**——真因不是"联网被风控挡住"，而是**网关对 zcode 额度根本没有联网腿**（旧实现只读客户端日志，而 16/16 个在册账号目录里一个 `.log` 都没有 ⇒ 额度列必然空）。定论：**联网腿 = 额度的唯一实时源**，客户端日志降级为**离线聚合面**（`upstream/zcode/quota.py:7` 三通道表、`upstream/zcode/billing.py:163`、`upstream/zcode/product.py:520`）。验收口径（方案 §10-5）：对表脚本与 DOM 额度列**同一时刻**采集（间隔 ≤1 个 tick）——有 `balances` **且存在未过期 active 包**的号 ⇒ 出数值 + `重置于 MM-DD HH:mm`；只有 balances 的号不因缺「重置于」判红；`plans=[]&&balances=[]` ⇒ 「无套餐」；`available_units=0` ⇒ 「已耗尽」；界面**零裸 epoch**。实盘分布（【探针台账】§3）：16 号全部 `HTTP 200 / code=0 / ≈0.1s`，**6 号出真实 token 数值**（其中一个为**自然耗尽**样本 `available_units=0`）、**10 号是 code=0 的空数组**——「16 号全显数值」不是验收目标，空数组必须落「无套餐」而不是「已耗尽」。
2. **10 个产品每个都要有「账号维度 + 产品维度」刷新额度**——两颗钮是**同一执行体的两条腿**，不是两套实现：执行体 `ops/builtin/query_balance.py:287 run_for(product, account, *, via=…)`；账号级端点 `api/admin_accounts.py:974`、产品级端点 `:1015`（🔴 **产品级 = 该产品下全部账号，不做 `product|null` 的全站形态**——能被调用却没人能点到的 API 面不收）。界面：行内第 3 颗「刷新额度」（序 = 签到 · 续期 · **刷新额度** · 探活 · 删除，前两颗按能力位渲染，`web/static/js/pages/accounts.js:666`）+ 卡头一颗（`:421`）；两者同受能力位 `balance` 门控（在册 10 产品 `balance=True` 10/10，`accounts/registry.py:71–237`）；**模型映射弹窗内零额度入口**（🔴 单层弹窗红线，frontend-spec §7.11）。语义边界：额度刷新是**只读视图**——不改凭据、不消耗签到配额、**停用账号照样刷**（与 §22.6「运营执行跳过停用」正交，否则"为什么停用它"失去依据）。

**Q32-③ 展示契约：三态 + `reason`**

- **额度列五档**（`accounts.js:574-613`）：**有余量 / 已耗尽 / 无套餐 / 未知 / 尚未刷新**。「尚未刷新」= 运行态里**没有额度快照**（网关还没查过这个号）；**唯一词表源 = `docs/specs/design-spec.md`**（方案 §9-4 裁定），页面不得另立第二份。
- **附属标注五档映射**（**不是第六档**，`accounts.js:563-569`）：`circuit`→（冷却中）｜`circuit-untrusted`→（熔断状态不可读）｜`unreachable`→（读取失败）｜`no_credentials`→（未发起）｜`no_identity`→（未发起）（后两档同文案、两条路径不同，必须在数据面分得开）。
- 🔴 **「未知不当零」一字不动**：`state=unknown` 时额度池**一个字节都不动**（`query_balance.py:264`）、`remaining:null` 的行**不得**出「已耗尽」（`accounts.js:601-615`）——"没给数字"与"数字是 0"是两件事。
- **合并写 vs 整键覆盖**（`query_balance.py:76/79/186-243`）：`reason ∈ SILENT`（上表五档）= **上游这一轮没说话** → 只覆盖状态类字段，**保住上一轮** `items/plan/remaining/data_at/plan_key`；其余（正常数值 / `no_plan` / `expired`）= **上游明确说了** → 整键覆盖（`expired` 走覆盖是有意的：凭据死了，旧数值不再可信）。完备性护栏 = zcode 钩子的每条非成功路径必须给出表内 `reason`，**忘登记一档就红在单测，而不是静默洗掉盘上的真实数值**。
- **`重置于 MM-DD HH:mm` 的定义**（`accounts.js:623-627`）= 该号 **active 且 `expires_at` 为 ISO 形状**的包里**最早**的那个 `expires_at`；🔴 **仅当匹配 `^\d{4}-\d{2}-\d{2}` 才渲染，否则整段不出**（`accounts.js:549`）——上游时间字段全是**秒级整数 epoch**（【探针台账】§6.4），**归一化是钩子的责任**（`product.py:497 _iso`），**裸 epoch（或被切碎的 `956800`）出现在用户可见面就是缺陷**。`active` 只表达"这个包有效"，**禁止**因本窗口用尽置 `False`。
- **「查于 X」= `data_at || checked_at`**（上游数据时刻优先，没有才退回网关写盘时刻，`accounts.js:646-650`）——熔断/失败轮上游什么都没给，若"查于"前进到本轮就等于把十几分钟前的数值说成刚刚查过。回执文案「未发起（本轮未对上游发请求）」与「未参与（账号已停用）」**分家**。
