## 0. 结论先行

### 0.1 一句话回答

**DSH 插件不是"本地 LLM 形式"，但它确实是"第三种形态"，而且比"本地端点"还要更靠内一层。**

准确名称：**宿主进程内原生 LLM Provider 插件**（in-process native LLM provider plugin）。接入方式是 `ctx.llm.registerAdapter()`，宿主以**进程内函数调用**消费它 —— **没有网络边界**。

**而用户真正指向的那个形态（本机常驻的标准化模型服务，被全机工具统一接入），恰恰就是 Model-Gateway 的定位 —— 而且我们已经具备。**

### 0.2 三层"本地"辨析（本文的核心框架）

> "本地 LLM"在业界不是一个词，是三个不同的东西。不分开，讨论必然吵不明白。

| 层 | 名称 | 什么东西在本地 | 模型权重在哪 | 边界形态 | 宿主怎么用它 | 代表 |
|---|---|---|---|---|---|---|
| **L1** | **本地权重推理** | 模型权重文件 | **本机** | 无（进程内算） | 指向本机推理服务 | Ollama 原生面、LM Studio、llama.cpp |
| **L2** | **本机端点服务** | **服务进程** | 远端**或**本机 | **网络（loopback）** | 填 base URL + key | **Ollama 的 `/v1` 面**、**Model-Gateway**、one-api / new-api |
| **L3** | **宿主进程内注册** | **适配器代码** | **远端** | **无边界**（函数调用） | 装插件 | **DSH 插件**、VS Code `LanguageModelChatProvider` |

**判据是"边界在哪"**：

- L1 / L2 的边界是**进程或网络** → 任何客户端都能复用（L2 甚至跨机器可用）。
- L3 的边界**不存在** → **只有宿主自己能调用**，任何外部进程都够不着。

> **⚠️ 这个框架的构造说明与已知边界（避免被当成形式化分类学）**
>
> 1. **它不是单一维度的严格分类，而是"两个维度 + 现实用法"的实用划分。** 主判据是**边界形态**（进程内 / loopback / 无边界）；"什么东西在本地"与"权重在哪"是**辅助属性**，用来解释为什么同一句话会被理解成不同东西。
> 2. **三层不是形式意义上的互斥穷尽**。例如：**云端聚合服务**（把 one-api 部署在远程服务器）在"边界"上属 L2，但**不在本机** —— 它落在本表之外。本表只刻画"**本地** LLM"这个说法的三种真实用法，不是 LLM 接入形态的全集。
> 3. **L1 与 L2 常同时存在**：Ollama 一个进程同时提供 L1（原生面，服务本地权重）与 L2（`/v1` 面，可服务本地或云端权重）—— 见 §1.2。**层是"接入面的性质"，不是"产品的性质"。**
> 4. 因此本文的用法是：**说"本地 LLM"时必须指明是哪一层**，而不是宣称这三层穷尽了一切。

### 0.3 用户判断的精确化（不推翻，只分层）

| 用户的判断 | 结论 | 精确表述 |
|---|---|---|
| "不是 API 形态" | ✅ **成立** | 插件不对外提供任何推理端点 |
| "不是 CLI 形态" | ✅ **成立** | `package.json` 无 `bin`；全仓 `spawn` 只用于开浏览器 |
| "像是'本地 LLM 形式'接入" | ✅ **成立** | 它确实是既非 API 也非 CLI 的**第三形态**，且是**最靠内**的一种。准确落在 **L3**。 |

> **关于 `07 §0.2` 初稿的自我修正**：该节曾写作"⚠️ 方向对、**措辞错**"。这是**学究式抬杠** —— 它把讨论引向"本地是不是指本地跑权重"这个纯语义问题，反而把用户**真正识别出来的那个判断（这是第三种形态）给盖掉了**。用户识别对了。"本地"在 L2 与 L3 两种读法下都成立，只是**指向不同的层**。本文给出分层，不再做措辞评判；`07 §0.2` 与 `§1.4` 已同步改写。

### 0.4 对 Model-Gateway 的四条结论

1. **我们网关是 L2，而且是 machine-wide 的 L2。** 它常驻一台机器，用标准协议（OpenAI 兼容 + Anthropic 原生）向**这台机器上所有 AI 工具**提供统一模型入口 —— 这正是补充说明里描述的定位。**上游可以任意多（厂商 API / 账号授权 / 甚至本地权重），但出口只有一个、且必须是标准协议 + 网络边界。**
2. **L3 与我们的定位互斥。** L3 要求适配器代码**住进某个具体宿主**；我们的定位是**不属于任何具体工具**。所以"要不要做插件"**不是性能取舍，而是定位一致性问题**（§3）。
3. **网关的"特有机制"（容错 + 模型统一）在 L3 下会被破坏，不只是"变慢"。** 冷却状态、切换状态、用量统计、跨厂商模型名映射表 —— **这些都是有状态的中枢能力，只能有一份**。放进 N 个宿主插件 = N 份无共享副本 → **"容错"退化成"每个工具各自容错"，"统一"退化成"各宿主各有一套映射"**（§2.3.1）。**这是比性能论证更根本的理由。**
4. **该借鉴的不是 L3 这个形态，而是 DSH 插件在 L3 里沉淀的四类机制**（提供方身份与模型目录 / 适配器吸收厂商差异 / 凭据与索引分离 / 一 provider 一协议）—— 这四类**在 L2 下同样适用**，因为它们解决的是"协议与元数据"问题，不是"进程边界"问题（§4）。

## 1. 业界"本地 LLM"的两种标准形态（外部取证）

### 1.1 L1：本地权重推理（Ollama 原生面）【一手】

Ollama 官方 API 文档（`docs/api.md`）列出的端点**全部是原生面**：

| 端点 | 用途 |
|---|---|
| `POST /api/generate` | 文本补全 |
| `POST /api/chat` | 对话补全 |
| `POST /api/create` | 创建模型 |
| `GET /api/tags` | **列出本地模型** |
| `POST /api/show` | 模型详情 |
| `POST /api/copy` / `DELETE /api/delete` | 复制 / 删除 |
| `POST /api/pull` / `POST /api/push` | 拉取 / 推送**权重** |
| `POST /api/embed`（及已被取代的 `/api/embeddings`） | 向量 |
| `GET /api/ps` | **列出正在运行的模型** |
| `GET /api/version` | 版本 |

文档中所有 `curl` 示例指向 **`localhost:11434`**（默认端口）。

**`ollama pull` 下载权重**这一步是 L1 的定义性特征 —— **权重在本机**。`GET /api/tags`（本地模型清单）与 `GET /api/ps`（正在运行的模型）这两条端点，在纯远端聚合服务里**没有对应物**。

### 1.2 L2：本机端点服务（Ollama 的 OpenAI 兼容面）【一手】

Ollama 官方 OpenAI 兼容文档（`docs.ollama.com/api/openai-compatibility`）逐字给出：

```python
client = OpenAI(
    base_url='http://localhost:11434/v1/',
    api_key='ollama',  # required but ignored
)
```

支持的兼容端点（逐字）：`/v1/chat/completions`、`/v1/completions`、`/v1/models`、`/v1/models/{model}`、`/v1/embeddings`、`POST /v1/responses`（v0.13.3 起）。

**三个关键观察：**

1. **同一个 Ollama 同时提供 L1（原生面）与 L2（兼容面）。** 客户端走哪条都行；但**能被"任意 OpenAI SDK 客户端"复用的是 L2 那条**，因为它是**标准协议 + 网络边界**。
2. **`api_key='ollama'  # required but ignored`** —— 协议要求这个字段存在，服务端根本不校验。这与我们网关"未配置任何接入密钥时 `/v1` 端点免鉴权放行（本地单用户场景）"（`model_gateway/main.py:174-175`）是**同一类设计取舍**。
3. **`/v1/models` 是 L2 的"目录面"**，也是宿主做模型发现的唯一入口。

**这就是"本地 LLM 形式"在业界最通行的读法：本机有个常驻服务，宿主填 base URL 指向它。**

### 1.3 L3：宿主进程内注册（DSH 插件 / VS Code）【一手】

- **DSH 插件**：五个适配器全部通过 `ctx.llm.registerConfigurableProviders()` + `ctx.llm.registerAdapter()` 注册（`src/llm-adapter.ts:1454` / `:1445` 等五组，见 07 §1.1 依据 2）。推理接口是 `async *stream(options: GenerateOptions): AsyncIterable<StreamChunk>`（`src/llm-adapter.ts:835`）—— **进程内异步迭代器，零序列化、零 socket**。
- **同进程的硬证据**：`AGENTS.md:984` 记录了一个真实事故 —— OAuth 回调服务器 `listen()` 失败且未注册 `'error'` 处理器时，错误"成为**进程级 unhandled error**，把**整个 DSH 宿主**打挂"。
- **VS Code** 的 `LanguageModelChatProvider` 同属 L3（08 §1.2）。
- **仓库自己明确否决 sidecar**：`docs/lobsterai-integration-plan.md:131` 整节标题「核心判断：不需要跑那个反代」，`:136` 给出理由"而本插件运行在 DSH 宿主进程内，`ctx.llm.registerAdapter()` **已经就是那一层**"，`:144` 列出收益"少一个进程、少一个端口、少一份配置"。

**L3 不是"本地 LLM"，L3 是"进程内 provider"。**

用"本地 LLM"称呼 L3，会导致一个**具体的误判**：以为 DSH 侧存在一个**可被网关调用的本地推理后端** —— 不存在。因为 L3 **没有对外边界**（§2.3）。

## 2. Model-Gateway 落在哪一层

### 2.0 定位原话（用户陈述，逐字）

> "这个网关工具**目标就是服务器电脑运行的所有 AI 工具用的**，所以它**不是某个编程工具内部的**，而是一个**独立的**、可以**对接融合很多独立的模型厂商**、也可以**授权使用一些工具内部的模型数据**。然后经过网关**统一输出标准化服务**。"
>
> "这个网关**就是一个公共的中枢网关**，它**接入了两方面的模型使用方式**：**一个是各大模型厂商源头的 API 能力直接对接进来；另一个是通过授权一些工具产品账号登录，来使用这些授权账号内部的模型能力**。所以我们**这一网关它有一个特有的机制**，就是有**容错机制、模型统一机制**，可以做到**对模型对接的稳定、高效**。"

**把这段话拆成结构，就是本项目的完整形态定义：**

| 结构 | 内容 | 落在哪一层 | 已有 / 待建 |
|---|---|---|---|
| **上游通路 A** | 各大模型厂商**源头 API** 直接对接 | 出站 HTTPS（L2 的服务进程内） | ✅ **已有** —— `resources[]` + `preset` + `access_mode: api`（`config.example.yaml:37+`） |
| **上游通路 B** | **授权工具产品账号登录**，使用该账号**内部的模型能力** | 出站 HTTPS（服务进程内） | ⏳ **待建，且必须先区分形态** —— 见下方「⚠️ 通路 B 的两种形态」 |
| **中枢** | **容错机制 + 模型统一机制**（重试 / 冷却 / 切换续跑 / 模型名归一 / 参数归一） | **服务进程内** | ✅ 部分已有 —— `scheduler.py`（重试+切换续跑）、`enums/matcher.py`（模型名三级归一）、`core/ir.py`（推理参数归一）。**⚠️ 作用域受合规约束，见下方「⚠️ 容错机制的作用域」** |
| **下游出口** | **统一输出标准化服务**（一个端点给全机所有 AI 工具） | **L2 本机端点** | ✅ **已有** —— `/v1/models` + `/v1/chat/completions` + `/v1/messages` |

> **⚠️ 通路 B 的两种形态（本表初稿未区分，经独立审计指出后补上）**
>
> "授权工具产品账号登录"有两种实现，**合规性完全相反**：
> - **②-a 官方授权形态**：用**你自己账号**在**官方**申请的 API Key / SDK / OAuth，调**官方开放接口** → ✅ **合规**（厂商明确欢迎）
> - **②-b 逆向形态**：提取工具客户端**内部凭据**，**冒充官方客户端**调内部端点 → 🔴 **违规**（三家 ToS 明文禁止）
>
> **`05` / `06` 号文档的结论是"不要走 ②-b"** —— 本表初稿把它们的结论**当成了支持建通路 B 的依据，引用方向相反，现已纠正**。
> **三家初期平台的判定**（详见 `00` 号文档 §六·零）：**CodeBuddy ✅ 有 ②-a**（官方 API Key + Agent SDK）；**TRAE ✅ 有等价物**（火山方舟）；**WorkBuddy ❌ 两者皆无 → 通路②暂不可行**；**智谱 ✅ 有 ②-a**（标准 API Key）。
> **所以定位里的通路②并未落空 —— 它只以 ②-a 形态成立。** `01` 号文档（DSH 插件的逆向接入机制）的定位是**机制知识参考**，**不是可照搬的实施依据**。
>
> **⚠️ 容错机制的作用域（同上，经审计指出后补上）**
>
> `05` 号文档明确限制：**②-b 场景下"多账号轮转 / 冷却避让 / 积分耗尽避让 / 自动签到 / 聚合式重试编排"一律不做**（§P1-2 / §P1-4 / §P1-6）。
> 但**这不否定网关的容错机制** —— 它只是要求**按上游形态分层**：**通路 ① 与 ②-a 上容错机制完整可用**（那是你自己的额度，与"规避风控"无关）；**②-b 一律不进调度池**。
> 架构含义：`resources[]` 需新增 `upstream_form` 标记（`official-api` / `official-sdk` / `reverse`），**容错策略按标记分派** —— 详见 `00` 号文档 §六·零·3。

> **这张表就是"为什么是 L2"的完整答案**：上游可以是任意多种（厂商 API / 账号授权 / 甚至本地权重），**但出口只有一个、且必须是标准协议 + 网络边界** —— 因为下游是"全机所有 AI 工具"，而**工具只会说标准协议**。
>
> 一句话：**上游的多样性由"适配器层"吸收，下游的稳定性由"标准端点"保证。** 这两件事都发生在 **L2 的服务进程里**，**不需要也不应该进入任何一个宿主的进程**。

### 2.2 与 Ollama L2 面的形态同构性

| 维度 | Ollama（L2 面） | Model-Gateway | 是否同构 |
|---|---|---|---|
| 部署形态 | 本机常驻服务 | 本机常驻服务（可选局域网） | ✅ |
| 监听 | `localhost:11434` | `0.0.0.0:8300` | ✅（我们更宽） |
| 模型发现 | `GET /v1/models` | `GET /v1/models` | ✅ |
| 对话 | `POST /v1/chat/completions` | `POST /v1/chat/completions` | ✅ |
| 鉴权字段 | `api_key`（"required but ignored"） | `Authorization: Bearer mg-…`（未配置则免鉴权） | ✅ |
| 第二协议面 | `/api/*`（Ollama 自有协议） | `/v1/messages`（Anthropic 协议） | ✅（都是"第二协议面"） |
| 额外能力 | `/v1/embeddings`、`/v1/responses` | `/v1/images/generations`、`/admin/api/*` | 各有侧重 |
| **模型权重位置** | **本机**（L1 特征） | **远端厂商** | ❌ **唯一差别** |

**结论：结构与 Ollama 的 L2 面完全同构；唯一差别是权重位置。** 而对下游客户端而言，**权重在哪是不可见的** —— 客户端只看到"一个能列出模型、能对话的本机端点"。

> 补充：Ollama 文档也确认了这一点 —— 它的 `/v1` 面**既能服务本地权重模型，也能服务云端模型**（"Direct cloud access" 一节给出 `base_url="https://ollama.com/v1"`）。**同一个协议面、两种后端**，正是 L2 层的价值所在。

### 2.3 结论：我们是 L2，且比 Ollama 的 L2 面更贴合"全机统一入口"

补充说明里的定位可以**逐句对上** L2 的定义：

| 用户描述 | 对应 L2 的哪一项 | 证据 |
|---|---|---|
| "部署在一台服务器上、常驻" | 常驻服务进程 | `model_gateway/main.py:307`（`uvicorn.Server`） |
| "服务这台机器上所有 AI 工具" | `0.0.0.0:8300` + 每工具一个 token | `config.example.yaml:10-11`、`:17-20` |
| "聚合多家独立厂商" | `resources[]` 扁平资源池 | `config.example.yaml:37+` |
| "也能授权使用一些工具内部的模型数据" | **上游**能力（借鉴 DSH 插件的授权接入） | 见 `01` / `05` / `06` 号文档 |
| "统一标准化输出" | 三个标准面：`/v1/models` + `/v1/chat/completions` + `/v1/messages` | `model_gateway/api/openai_compat.py:36`/`:101`、`model_gateway/api/anthropic.py:316` |
| "不属于任何单个编程工具" | 独立进程，无 `bin` 依附，不装进任何宿主 | `model_gateway/main.py:288`（`main()` 独立入口） |

**所以我们不需要"变成"L2 —— 我们已经是 L2。** 需要做的是把 L2 面**打磨到零摩擦**（§4），而不是新造一个 L3。

#### 2.3.1 "特有机制"这一条，恰恰是 L3 做不到的（决定性补充）

用户点出的**特有机制 = 容错机制 + 模型统一机制**。这一条比"全机统一入口"更能说明形态选择：

| 机制 | 在网关里是什么 | 为什么**必须**在 L2（中枢）而不是 L3（宿主） |
|---|---|---|
| **容错机制** | 重试（`retry_per_request`）→ 连续失败冷却（`fail_threshold`）→ **切换续跑**（`max_active_per_model`）；请求总预算；配额退避 | **状态是全局的**：某厂商 Key 在 10:00 被判定失败并冷却，**10:01 从另一个工具来的请求必须也看到这个冷却**。如果机制分散进 N 个宿主的插件里，**每个宿主各有一份独立状态** → 冷却不共享、切换不共享、用量统计分裂。**"容错"变成了"每个工具各自容错"，等于没有容错。** |
| **模型统一机制** | 模型名三级归一（精确 → 别名 → 规范化，`model_gateway/enums/matcher.py`）；推理参数三级合并（`model_gateway/core/ir.py`） | **映射表必须唯一**：同一个 `deepseek-v4-flash` 在厂商 A 叫 `deepseek/deepseek-v4-flash`、在厂商 B 叫别的名字 —— 这份**跨厂商对照表只能有一份**。放进 N 个插件就是 N 份副本，必然漂移。 |

**结论**：网关的差异化能力是**有状态的中枢能力**（冷却 / 切换 / 用量 / 映射表）。**有状态的东西天然属于中枢，不属于边缘。**

> **⚠️ 本条论证的适用边界（自我修正，避免过度推论）**：它**只否决"胖插件"**（把凭据 / 账号池 / 调度搬进宿主）—— 因为那才会产生 N 份无共享状态。
> 它**不能**否决"**瘦插件**"（插件只做"把请求转发给网关的 L2 面"，状态仍全在网关 —— 见 §5 与 `08 §4.4`）。**瘦插件下状态仍然是集中的，本条论证不适用。**
>
> 那么为什么仍然不做瘦插件？**靠另外三条论证**：① 成本随宿主数线性增长（`N × 1000~1600 行`，§3.4）；② 跟宿主**内部 API** 走，版本漂移风险最高（§3.3）；③ **同进程 —— 插件崩了打挂宿主**（§3.3，有 `AGENTS.md:984` 真实事故背书）。
>
> **一句话：§2.3.1 否决"胖插件"，§3.2~§3.4 否决"瘦插件"。两者合起来才是"不做 L3"的完整理由。**

> 这条论证比 §3.2 的数量级论证更根本：**§3.2 说 L3 省不了多少延迟；§2.3.1 说胖插件会破坏网关的核心价值。** 前者是"不划算"，后者是"做错了"。

**顺带回答一个容易混淆的点**：既然网关是 L2，那么"DSH 插件那套东西"对我们还有没有用？**有，但用处在上游，不在下游。** 插件里真正有价值的沉淀是"**怎么把平台内部的模型能力授权提取出来**"（五套认证协议、账号池、凭据续期、限流切换）—— 那是**上游适配器**的参考（对应 §2.0 表的"上游通路 B"）。**下游形态我们自己就是标准答案。**

## 3. 为什么 L3 与我们的定位互斥（决定性论证）

### 3.1 定位冲突（最重要的一条）

L3 的适配器代码**必须住进某个具体宿主**：`ctx.llm.registerAdapter()` 里的 `ctx` 是**宿主进程的上下文**，离开宿主它什么都不是。

而网关的定位是"**不属于任何单个编程工具**"。写一个 DSH 插件 = 把网关的一部分搬进 DSH = **网关开始依附 DSH**。一旦为 DSH 写了插件，就会立刻面临"为什么 Trae 没有""为什么 ZCode 没有" —— 于是**网关的形态被它要服务的工具牵着走**。

**形态选择不是"哪个更快"的函数，是"网关是什么"的函数。** 这一条是决定性的；下面三条是佐证（即：即便抛开定位，L3 也不占优）。

### 3.2 数量级论证（为什么"插件更快"这个直觉不成立）

| 环节 | 量级 |
|---|---|
| L3 插件省掉的：本机 loopback 的 TCP 握手 + HTTP 头 + JSON 序列化 | **亚毫秒** |
| 网关端到端延迟（由**上游厂商 API** 主导） | **几百毫秒 ～ 数秒** |

相差 **2～3 个数量级**。为省 0.1% 的开销，牺牲可移植性 + 进程隔离 + 版本稳定性 —— 不划算。（完整推导见 08 §4.2 理由 1）

### 3.3 稳定性论证（有真实事故背书）

| 形态 | 崩溃隔离性 | 版本漂移风险 |
|---|---|---|
| **L2（API）** | ✅ **进程隔离** —— 网关崩了只影响自身 | **最低**（OpenAI 兼容面几乎冻结） |
| L3（插件） | ❌ **同进程** —— 插件抛未捕获错误可打挂宿主 | **最高**（跟宿主**内部 API**） |

L3 的隔离性问题**不是理论推测**：参考插件自己的 `AGENTS.md:984` 记录了真实事故（§1.3）。

对网关这种"要长期稳定服务多个客户端"的定位，**稳定性权重必须高于那点延迟**。

### 3.4 成本论证

- **L2 的成本恒定为 1** —— 而且我们**已经有** OpenAI 面 + Anthropic 面两个入站面（`openai_compat.py`、`anthropic.py`）。
- **L3 的成本 = `N 宿主 × 1000~1600 行`**，且要跟 **N 套宿主内部 API** 的变更（Cordis 官方自述 API 尚未稳定，见 08 §2.2）。
- 覆盖 10 个宿主时，差距被放大到不可接受。

### 3.5 本节结论

**L3 与我们的定位互斥；即便抛开定位，L3 也不占优。**

所以默认立场是：**不写宿主插件**。唯一例外见 §5 —— 某个宿主**既无自定义 provider 能力、又有公开插件 API** 时（目前仅 VS Code 落在这一格），才考虑**瘦插件**。

## 4. 该借鉴什么：从 L3 插件里搬走的四类机制

> **注意：借鉴的是机制，不是形态。** 这四类机制在 L2 下同样适用 —— 因为它们解决的是"**协议与元数据**"问题，不是"**进程边界**"问题。

### 4.1 机制一：提供方身份 + 模型目录（Provider identity + catalog）

**DSH 插件怎么做的**：每个厂商注册为一个**具名 provider**，带 `displayName` 与 `settingsNs`：

```ts
ctx.llm.registerConfigurableProviders([
  { provider: PROVIDER, displayName: 'CodeArts Agent', settingsNs: 'llm-codearts', settingsPath: [] },
])
```
（`src/llm-adapter.ts:1454-1443`）

模型目录**独立于 provider**（`listModels()`，见 07 §4.3），settings 页按 `settingsNs` 分组渲染 —— 用户看到的是"CodeArts Agent 这个提供方下面有哪些模型"，而不是一堆裸模型名。

**映射到我们**：我们的对应物是 `GET /v1/models`（`model_gateway/api/openai_compat.py:36`），但**只下发 6 个字段**（`id` / `object` / `created` / `owned_by` / `endpoint` / `group`），而 `EnumEntry` 里**存了 16 个字段**（`model_gateway/enums/matcher.py:17-49`：含 `context_window` / `max_output` / `image_input` / `video_input` / `audio_input` / `reasoning` / `effort_levels` / `params_default` / `vendor` / `display` / `aliases` …）。**这是能力浪费**（`00` 号文档 B3）。

**为什么现在特别值得补**：DSH 的"获取可用模型"探测**读取的正是 `data` 数组或 `models` 对象**（【一手】DSH 官方文档逐字）：

> "**获取可用模型提示既没有 `data` 数组也没有 `models` 对象**：端点返回的列表格式不在探测的读取范围内。请手动输入模型。"

我们返回 `{"object": "list", "data": [...]}` —— **正好命中 `data` 数组**，探测会成功。但探测只拿得到 `id`，**模态 / 上下文窗口 / 推理档位它拿不到**，而这些在 DSH 侧**必须手填**（见 §4.2、§4.4 引用的 `input` / `context_window` / `max_output` / `reasoningEfforts`）。

> **⚠️ 补元数据时必须绕开 B4**：枚举池里 `claude-sonnet-4` / `claude-opus-4` 两条**属性未取证**（`model_gateway/enums/matcher.py:137` 注释逐字："跨协议族预置（Anthropic 原生 model id 别名，供 Claude Code 直连解析；**属性未取证**）"）。**未取证的字段应省略，不能下发 `null`** —— 客户端会把 `null` 误判为"不支持"。

### 4.2 机制二：适配器层吸收厂商差异（Adapter absorbs vendor quirks）

**DSH 插件怎么做的**：`compat` 开关族 —— `supportsDeveloperRole` / `maxTokensField` / `thinkingFormat: deepseek` / `input` / `defaultInput` / `reasoningEfforts` / `modelOverrides`（`07 §4.3` 有实现矩阵）。

**DSH 官方排错文档把这两个坑列为"网关最常被拒的两样"**（【一手】逐字）：

> "其中两样占了绝大多数。声明了推理能力的模型，其系统提示词会以 `role: "developer"` 发出，很多网关直接拒绝；输出上限则写作 `max_completion_tokens`，只认 `max_tokens` 的服务端会拒绝。"

以及官方给出的解法（【一手】逐字）：

> "**密钥与地址都正确，网关却拒绝每一个请求**：它的请求形状与 OpenAI 不同。先在路由上设 `compat.supportsDeveloperRole: false` 与 `compat.maxTokensField: max_tokens`。"

**这条证据的价值**：DSH 官方**把修复责任放在客户端侧开关上，而不是要求网关改行为**。这**印证了 `08 §4.3` 第 3 项的判断** —— 我们倾向的"零代码方案（文档告知用户设两个开关）"是**官方推荐路径**，不是权宜之计。

**映射到我们**：我们的 `model_params`（`model_gateway/main.py:67` 定义 / `:93` 装配）+ 资源级推理默认（`model_gateway/main.py:88-91`）是同类东西，但**对 `developer` / `max_completion_tokens` 零命中**（全仓 grep 各 0 处）→ 收到即**原样透传**。透传链路：`model_gateway/api/openai_compat.py:104`（读 body）→ `:123-125`（`body` 装入 `IRRequest`）→ `model_gateway/core/scheduler.py:223-232`（出站组装）→ `model_gateway/adapters/openai_out.py:66`。**这是 B6 互操作缺口。**

**动作**：文档给出 DSH 侧开关配置（**零代码**）；是否在网关侧做归一需拍板 —— 因为它属于**语义改写**（把客户端的意图改掉）而非**协议转换**（同一意图换一种表达），与"透传优先"（`api/anthropic.py:3` 逐字："IR 双向转换（透传优先，只做协议间必需的语义映射）"）和铁律 4「无依据自创禁止」有张力。

### 4.3 机制三：凭据与索引分离（Credential / index separation）

**DSH 插件怎么做的**：凭据存 `ctx.credentials`，索引存 `ctx.settings` 的 `llm-${product.id}` namespace，两者靠 `credentialRef` 关联（`01` 号文档有完整链路）。

**DSH 宿主怎么做的**（【一手】逐字）：

> "密钥是**只写**的。保存后，页面只会收到脱敏描述符，永远不会收到明文密钥。密钥存储在 `$DSH_HOME/.credentials.yaml` 中，settings 只保留它的**凭据引用**。"

**映射到我们**：我们的 `resources[].api_key` 是**明文存在 `config.yaml`**（`config.example.yaml:48` 逐字注释："`api_key: sk-xxxxxxxx          # 明文；后续支持 ${SENSORVA_API_KEY} 环境变量引用（P1）`"）。

**值得借鉴的是"只写 + 引用"这个交互契约**（管理界面保存后只回脱敏描述符，不回明文），**不是它的存储位置** —— 我们的铁律 1 明确要求"密钥仅存本地明文"（`config.example.yaml:3`）。

两者的**共同点**恰好是关键：**凭据与路由配置分离，用引用关联**。这样带来的好处是一致的 —— **配置文件可以导出、分享、进版本库，而不泄密**。

### 4.4 机制四：一个 provider = 一种协议（One provider, one protocol）

**DSH 官方逐字**（【一手】）：

> "**API 协议**必须选网关实际使用的那一种，选择框提供三种：OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages，在 `settings.yaml` 中分别存为 `openai-completions`、`openai-responses` 和 `anthropic-messages`。**一个提供商只使用一种协议，网关同时提供两种时需要建两个提供商。**"

**映射到我们**：我们**同时**提供 OpenAI 面（`/v1/chat/completions`）与 Anthropic 面（`/v1/messages`）→ **用户在 DSH 里需要建两个 provider 条目**（例如 `mgw-openai` 与 `mgw-anthropic`，base URL 相同、协议不同）。

**这是一个必须写进对接文档的坑** —— 否则用户会以为一个条目能通吃，然后在"为什么我的 Claude 模型走不了"上卡住。

### 4.5 机制小结

| # | 借鉴的机制 | 在 L3 里的形态 | 在 L2 下的对应动作 | 成本 |
|---|---|---|---|---|
| 1 | 提供方身份 + 模型目录 | `registerConfigurableProviders` + `listModels()` | **`/v1/models` 下发富元数据**（补 B3，绕开 B4） | 小 |
| 2 | 适配器吸收厂商差异 | `compat` 开关族 | **文档给出 DSH 侧开关配置**（补 B6，零代码优先） | 文档 |
| 3 | 凭据与索引分离 | `ctx.credentials` + `settingsNs` + `credentialRef` | 管理界面"只写 + 引用"交互（保留明文存储） | 中 |
| 4 | 一 provider 一协议 | 三种 `api` 值互斥 | **文档写清"两个协议 = 两个条目"** | 文档 |

## 5. 形态决策矩阵（宿主能力 × 我们的动作）

| 宿主能力 | 代表宿主 | 我们的动作 | 每宿主成本 |
|---|---|---|---|
| **有"自定义提供方"**（任意 base URL + 协议选择） | **DSH**（【一手】官方支持）、Continue、Cline、Roo Code、Zed(ACP) | **只需文档 + 富元数据** —— 用户填 base URL 即通 | **0** |
| **只能改环境变量指向网关** | Claude Code（`ANTHROPIC_BASE_URL`） | **我们已有** `/v1/messages` | **0** |
| **有公开 provider 插件 API，但无自定义端点** | VS Code（`LanguageModelChatProvider`） | 视用户要求做**瘦插件**（只转发到网关 L2 面；凭据 / 账号池 / 调度**全部留在网关**） | 每宿主 1 份 |
| **只有 MCP** | — | **不做** —— MCP 能力面是 tools/prompts/resources，官方**没有**注册模型的机制；硬做会退化成嵌套 LLM 调用（双倍 token、双倍延迟、用量统计分裂） | — |
| **什么都不支持** | — | 上游 CLI 适配器（**上游**问题，不是下游形态问题） | — |

**判定顺序（两问）**：

1. 这个宿主**能不能填自定义 base URL**？→ 能，就用 **L2**（成本 0）。
2. 不能，那**有没有公开插件 API**？→ 有，才考虑**瘦插件**（且必须"瘦"到只做转发）。

**关键判断：DSH 在第 1 问就通过了。** 所以对它，**插件是零收益的冗余路径**。

## 6. 待用户拍板

| # | 事项 | 为什么需要拍板 |
|---|---|---|
| 1 | **是否接受"一个网关 = 两个 DSH provider 条目"**（OpenAI 面 + Anthropic 面各一条） | 这是 DSH 官方协议的硬约束（§4.4）。接受 → 文档照写；不接受 → 需要评估"是否只暴露一个协议面"这种更大的产品决策 |
| 2 | **`/v1/models` 是否下发非标准元数据字段**（`context_window` / 模态 / 推理档位） | 属于"协议自创"边界问题；收益是让宿主侧少手填一批字段（§4.1）。另需遵守 B4：未取证字段**省略**而非发 `null` |
| 3 | **是否在网关侧做 `developer` / `max_completion_tokens` 归一** | 与"透传优先"、铁律 4 有张力（§4.2）。**倾向不做**：DSH 官方推荐的是客户端侧开关，零风险且同样有效 |
| 4 | **是否做 VS Code 瘦插件** | 需要确认是否真有 VS Code 场景；且需明确"瘦"的边界（凭据与调度必须留在网关） |
| 5 | **本机 HTTP（非 TLS）base URL 是否被 DSH 接受** | 官方文档**未限制 host**，且明确把"**公司网关、自建服务**"列为自定义提供方的目标场景（【一手】逐字："公司网关、自建服务或目录里没有的提供方，可通过 **添加自定义提供方** 配置"）；但**未逐字确认 `http://127.0.0.1` 可用** → 建议**实测一次**再写进文档（本文不把它当既成事实） |
