# 网关能力升级调研 · 总览与落地建议

> 调研日期：2026-09-22
> 调研目标：为网关后续迭代升级提供依据 —— ① 平台账号授权接入与内部模型转接；② 同模型多厂商参数标准归一化；③ API 之外引入 CLI 对接模式与模型清单下发；④ **核实 DSH 插件的接入形态（是否为"本地 LLM"），并给出网关下游对接形态的专业建议**
> **网关定位（用户补充澄清，是本文多处结论的前提）**：这是一个**公共的中枢网关**，**目标就是服务器电脑上运行的所有 AI 工具**用的 —— 所以它**不是某个编程工具内部的**，而是一个**独立的**、可以**对接融合很多独立模型厂商**、也可以**授权使用一些工具内部的模型数据**，然后经过网关**统一输出标准化服务**。
> 它**接入了两方面的模型使用方式**：**① 各大模型厂商源头的 API 能力直接对接进来；② 通过授权一些工具产品账号登录，使用这些授权账号内部的模型能力**。
> 它**特有的机制是"容错机制 + 模型统一机制"**，以此做到对模型对接的**稳定、高效**。
> → **这段定位直接决定了下游形态：L2（本机常驻服务 + 标准协议端点），而不是 L3（宿主进程内插件）。完整论证见 `09` 号文档 §2.0 / §2.3.1 / §3。**
> 参考项目（**全程只读，零改动**）：`deepseek-harness-codearts`（DSH 插件）、`ZCode`（智谱开源）
> 产出位置：`/Users/w/Desktop/Model-Gateway/docs/research/`

## 一、一页纸结论（先读这个）

### 各任务/问题的最终答案

| # | 任务 | 最终结论 |
|---|---|---|
| 1 | **DSH 插件怎么做到多平台授权接入 + 内部模型转接 + 签到领取** | 它**不是网关**，是 DSH 宿主的进程内 `LlmAdapter` 实现，**不对外暴露 HTTP 端点**。可搬的是"授权接入 + 选号 + 续期"这套**内部机制**，接口形态必须我们自己写。五家平台是**五套互不复用的认证协议**，没有通用抽象可抄。**签到完全没有自动调度**，且**本地不记录"今天领没领"** —— 这两块是我们的设计机会，不是可抄的现成方案。 |
| 2 | **ZCode 的同模型多厂商参数处理机制** | 它**比传闻窄得多**：`model-option-map` 只归一化 **2 个参数**（`reasoningLevel` / `maxOutputTokens`），求值期只接受**一个标量输入**。`temperature` / `topP` / 惩罚项 / `stop` 走**第二条路径**（`ModelRequestSettings` 直通透传），**与我们网关的 `apply_model_params` 完全同级**。真正值得学的是**补丁语义**（RFC 7386 Merge Patch 打在 fetch 拦截器上 → 与协议完全解耦）和**冲突守卫**，不是那套 DSL。**最终建议：不引入 DSL，用 4 个纯数据字段即可覆盖。** |
| 3 | **API 之外要不要做 CLI 模式** | **风险不在"API vs CLI"这个形态，在"凭据来源"。** 合规边界是"谁代表谁 + 凭据存哪 + 是否改二进制"，换 CLI 并不能规避。而客户端（Trae / Cherry Studio）**基本不读 `/v1/models`，要求手填模型 ID** —— 所以"下发模型清单"真正可用的形态是**人可复制的表格**，不是接口。**推荐：`mgw` 本地 CLI 作统一入口（不承载模型流量），CLI 上游适配器降为受限可选、默认关闭。** |
| 4 | **初期接入的 CodeBuddy / WorkBuddy / TRAE 三家，风险各如何** | 三家 ToS 均**明文禁止"非官方客户端 / 自动化程序接入"**，走逆向即条款违规。但**存在合规替代路径**：**CodeBuddy 有完整的官方 API Key + SDK + HTTP API**（入口 `copilot.tencent.com/profile/`）→ 改走官方即可把风险降到接近零；**TRAE 的等价路径是改用火山方舟**按量计费；**只有 WorkBuddy 是"必须走逆向、无合规替代"** 的一家，而它风控条款写得最细（ToS §3.5 明文保留检测规避措施 + 识别未授权程序 + 上报账号）。**建议：CodeBuddy 直接走官方 API，别做逆向。** |
| 5 | **后续接入的智谱（ZCode / BigModel / Z.ai），通路怎么走** | **有官方合规通路，但形态是"标准按量计费 API Key"，不是"Coding Plan 订阅"。** 智谱对"用官方 API Key 自由集成"**明确欢迎**——《用户协议》三.7(7) **明文豁免**"集成至您自有产品、应用或功能中"（禁止的只是"向第三方提供"）；但 **Coding Plan 被《订阅及自动续费协议》六.2 逐词点名禁止**："不得用于…通用 API 接入或其他场景，包括但不限于在**自建应用**…中直接调用"，国际版更点名 `SDK-based access` 与 `proxy`。**罚则是四家中最重**：**5 倍违约金 + 余额不退**，且"**中转**"被官方列为**永久封禁**事由。**结论：走标准 API Key（`open.bigmodel.cn/api/paas/v4`），不碰 Coding Plan，更不要用 `zhipu-account` 账号凭据逆向 `zcode.z.ai`。详见 `06` 号文档。** |
| 6 | **DSH 插件是不是"本地 LLM"形态？我们是否要跟进这种模式？** | **用户的判断成立，需分层精确。** 它确实既非 API 也非 CLI，是**第三形态**，且是**最靠内**的一种。把"本地"拆成三层可把问题说清：**L1 本地权重推理**（权重在本机）· **L2 本机端点服务**（服务进程在本机，**边界是网络**）· **L3 宿主进程内注册**（代码与宿主**同进程**，**没有边界**）。**DSH 插件落在 L3**（`ctx.llm.registerAdapter()`，推理走 `AsyncIterable<StreamChunk>` 进程内函数调用，零序列化零 socket）；**模型推理仍在远端厂商，本地不加载任何权重**。**而 Model-Gateway 落在 L2 —— 这正是它的定位**（服务器常驻、服务全机所有 AI 工具、不属于任何单个编程工具；业界同类是 **Ollama 的 `/v1` 面**）。**L3 与我们的定位互斥**：插件代码必须住进某个具体宿主 = 网关开始依附某个工具。**专业建议：不写宿主插件；主路径是把已有的 OpenAI 兼容面打磨到零摩擦；该借鉴的是插件沉淀的四类机制（提供方身份+模型目录 / 适配器吸收厂商差异 / 凭据与索引分离 / 一 provider 一协议），而不是 L3 这个形态。** 详见 `09` 号文档（形态辨析 + 借鉴清单）与 `08` 号文档 §4（怎么对接最高效最稳定）。 |
| **7** | **定位里的"授权工具账号登录使用其内部模型能力"（通路②）能不能做？** | **能，但必须以"官方授权形态"做，不能以"逆向形态"做。** 通路②有两种实现，**合规性完全相反**：**②-a 官方授权形态**（用你自己账号在**官方**申请的 API Key / SDK / OAuth 调官方开放接口）→ ✅ **合规，厂商明确欢迎**；**②-b 逆向形态**（提取工具客户端内部凭据、冒充官方客户端）→ 🔴 **违规**（三家 ToS 明文禁止）。**初期平台判定**：**CodeBuddy ✅ 有 ②-a**（官方 API Key + Agent SDK，入口 `copilot.tencent.com/profile/`）；**TRAE ✅ 有等价物**（火山方舟）；**WorkBuddy ❌ 两者皆无 → 通路②暂不可行，需你拍板**；**智谱 ✅ 有 ②-a**（标准 API Key）。**所以通路②没有落空 —— 它只以 ②-a 形态成立。** ⚠️ **同时必须注意**：`05` 号文档禁止在 **②-b** 场景做"多账号轮转 / 冷却避让 / 自动签到 / 聚合式重试编排"——**这不否定网关的容错机制，而是要求它按上游形态分层**（①与②-a 完整可用，②-b 不进调度池）。**详见 §六·零（含架构含义：`resources[]` 需加 `upstream_form` 标记）。** |

> **⚠️ 第 6 行的决定性论证是"定位"，不是"性能"**：用户的定位陈述（见文首）**直接决定**形态 —— **L2（本机常驻服务 + 标准协议端点）就是定位本身**，而 **L3 插件形态要求代码住进某个具体宿主，与"不属于任何单个工具"直接互斥**。所以"要不要写插件"**不是性能取舍，是定位一致性问题**。
>
> **更根本的一条：网关的"特有机制"在 L3 下会被破坏，不只是"变慢"。** 用户点明的特有机制 = **容错机制 + 模型统一机制**。冷却状态、切换续跑状态、用量统计、**跨厂商模型名映射表** —— 这些**都是有状态的中枢能力，只能有一份**。放进 N 个宿主插件 = N 份无共享副本 → **"容错"退化成"每个工具各自容错"，"统一"退化成"各宿主各有一套映射"**。**有状态的东西天然属于中枢，不属于边缘。**
> （**适用边界**：本条**只否决"胖插件"**；"瘦插件"靠成本/版本漂移/同进程崩溃三条否决 —— 见 `09` §2.3.1 的自我修正段。）
>
> **性能论证是佐证，不是依据** —— 它的价值在于说明：**即便抛开定位，L3 也不占优**（原生插件的效率优势是"省掉本机 loopback 的 TCP + JSON 序列化"，**亚毫秒级**；而网关端到端延迟由**上游厂商 API 主导**，**几百毫秒～数秒** —— 相差 2～3 个数量级，为省这点开销牺牲可移植性、进程隔离与版本稳定性不划算）。"最高效"（插件）与"最稳定"（API）**不是同一个答案**，对网关这种"长期服务多客户端"的定位，**稳定性权重必须高于那点延迟**。

> **🔴 一条必须提前说清的实测事实（会改变优先级判断）**：解析本机实跑日志 `data/gateway.log`（33,380 行，截至 **2026-09-20**）得到 —— **`/v1/models` 被调用 0 次、`/v1/chat/completions` 仅 2 次、`/v1/messages` 与 `/v1/images/generations` 各 0 次**；而管理面 `/admin/api/*` 被调用 **32,735 次**（其中 `/admin/api/status` 单点 32,583 次）。
>
> **也就是说：网关目前几乎只被它自己的管理界面使用 —— 还没有任何外部 AI 工具真正接进来。**
>
> **推论（本次调研最重要的行动结论）**：
> 1. 所谓"下游对接形态"之争**目前在实践中完全未被检验** —— 因为**还没有下游客户端**。所以**不要再继续论证形态**，而要**把第一个客户端端到端接通**（建议选 **DSH**，因为它**零适配成本**：填 base URL 即通）。
> 2. 因此 **B3（`/v1/models` 元数据）与 B6（`developer`/`max_completion_tokens`）都不是"当前用户痛点"，而是"接入后才会暴露的准备项"** —— 优先级按此调整，**不必紧急修复**，但接入前应把文档准备好。
> 3. 详细统计与三条实证结论见 `09` §2.4。

## 三、任务一：DSH 插件的授权接入与模型转接（核心结论）

### 3.1 最重要的认知纠偏

**它不是网关。** 对外**不暴露任何 OpenAI 兼容 HTTP 端点**，唯一 HTTP 端点是 Jet Hub 管理面（`src/jet-hub-rpc.ts:95`）。它实现的是 DSH 宿主的 `LlmAdapter` 契约（`src/llm-adapter.ts:1`），由宿主**进程内调用**。

→ **可直接搬的是"授权接入 + 选号 + 续期"内部机制；对外接口形态必须我们自己写。** 好消息是它有现成的 `src/openai-compat.ts`（554 行）可以参考。

### 3.2 五套认证协议彼此独立，没有通用抽象

| 平台 | 登录流程类型 | 关键证据 |
|---|---|---|
| `codearts` | 本地回调 + **PKCE + DPoP** | `src/login.ts:393` |
| `buddy` / `workbuddy` | **external-link 轮询** | `src/buddy-oauth.ts:137,178,231` |
| `lobsterai` | 本地回调 + `authCode` 换 token | `src/lobsterai-oauth.ts:232,130` |
| `qoder` | **设备码轮询**（不起监听端口） | `src/qoder-oauth.ts:119,205` |
| `trae` | 本地回调直传 token + `ExchangeToken` | `src/trae-oauth.ts:99,273,365,583` |

**`src/oauth.ts` 并非通用抽象** —— 它是 CodeArts 专用（`CLIENT_ID='codearts-agent'`、`STS_TOKEN_ENDPOINT='sts.cn-north-4.myhuaweicloud.com/...'`，见 `src/oauth.ts:6,8,10`）。

**真正可复用的只有四件**：`RefreshScheduler`（`src/refresh.ts`）、`AccountPool`（`src/account-pool.ts`）、产品配置对象（`xxx-product.ts`）、SSE 工具集（`src/sse.ts`）。

### 3.3 三条最值得借鉴的设计

**① 凭据与账号索引分离（可搬）**

- 凭据本体存 `ctx.credentials`（加密），账号索引 / 黑名单 / 顺序存 `ctx.settings` 的 `jet-hub` namespace，靠 `credentialRef` 字符串关联（`src/account-pool.ts:19,114-115,313-317`）
- **对我们的映射**：网关的 `resources[]` 已把 Key 放在 `api_key` 字段（明文配置，符合铁律 1）。若要支持 OAuth 类凭据，建议**同样拆两张表**：账号索引（明文，可展示/排序/黑名单）+ 凭据本体（明文或独立文件），用 `credential_ref` 关联 —— 与现有扁平资源模型（资源 = 厂商 + 账号 + Key）兼容。

**② 两步式登录（必须照做）**

先返回 `loginUrl` → 先写占位账号条目 → 后台回填 → 失败删除占位（`src/jet-hub-rpc.ts:636-646,665,648-659,660-664`）。**这是浏览器 transient activation 的硬约束**，不是设计偏好：授权 URL 必须在用户点击的同步调用栈内返回。

**③ 失效判定用结构化特征而非 `instanceof`（可搬）**

`src/refresh.ts:14-25` 用 `error.name` + 正则判定，原因注释在 `:16-20`（跨模块同名类 identity 不同）。**对我们的映射**：网关 `core/errors.py` 已有错误分类器，但判定应坚持"结构化码优先 + 文本兜底"，不要依赖异常类型。

### 3.4 一个必须警惕的坑：账号池**没有租约机制**

`src/account-pool.ts:532-592` 全文**无 in-flight 标记/互斥**，只有 `enabled` 过滤（`:538`）、模型级限流过滤（`:540-546`）、`excludeAccountIds`（`:539`）。

→ **并发请求下同一账号可能被重复选中。** 我们的网关是**高并发**场景（DSH 插件是单宿主进程内调用，压力模型不同），**不能照搬** —— 必须自建占用/释放（租约）机制。

## 四、任务二：ZCode 参数机制（核心结论）

### 4.1 认知纠偏：它比传闻窄得多

| 传闻 | 实际 |
|---|---|
| "一套完整的模型参数处理机制" | `model-option-map` 只归一化 **2 个参数**：`reasoningLevel` / `maxOutputTokens`（`types.ts:9`） |
| "参数上下文丰富" | 求值期**只允许一个标量输入**（`types.ts:8` `RestrictedCelValue = string \| number`）；**无上下文对象**（无 `model.id` / `provider.name` / `api.type`） |
| "所有厂商差异都归一化" | 差异靠 **478 条配置规则穷举**补偿，不是通用推导 |

**关键补充（原草稿漏掉、核验后补上）**：ZCode 的参数处理是**双轨制** ——
- **归一化轨**：`option map` 只管 2 个参数
- **直通透传轨**：`temperature` / `topP` / `topK` / 惩罚项 / `stopSequences` / `seed` 走 `ModelRequestSettings`（`contracts/src/model/index.ts:625-631`）→ `runner-options.ts:73-79` **逐字段直通**，**不做任何厂商方言归一化**

→ **这一条反转了"我们差距很大"的论证**：在 `temperature` 这类参数上，ZCode 与我们网关的 `apply_model_params`（`ir.py:58-70`，`body[k]=v` 式注入）**完全同级**。真正有差距的只有 **reasoning / maxOutputTokens 这两个参数**。

### 4.2 最值得学的两点

**① 补丁语义（强烈建议借鉴）**

求值结果被当作 **RFC 7386 JSON Merge Patch** 打在出站请求体上（`merge-patch.ts:63-78`：`null`→删除 / object→递归 / 其余→整体替换），注入点在 **fetch 拦截器**（`model-option-map-fetch.ts:23`）。

**为什么这个设计好**：注入点与 SDK / 协议**完全解耦** —— openai-responses、anthropic、openai-compatible **三条协议分支共用一个 patch 点**（`model-execution.ts:286,296,307`）。我们的网关有 `adapters/openai_out.py` 一个真实适配器 + 两个空占位，未来要接 Anthropic / Gemini 协议，**这套"出站前统一打补丁"的位置选择值得直接照搬**。

**② 冲突守卫（治我们 B1 缺陷的药）**

多个补丁写重叠路径时**抛错而非静默覆盖**（`merge-patch.ts:22-27`，`ownedPaths` + `pathsOverlap` 前缀判定在 `:51-57`）。

→ 这正是我们 `apply_model_params` 与 `inject_reasoning_into_body` 各写各的字段、互不知情（**B1**）所缺的机制。

### 4.3 最终建议：**不引入 DSL**

原草稿的建议依据（"119 条 map 只用 3 种语义，引入 DSL 是过度设计"）**被核验证伪** —— 实测 5 条 map 用到了 `||` / `&&` / `!=` / 链式三元 / `false` 字面量（如 `zcode-builtin.json:2514`、`:2528`），且归类漏了**布尔谓词语义**。

**但修正后的结论方向不变**：不是"3 个字段够用"，而是 **4 个纯数据字段够用**：

| 字段 | 覆盖的语义 | 例 |
|---|---|---|
| `dialect` | 厂商方言（决定字段名与结构） | `anthropic-thinking` / `openai-reasoning-effort` / `qwen-enable-thinking` |
| `effort_words` | 档位词表翻译（含链式多入口） | `disabled→none`、`enabled→high`、其余透传 |
| `boolean_fields` | **布尔谓词**（档位 ∈ 集合 → true/false） | `enable_thinking: reasoningLevel == "enabled"` |
| `max_tokens_field` | 输出上限字段名 | `max_tokens` / `max_completion_tokens` / `max_output_tokens` |

→ **代价从"多写一门语言"降为"多写一个字段"。** 用声明式规则表（YAML/dict）即可，不需要 parser / tokenizer / compiler / evaluator。

### 4.4 其他值得借鉴的机制

- **优先级 = 数组顺序**（`schema.ts:80-106`，model → model-api → provider-site → template-model → provider-model），**overlay 三态语义**（`config-overlay.ts:21-38`：`undefined`=继承 / `null`=重置 / 有值=覆盖）
- **用户可编辑叶子白名单**（`manual-model-config.ts:24-26`）：`reasoningLevel` 整个可改（含 values + map），`maxOutputTokens` 只可改 `max`
- **缺"站点/协议"维度**：ZCode 用 **52 条 `providerSiteRules`**（覆盖 12 个站点）证明"同一模型在不同站点参数不同"是真实需求 → **我们目前只有模型级 `params`，缺这一维**

### 4.5 风险提示

- **`model-option-map` 零测试**（全库仅 4 个测试文件，均与该包无关）→ 借鉴其**设计思想**可以，**不要照搬其边界行为**（DSL 的边界语义无测试保障）
- **许可证是 Apache-2.0**（非草稿误写的 MIT）→ 移植需保留 `LICENSE` 与 `NOTICE`/版权声明（Apache-2.0 §4）

## 五、任务三：API 模式 vs CLI 模式（核心结论）

### 5.1 风险不在形态，在凭据来源

> **适用范围说明（2026-09-22 补充）**：Q1 已确认，初期接入的是**腾讯 CodeBuddy、腾讯 WorkBuddy（国际版）、字节 TRAE** 三家 —— **不是 Anthropic**。因此下面这段 Anthropic 官方原文的作用是**提供一个"官方是如何划边界"的分析范式**（它把问题从"API vs CLI"重新定义成"谁代表谁 + 凭据存哪 + 是否改二进制"），而**三家平台各自的具体条款命中与风险分级，请看 `05-初期接入平台可行性与风险评估.md`**。两者的结论方向一致：**换形态不能规避，只有换凭据来源（走官方 API）才能。**

这是本次调研**最重要的一个结论**，也是最容易被误判的一点。

**Anthropic 官方原文**（`code.claude.com/docs/en/legal-and-compliance`）：
- ❌ 禁止：**第三方开发者**在自己应用里提供 Claude.ai 登录、**代表用户路由订阅凭据**、网关**存储/中转**会话 token
- ✅ **明文不禁止**："Nor does it prevent an **end user from signing in to the unmodified Claude Code binary with their own Claude subscription**"

→ **合规与否取决于三个问题：谁代表谁 + 凭据存哪 + 是否改二进制。不是 API vs CLI。**

**CLI 模式规避的是"网关存储/中转订阅凭据"这一点，并不规避"把订阅凭据喂给非官方客户端"。** 官方脚本化推荐的 `--bare` 模式明确**不读 OAuth**、要求用 `ANTHROPIC_API_KEY`（`code.claude.com/docs/en/headless`）—— 也就是说，**官方认可的 CLI 路径恰恰是回到 API Key**。

**同理，账号风控维度存在来源冲突**：官方二进制身份校验可通过（`awesomeagents.ai`），但**非交互 / 自动化 / 高频**画像本身就是风控信号（`woodchen.ink` 报告 §6.4：`is_ci: true` / `is_interactive: false` / `entrypoint: "sdk"` → 自动化滥用嫌疑）。而网关正是**无人值守、非交互、高并发**的调用方。**两个来源方向相反，无法判定孰强 → 标注为未验证。**

### 5.2 客户端基本不读 `/v1/models`

| 客户端 | 官方口径 |
|---|---|
| **Trae** | 社区教程反复强调"模型ID！！！！！无数的人都挂在ID上，**请自己去查询**"（**注：作者是社区用户，非 Trae 官方**） |
| **Cherry Studio** | 官方文档：「点击"+ 添加"按钮，**手动添加**此提供商下您想要使用的模型ID」；页面**无任何"自动获取模型列表"功能** |
| **Claude Code** | **支持**读网关 `/v1/models`，但需显式开启 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`（**默认关闭**），且受 `availableModels` 白名单过滤 |

→ **"把模型清单下发给软件"的真正可用形态是「人可复制的表格」，不是接口。** 接口仍应补齐（Claude Code 这类支持发现的客户端会用），但不能指望它解决"用户在 Trae 里手动输入模型 ID"的体验问题。

### 5.3 推荐方案

| 方案 | 内容 | 评价 |
|---|---|---|
| **主方案（推荐）** | **`mgw` 本地 CLI 作统一入口**：`mgw setup <trae\|cursor\|cherry\|claude-code\|codex>` 打印该工具的接入配置片段、`mgw models` 打印可复制的模型表格、`mgw status` 查看网关状态。**CLI 不承载模型流量**，工具继续走现有 OpenAI 兼容 `base_url` | ✅ **零客户端改造、零新增故障面**；"最直接最稳定最短路径"的达成方式是**不新增中间层** |
| **可选方案（受限，默认关闭）** | `adapters/cli_out.py` 调用厂商 CLI headless 模式作为**上游** | ⚠️ **合规前置 + 默认关闭**；且凭据必须走环境变量 API Key（若走厂商 CLI 自持凭据 → 与铁律 1 冲突） |

> **诚实说明**：CLI 上游方案**并不比 API 模式更稳定** —— 它同样面对协议易变、风控、额度耗尽。它唯一的真实价值是"覆盖那些**不提供公开 API** 的平台"。

### 六·零 — **先裁决：通路②的合规形态，以及容错机制的作用域**（影响 P2-1 与全部容错设计）

> **本节是对一次独立审计发现的偏离的纠正。** 审计指出：`05` / `06` 号文档的结论**实质上否决了"逆向工具账号"这条路**，但本文此前把"授权工具账号登录"标为"待建"并引用 `05`/`06` 为据 —— **引用方向与它们自己的结论相反**；且**"容错机制"被当成可以无差别套用到两条上游通路上**，而 `05` 明确禁止在账号授权场景做轮转/冷却。**这两点必须先在定位层面裁决，否则 P2-1 与容错设计都会错。**

#### 六·零·1 通路②有两种形态，必须分开说

用户定位里的"**通过授权一些工具产品账号登录，来使用这些授权账号内部的模型能力**"，在实现上有**两种形态**，合规性完全相反：

| 形态 | 做法 | 凭据来源 | 合规性 | 代表 |
|---|---|---|---|---|
| **②-a 官方授权形态** | 用**你自己账号**在**官方**申请的 API Key / SDK / OAuth 授权，调用**官方开放的接口** | **官方签发** | ✅ **合规** —— 这是厂商明确欢迎的用法（`06` 号文档：智谱《用户协议》三.7(7) 明文豁免"集成至您自有产品"） | **CodeBuddy 官方 API Key + Agent SDK**（入口 `copilot.tencent.com/profile/`）；智谱标准 API Key |
| **②-b 逆向形态** | 提取工具客户端**内部的登录凭据**（cookie / token），**冒充官方客户端**调用其内部端点 | **逆向取得** | 🔴 **违规** —— 三家 ToS 均明文禁止（CodeBuddy §8.2、TRAE §5.2、WorkBuddy AUP §4） | DSH 插件的做法（`01` 号文档）；`codebuddy2api` 类项目 |

#### 六·零·2 裁决结论

1. **通路②在合规意义上依然成立 —— 但只以 ②-a 形态成立。** ②-b 形态（逆向）在初期三家平台上**全部不可行**（`05` 号文档逐条命中）。
2. **所以 `09` §2.0 表里"上游通路 B ⏳ 待建 —— 借鉴 01/05/06"的写法要改**：`01` 是**逆向形态的机制参考**（可读、不可照搬）；`05`/`06` 的结论是**"不要走逆向"**，不是"支持建通路②"。**引用方向必须纠正。**
3. **三家初期平台的通路②判定**：

| 平台 | ②-a 官方形态 | ②-b 逆向形态 | 结论 |
|---|---|---|---|
| **CodeBuddy（腾讯）** | ✅ **有**（官方 API Key + Agent SDK + HTTP API） | 🔴 禁止 | **走 ②-a。等于"用你账号的官方额度"，与定位的通路②完全一致** |
| **TRAE（字节）** | ✅ **有等价物**（改用**火山方舟**按量计费） | 🔴 禁止（且设备级风控与"共享账号"结构性冲突，见 `05` §3.3.3） | **走 ②-a 等价物** |
| **WorkBuddy（腾讯国际版）** | ❌ **未找到** | 🔴 禁止（且风控条款最细：ToS §3.5 明文保留"检测规避措施 + 识别未授权程序 + 上报账号"） | **通路②暂不可行 —— 只能等官方通路，或不做** |
| **智谱（BigModel / Z.ai）** | ✅ **有**（标准按量计费 API Key，`open.bigmodel.cn/api/paas/v4`） | 🔴 禁止（Coding Plan 被逐词点名禁止；"中转"列为永久封禁事由） | **走 ②-a（标准 API Key），不碰 Coding Plan** |

4. **对定位的一句话回应**：**你的通路②没有落空** —— 只是它在初期三家平台上**必须以"官方授权形态"实现**，而不是以"逆向工具账号"实现。**唯一例外是 WorkBuddy**（无官方等价通路）—— 这一条需要你拍板"等官方通路 / 换平台 / 不做"。

#### 六·零·3 容错机制必须按上游通路分层（重要，影响架构）

`05` 号文档的合规结论里有两条**直接限制了容错机制的作用域**：

- `05` §P1-2（`:741`）：**不做"多账号自动轮转 / 冷却 / 积分耗尽避让"** —— 属"独立于网关接入的违规行为，且属加重情节"。
- `05` §P1-6（`:745`）：**限速 + 限制并发 + 不做聚合式重试编排** —— WorkBuddy AUP §3.5 明文禁止"Chain or orchestrate multiple Service calls in loops or recursions"。

**但网关的核心资产恰恰是容错机制（重试 / 冷却 / 切换续跑 / 并发控制）。** 两者不矛盾，前提是**分层**：

| 上游通路 | 容错机制 | 理由 |
|---|---|---|
| **① 厂商源头 API**（你自己的付费 Key） | ✅ **完整可用** —— 重试、连续失败冷却、切换续跑、并发上限、配额退避**全都做** | 这是**你自己的额度**，没有"规避平台风控"的问题；`05` 的限制针对的是**账号共享与规避检测**，不是 API 调用本身 |
| **②-a 官方授权形态**（你账号的官方 API 额度） | ✅ **可用**，但受**官方配额/速率条款**约束（按官方限速设并发，不做规避式绕行） | 合规前提是"遵守官方速率限制"，而非"不做重试" |
| **②-b 逆向形态** | 🔴 **一律不做** —— 多账号轮转、冷却避让、积分耗尽避让、自动签到、聚合式重试编排**全部禁止** | `05` §P1-2 / §P1-4 / §P1-6；属加重情节 |

> **架构含义**：资源（`resources[]`）需要新增一个**能力标记**，例如 `upstream_form: official-api | official-sdk | reverse`，
> 容错策略按该标记分派 —— **逆向形态的资源根本不进调度池**（而不是"进了池子但配保守参数"）。
> 这样"容错机制"仍是中枢唯一实现（符合 `09` §2.3.1），但**它的作用域被合规边界约束住了**。
