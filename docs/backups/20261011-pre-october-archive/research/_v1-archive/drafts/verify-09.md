## 4. 自对抗复核（主动构造对自身论证的最强反驳）

> 因为缺少独立核验员，主 agent 主动扮演反方，对**新提出的两条核心论证**做最强反驳。

### 4.1 对 §2.3.1「有状态机制必须在中枢」的反驳

**反驳**：这个论证不成立 —— 如果做的是"**瘦插件**"（插件只把请求转发给网关的 HTTP API），状态**仍然全在网关**，根本不会出现"N 份无共享副本"。所以这条论证**推不出"不能做 L3"**。

**裁决：反驳成立，原表述过度推论。** 该论证**只能否决"胖插件"**（把凭据/账号池/调度搬进宿主），**不能否决"瘦插件"**。

**已修正**：`09 §2.3.1` 增加「本条论证的适用边界（自我修正，避免过度推论）」段落，明确：
- §2.3.1 否决 **胖插件**；
- §3.2~§3.4（成本 O(N) / 版本漂移 / 同进程崩溃）否决 **瘦插件**；
- **两者合起来才是"不做 L3"的完整理由。**

### 4.2 对 §0.2「三层本地」框架的反驳

**反驳**：这个框架**混了两个维度** —— L1 按"权重在哪"分类，L2/L3 按"边界在哪"分类；且它**既不互斥也不穷尽**（例如云端聚合服务在"边界"上属 L2 却不在本机）。当成形式化分类学是站不住的。

**裁决：反驳成立，框架需加限定。** 但**不影响结论** —— 本文用这个框架的目的是**解释"本地 LLM"这句自然语言在现实中指哪几件事**，不是构建分类学。

**已修正**：`09 §0.2` 增加「框架的构造说明与已知边界」四条：
1. 主判据是**边界形态**，权重位置是**辅助属性**；
2. **不是互斥穷尽**，明确举出"云端聚合服务"落在表外；
3. **L1 与 L2 常同时存在**（Ollama 一个进程两个面）—— 层是"接入面的性质"，不是"产品的性质"；
4. 用法纪律：说"本地 LLM"**必须指明是哪一层**。

### 4.3 对 §0.3「用户判断成立」的反驳

**反驳**：用户说的"本地 LLM 形式"如果按业界主流读法（L1/L2）理解，就**是错的**；把它判为"成立"是在迁就用户。

**裁决：反驳不成立，但原表述需给足理由。** 理由：用户并列提出了三个判断（"不是 API""不是 CLI""像是本地 LLM"）。**前两个已证实**，第三个是"在排除前两者后，识别出这是一个嵌在宿主里的第三形态" —— 这个**识别动作本身是正确的**（该形态确实存在且确实是第三形态）。分歧只在**术语**，不在**观察**。
> 而 `07 §0.2` 初稿写"方向对、措辞错"，把**一个术语分歧**放大成对用户判断的否定，且**因此没有回答"那如果是，我们该借鉴什么"** —— 这才是用户说"跑偏"的实际内容。
>
> **已修正**：`07 §0.2` 改为"✅ 成立，需分层精确"，并加"本节初稿曾写作'方向对、措辞错'，这是学究式抬杠"的自我修正说明。
