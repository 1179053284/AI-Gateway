## 3. 主 agent 逐条核实（**不盲信审计结论**）

### 3.1 审计发现 1 —— 【严重】通路②被静默替换 → **核实：成立**

**核实过程**：打开 `09` §2.0 表与 `05` §P1-2/P1-4/P1-6、`06` 的结论段。

| 审计断言 | 核实结果 |
|---|---|
| `09` §2.0 标通路 B 为"⏳ **待建** —— 借鉴 DSH 插件的授权接入（`01` / `05` / `06` 号文档）" | ✅ **原文属实** |
| `05` 的结论是"不要走逆向、改走官方 API" | ✅ **属实** —— `05` §P2-1（`:267`）逐字："**唯一能消除条款风险的路径是走官方 API**" |
| 因此 `09` 引用 `05`/`06` **方向相反** | ✅ **成立** —— `05`/`06` 不支持建通路②，`09` 却把它们列为通路②的依据 |

**裁决：审计成立。** 这是**真实的引用方向错误**，且掩盖了一个定位层面的问题（用户的通路②是否落空？）。

**但审计漏了一点（主 agent 补充）**：通路②**并非落空**，而是有**两种形态**：
- **②-a 官方授权形态**（用你自己账号在**官方**申请的 API Key / SDK）→ ✅ **合规**，且这正是用户定位里想要的东西
- **②-b 逆向形态**（提取工具客户端内部凭据）→ 🔴 违规

**CodeBuddy 的官方 API Key + Agent SDK 正是 ②-a** —— 也就是说**通路②在 CodeBuddy 上是可行的，只是要走官方形态**。审计把它简化成"通路②被否掉了"，**这一步过度**。

### 3.2 审计发现 2 —— 【严重】P3 与合规约束冲突未披露 → **核实：成立**

**核实过程**：用 Grep 逐条查 `05` 的原文。

| 审计引用的 `05` 条款 | 实际原文（逐字核实） |
