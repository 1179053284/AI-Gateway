# 初期接入平台可行性与风险评估

> 调研日期：2026-09-22
> 调研对象：腾讯 CodeBuddy（中国版 `copilot.tencent.com`）、腾讯 WorkBuddy（国际版 `www.workbuddy.ai`）、字节 TRAE（`trae.cn` / `trae.ai`）
> 调研问题：把三家平台的**订阅账号凭据**接入自建本地网关（复用官方客户端与后端的**逆向私有接口**），在**服务条款**与**风控实践**两个层面各自的风险有多大？是否存在**官方 API 的合规替代路径**？
> 取证方式：WebSearch + WebFetch，优先官方来源（官方协议页 / 官方文档 / 官方定价页）
> 证据标注约定：
> - **【一手】** = 平台官方发布的协议页、官方文档、官方定价页、官方公告
> - **【二手】** = 社区论坛、GitHub Issue、媒体报道、第三方镜像、第三方教程
> - **【推断】** = 本文基于已有证据的推理，**无直接来源支撑**，不得当作事实引用
> - **【未找到】** = 检索后未发现公开依据，**不编造**

## 一、结论先行

### 1.1 风险分级汇总表

| 平台 | 合规风险 | 技术风险 | 账号风险 | 是否有官方 API 替代路径 | 一句话判断 |
|---|---|---|---|---|---|
| **腾讯 CodeBuddy（中国版）** | 🔴 **高** | 🟡 中 | 🟠 中高 | ✅ **有，且完整**（官方 API Key + Agent SDK + HTTP API） | **条款明文禁止，但存在官方许可的等价路径，改走官方 API Key 即可把合规风险降到接近零** |
| **腾讯 WorkBuddy（国际版）** | 🔴 **高** | 🔴 **高** | 🔴 **高** | ⚠️ **部分**（腾讯云 TokenHub / Token Plan 提供官方模型 API，但 WorkBuddy 自身未找到面向个人的模型推理 API） | **三家中最危险的一家：协议明文写了"检测规避措施 / 识别未授权程序"，且已有公开的多账号风控实例** |
| **字节 TRAE** | 🔴 **高**（中国版）<br>🟡 中（国际版，**待核验**） | 🔴 **高** | 🟠 中高 | ❌ **TRAE 自身无**<br>✅ **有（火山方舟按量计费 API）** | **条款明文禁止"自动化程序接入"，且已实施"2 设备上限 + 24h 风控"的硬性设备约束，与网关形态直接冲突** |

> **风险分级口径**（本节为本文自定口径，非平台官方口径）：
> - **合规风险** = 是否被服务条款**明文**禁止（有原文条款直接命中 = 高；只能靠兜底条款覆盖 = 中；未覆盖 = 低）
> - **技术风险** = 私有接口的稳定性 + 平台是否有**客户端完整性校验/设备指纹/行为遥测**（官方条款明示有检测能力 = 高）
> - **账号风险** = 是否有**公开可查的**封号/风控实例 + 官方处置权限的明确程度

### 1.2 一句话总判断

**三家平台的服务条款都**（至少中国版/国际版其中之一）**明文禁止了"用非官方客户端或自动化程序接入订阅账号"，因此"逆向私有接口 + 伪装 UA 做网关"这条路在三家身上都属于条款违规；但 CodeBuddy 恰好提供了官方 API Key + 官方 SDK 的等价通路，TRAE 的等价通路是改用火山方舟按量计费 API，只有 WorkBuddy 国际版（`workbuddy.ai`）目前**未找到**面向个人用户的官方模型推理 API——也就是说，**只有 WorkBuddy 这一家是"必须走逆向、没有合规替代"的**，而它偏偏又是风控条款写得最细、且已有公开风控实例的一家。**

### 1.3 最关键的一个发现（单列）

> **CodeBuddy 中国版的官方 API Key 入口，与 DSH 插件逆向使用的 endpoint 是同一个域名。**

| 项目 | 值 | 来源 |
|---|---|---|
| DSH 插件中 `CODEBUDDY` 产品的 endpoint | `https://copilot.tencent.com` | 本项目代码事实（用户提供，已核实） |
| CodeBuddy 中国版**官方 API Key 获取入口** | `https://copilot.tencent.com/profile/` | **【一手】** [CodeBuddy Agent SDK 文档](https://www.codebuddy.cn/docs/cli/sdk) / [身份和访问管理文档](https://www.codebuddy.ai/docs/zh/cli/iam) |

官方 SDK 文档原文（**【一手】**）：

> 「如果你已经在终端中通过 `codebuddy` 命令完成了交互式登录，SDK 会自动使用该认证信息，无需额外配置。」
>
> 「获取 API Key：… 中国版 `https://copilot.tencent.com/profile/`」

**这意味着**：对于 CodeBuddy，"让订阅账号的模型能力被本地工具调用"这件事，存在一条**官方文档明确支持**的实现方式——**官方 API Key 认证**，或用官方 `@tencent-ai/agent-sdk`（TypeScript）/ `codebuddy-agent-sdk`（Python），或用官方 HTTP API（`codebuddy --serve --port 8080`，暴露 `/api/v1/*` REST 与 `/api/v1/acp` 有状态流式协议）。

**【推断】** 该官方 API Key 很可能复用同一订阅账号与积分体系（因为 Key 入口就在用户 profile 页，且 SDK 明确"可自动复用交互式登录的认证信息"）——但**本文未找到"API Key 是否消耗同一订阅积分"的官方明文说明**，此点列为待核验事项（见第六章第 8 条）。**若该推断成立**，则对 CodeBuddy 而言，把网关的上游适配从"逆向 `/v2/plugin/*` + 伪装 `CodeBuddyIDE/1.106.1` UA"切换为"官方 API Key + 官方 HTTP API"，可以在几乎不损失功能的前提下，把第 3.1 节列出的全部条款命中项一次性消除。

| 产品 id | displayName | endpoint | 定位 |

**逐项对照本项目的接入方式：**

#### （2）直接命中：账号不得提供给他人 —— 《腾讯云账号协议》§2.2.1

**【一手】** 来源：[cloud.tencent.com/document/product/301/91174](https://cloud.tencent.com/document/product/301/91174) §2.2.1

> 「2.2.1 您在腾讯云网站注册的账号是腾讯云为您提供服务的唯一服务标识，依托账号您可以获取相应的腾讯云服务。**腾讯云账号仅限于您自身使用，未经腾讯云同意，您不得将账号以任何方式提供给他人使用，包括但不限于转让、赠与、出租或借用等。**任何私自交易、出让账号的行为，腾讯云均不予认可，您应当自行承担因此而产生的后果和法律责任。」

**对本项目的意义**：如果网关是**纯单用户本机自用**（只有账号持有人本人通过网关调用），则 §2.2.1 的"提供给他人使用"**不构成命中**——账号仍限本人使用，只是换了调用工具。**这是本项目唯一可能不触碰该条款的形态。** 一旦网关被用于多人共用、或代他人中转，该条款立即命中。

#### （3）许可范围：个人、不可转让 —— §2.3 / §7.1

**【一手】** 来源：同上 §2.3、§7.1

> 「2.3 腾讯云授予您一项**个人的、不可转让及非排他性的许可**，以使用本软件。本协议未明示授权的其他一切权利仍由腾讯云保留。」

> 「7.1 本软件及提供的相关服务您需登录已实名认证的腾讯云账号后方可使用。您有责任妥善保管注册账号信息及账号密码的安全，您需要对注册账号以及密码下的行为承担法律责任。**您同意在任何情况下不向他人透露账号及密码信息。**」

> **注**：`codebuddy2api` 类项目的做法是**读取本机 `auth/*.info` 凭据文件**（而非索要密码），**没有**"向他人透露账号密码"的行为。因此 §7.1 的末句**不构成命中**——但凭据被复制到网关进程内、由网关而非官方客户端持有，是否等价于"非授权第三方软件登录"，仍落入 §8.2(6)。

#### （4）对外提供服务会触发额外法定义务 —— §7.4（**易被忽略但很重要**）

**【一手】** 来源：同上 §7.4

> 「7.4 如果您将本软件应用到您的产品、应用、功能中并对外提供服务的，**您作为生成式人工智能服务提供者**，应当遵守《生成式人工智能服务管理暂行办法》《互联网信息服务算法推荐管理规定》《互联网信息服务深度合成管理规定》等适用法律的相关规定，依法履行相关法定义务并承担相关法律责任，包括：
> （1）落实信息安全主体责任，建立健全相关管理制度。…（3）依法对用户进行真实身份信息认证。…（10）设置便捷有效的用户申诉和投诉、举报入口。（11）如提供具有舆论属性或社会动员能力的服务，应按规定开展安全评估并履行算法备案手续。」

**对本项目的意义**：**"个人本地自用单实例"与"对外提供服务"是两条完全不同的合规轨道。** 前者基本不触发 §7.4；后者会把网关运营者变成"生成式人工智能服务提供者"，需要实名认证用户、内容审核、算法备案。**这是本项目最应该主动规避的一条红线。**

> 「8.4 腾讯云有权依合理判断对违反有关法律法规或本协议规定的行为进行处罚，包括**警告、限制功能、删除屏蔽内容、封号、依法追究法律责任**等。因您违反本协议导致的第三方索赔、要求或损失，您应当独立承担责任。」

#### （6）上位协议：账号限制措施 —— 《腾讯云账号协议》§5.2

**【一手】** 来源：[cloud.tencent.com/document/product/301/91174](https://cloud.tencent.com/document/product/301/91174) §5.2

> 「5.2 在下列情况下，腾讯云有权限制或终止向您提供部分或全部产品和服务，同时有权对您的账号采取限制措施，包括**限制账号功能、冻结操作权限、限制登录等，甚至注销账号、永久停止提供服务**（合称"账号限制措施"）：
> …
> **5.2.6 腾讯云发现您的账号存在异常的；**
> 5.2.9 其他必须采取账号限制措施才能避免危害发生和扩大的情形。」

> 「5.3 您注册有多个账号的，腾讯云有权在您存在第5.2条约定的情形时，**对您注册的多个账号统一处理**，采取账号限制措施。」

**关键**：§5.2.6「发现您的账号存在异常」+ §5.3「多账号统一处理」——**这两条组合起来，意味着"多账号池 + 轮转"的风险不是线性的，而是会连带封禁同一主体控制的所有账号。**

**这个案例的信息量极大：**

| 客服列出的触发因素 | 对本项目的直接映射 |
|---|---|
| 环境变量残留 | **【推断】** 暗示存在客户端环境探测；网关若在环境中留下官方客户端的残留标识（或反之），可能被判定异常 |
| 多设备同时在线 | **直接命中"网关 + 官方客户端同时使用"的形态**——网关会被视为额外设备 |
| **请求频率或行为模式异常** | **直接命中"网关聚合多客户端流量"的形态**——Trae / Cursor / Cherry Studio 同时打网关，请求特征与单个官方客户端明显不同 |
| 代理 VPN | 使用代理会显著提高风险 |
| 网络出口 IP 变化 | **网关部署在服务器/VPS 上会导致出口 IP 与官方客户端不一致** |

> **【推断】** 客服未提及"检测到第三方客户端"，而是把原因归为"登录环境异常"与"行为模式异常"。这**不能**解读为"平台不检测第三方客户端"，只能说明**本次触发路径是环境/行为维度的**。结合 ToS §3.5 明文保留的程序指纹检测能力，**行为与设备维度是当前可观测到的主要风控面**。

**对本项目的直接映射（这是 TRAE 最致命的一点）：**

| TRAE 机制 | 对本项目的影响 | 严重度 |
|---|---|---|
| **单账号最多 2 台设备同时登录** | 若网关 + 官方 IDE 同时使用 → 已占 1 个额度；若网关部署在服务器 → 被识别为独立设备；**若用户在 IDE 和网关之外还在手机上用过，直接超限** | 🔴 高 |
| **超出即 24h 风控（全功能锁定）** | 不是"限流"，是**整个账号不可用 24 小时**；提示语伪装成"休息一下"，用户很难定位原因 | 🔴 高 |
| **行为风控：短时间频繁切换** | 网关的多客户端并发请求（Trae + Cursor + Cherry Studio 同时打）**在特征上等价于"频繁切换"** | 🔴 高 |
| **设备限制存在误判**（社区反馈） | 意味着**即使合规使用也可能被误伤**，容错空间小 | 🟠 中高 |
| **无设备管理功能** | 无法查看/踢出已登录设备 → **无法自助排查与恢复** | 🟠 中高 |

> **【推断】** 该机制与"自建网关"存在**结构性冲突**：网关的本质是"让多个客户端共享一个账号"，而 TRAE 的风控设计目标恰恰是"限制单个账号被多少设备使用"。**这不是可以通过限速或降低并发规避的问题，而是设计目标层面的对抗。**

## 五、降低风险的做法建议

> **总原则**：本项目的风险主要**不来自"用 Python 写网关"这件事本身**，而来自四个具体行为：① 用非官方客户端登录；② 逆向私有接口；③ 伪装官方客户端身份；④ 多账号/对外中转。**前三条可以通过改用官方 API 一次性消除，第四条可以通过"只给自己用"消除。**

### 5.1 P0（必做 · 决策前）

| # | 措施 | 理由 | 对应的风险消除 |
|---|---|---|---|
| **P0-1** | **对 CodeBuddy 优先验证官方 API Key 路径**：用 `https://copilot.tencent.com/profile/` 获取 Key，跑通官方 Agent SDK / `codebuddy --serve` HTTP API，评估能否覆盖本地工具（Trae / Cursor / Cherry Studio / Claude Code）的需求 | 官方 API Key 入口与逆向 endpoint **同域**，官方 SDK 明确支持复用登录凭据（**一手**）。若可行，**CodeBuddy 的全部条款命中项可一次性消除** | 消除 §8.2(2)(4)(5)(6) 全部命中 |
| **P0-2** | **把 WorkBuddy（国际版）移出初期接入范围** | 三家唯一"无官方等价替代路径"（**未找到**官方模型 API）+ 条款最细（AUP §4 精确命中）+ 已有公开风控实例（**二手**）+ 黑箱判定 | 消除最高风险项 |
| **P0-3** | **对 TRAE 评估"改用火山方舟 API"的可行性**，而非从 TRAE 提取 | TRAE 有 2 设备硬上限 + 24h 风控，与网关形态**结构性冲突**；火山方舟提供官方按量计费 API（**一手**） | 消除 §5.2/§5.3 命中 + 绕过设备风控 |
| **P0-4** | **明确"绝不对外提供服务"** 并写入网关设计约束 | CodeBuddy §7.4 会把"对外提供服务"的运营者变成**生成式人工智能服务提供者**（需实名认证用户、内容审核、算法备案）；腾讯云服务协议 §5.7(7) 另禁"非法代理服务器" | 避免最高等级的法律合规风险 |

### 5.2 P1（必做 · 若坚持走逆向路径）

| # | 措施 | 理由 |
|---|---|---|
| **P1-1** | **仅单用户本机自用，不做多账号池** | 多账号是 AUP §3.10「Scaled Abuse」的**独立命中项**，且腾讯云账号协议 §5.3 明确"多账号统一处理"——风险非线性放大 |
| **P1-2** | **不做"多账号自动轮转 / 冷却 / 积分耗尽避让"** | 见 §3.2.4：这是**独立于网关接入的违规行为**，且属加重情节 |
| **P1-3** | **不做"绕过内容审核"类功能**（如零宽字符脱敏、审核拦截后重试） | AUP §3.4 明确禁止「bypass, disable, or circumvent any safety filter, content moderation system, or usage restriction」。**这是最容易被平台重点打击的一类行为** |
| **P1-4** | **不做自动签到 / 积分自动领取** | AUP §3.5「automated bots … unless expressly authorised via our API terms」。**注意豁免条件只有"官方 API"** |
| **P1-5** | **不修改客户端二进制、不伪造签名** | WorkBuddy ToS §3.5 明确采集 `software, signatures` 与已知未授权程序名单；伪造签名属技术层面无法成功、条款层面明确禁止的行为 |
| **P1-6** | **限速 + 限制并发 + 不做聚合式重试编排** | WorkBuddy AUP §3.5 明确禁止「Chain or orchestrate multiple Service calls in **loops or recursions**」；TRAE §5.3(14) 禁止"超出速率限制"；TRAE 风控明确将"请求频率或行为模式异常"列为触发因素（**二手**） |
| **P1-7** | **固定出口 IP，不使用代理/VPN** | 腾讯客服明确将「代理 VPN」「网络出口 IP 变化」列为风控触发因素（**二手**） |
| **P1-8** | **避免"网关 + 官方客户端"同时在线的多设备形态** | TRAE 明确"2 台设备上限"；WorkBuddy 客服明确"多设备同时在线"是触发因素 |
| **P1-9** | **移除环境变量残留** | 客服明确列出「环境变量残留」（**二手**）——**【推断】** 建议网关运行环境与官方客户端环境做隔离 |

|---|---|---|
| **P2-1** | **设计"上游随时失效"的降级路径**：把上游适配层做成可插拔，一旦某平台风控/改协议，能在不改下游客户端的情况下切换 | TRAE 已实施 24h 风控；私有接口无兼容性承诺（CodeBuddy §5.3 明确"不保证旧版本软件继续可用"） |

| **P2-5** | **不要在公开渠道（含 GitHub Issue / 论坛）讨论绕过风控的具体方法** | 参考 TRAE 遥测事件的公开案例：研究者公开质疑后，**账号被管理员禁言 7 天**，且平台"迅速将关键词 track 加入自动禁用黑名单"（**二手**） |

### 5.4 关于"仅单用户本机自用"这一形态的准确评估

**需要澄清一个常见误解**：

| 常见误解 | 准确结论 |
|---|---|
| "单用户本机自用就不违规" | ❌ **不准确**。单用户自用能消除的是"账号共享/凭据转让"（CodeBuddy §2.2.1、WorkBuddy AUP §5、TRAE §4.4 的"提供给他人使用"要件），**但无法消除**"非授权第三方软件登录"（CodeBuddy §8.2(6)）、"inter-operate with the Service without permission"（WorkBuddy AUP §4）、"自动化程序接入"（TRAE §5.2）这三条**与用户数量无关**的条款 |
| "不开源、不公开就不被发现" | ❌ **不准确**。WorkBuddy §3.5 明确保留"检测未授权程序 + 上报账号"的能力；TRAE 有设备指纹级遥测；客服回复证明风控在**环境与行为维度**实际生效 |
| "官方 API 只是另一个入口，功能一样" | ✅ **基本准确**（针对 CodeBuddy）。官方 SDK 明确支持复用交互式登录的认证信息，且官方 HTTP API 提供 REST + ACP 两种协议，形态上足以替代逆向的 `/v2/plugin/*` |

> **本文的核心建议**：**单用户本机自用是"降低风险"的必要条件，但不是"消除风险"的充分条件。** 真正能消除条款风险的只有一条路径——**走官方 API**。三家中只有 CodeBuddy 提供完整的官方等价路径（TRAE 的等价路径是改用火山方舟，WorkBuddy 的等价路径是改用腾讯云 TokenHub/Token Plan 并放弃"从 WorkBuddy 提取"这一目标）。
