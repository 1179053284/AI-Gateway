## 0. 结论先行

### 0.1 用户需求 ① 在 DSH 里**已经被实现过，且有血泪注释**——直接抄结论

DSH 的 TRAE 接入是唯一一个**完整实现了「设备身份」**的产品，代码注释里把风控后果写得非常直白：

| 事实 | 证据（DSH 源码） |
|---|---|
| 凭据里必须持久化 **两个**设备标识 | `trae.ts:89-127` `TraeCredential` 含 `machine_id` + `device_id` |
| `machine_id` = 32 位 hex，**不可每次重新生成** | `trae.ts:108-112`：「同一账号用不同的 `machine_id` 可能会触发**风控或要求重新登录**」 |
| `device_id` = 16 位纯数字，**每个账号必须互不相同** | `trae.ts:116-119`：「Go 端 `deviceid.go` 用 `crypto/rand` 生成……**每个账号必须有自己的 device_id**」 |
| **两个账号共用 device_id 的直接后果** | `trae.ts` 头注释：「`device_id` 签到不能共用（**同一天两个账号共用同一 device_id 会被『该设备已签到』拦截**）」 |
| 续期时设备指纹**完全不动** | `trae-auth.ts:10-14`：「续期时只改 token/expiresAt，这两个设备指纹字段**完全不动**」 |
| 请求头要带全套设备描述 | `trae.ts` 头部（`X-Device-Type: 'macos'`、`X-OS-Version`、`X-Device-Brand`、`Request-Traffic-Type`） |
| 登录 URL 要带 9 个设备参数 | `trae-oauth.ts:99-128`：`machine_id`/`device_id`/`x_device_id`/`x_machine_id`/`x_device_brand`/`x_device_type`/`x_os_version`/`x_app_version`/`x_app_type` |

**用户说的「trae 一个设备信息登录多个账号就会提示异常」，与 DSH 注释完全吻合。** 这不是理论风险，是已被代码作者踩过并写进注释的现实。

### 0.2 但 DSH 的设备隔离**做得不完整**——这是我们要补的

**【代码】DSH 只在「生成」时保证互异，没有全局唯一性校验与冲突处理**：`machine_id` / `device_id` 在登录时由调用方生成并写入凭据（`trae.ts:108-119`），**凭"随机 32hex / 16 位数字撞车概率极低"来保证唯一**，没有注册表、没有分配前查重、没有导入已有账号时的冲突处理。

后果：**「识别本地已登录过的账号缓存」这条路径在 DSH 里是缺失的**——它只覆盖了「新登录 → 新生成」，没覆盖「已有缓存 → 必须复用原设备 ID」。而用户明确要求的是**两条路径都要关联到虚拟设备 ID**。

> **这是我们要比 DSH 多做的一点**：建立**设备注册表（Device Registry）**，把「分配 / 复用 / 冲突检测」做成显式机制，而不是靠随机数不撞车。

### 0.3 用户需求 ② 在 DSH 里**已经有一个运营操作模块**，可直接照搬架构

| 事实 | 证据 |
|---|---|
| 签到端点（WorkBuddy 实测逆向） | `credits.ts`：`POST /v2/billing/meter/checkin-activity-status`（查状态）、`POST /v2/billing/meter/daily-checkin`（领取） |
| 积分余额端点 | `credits.ts`：`/v2/billing/meter/get-user-resource`（**两个产品通用**，只有 baseURL 不同） |
| 批量入口 | `jet-hub-rpc.ts`：`credits.status` / **`credits.claimAll`** / `credits.balances` |
| 单账号失败隔离 | `buddy-auth.ts` `refreshAll(pool)`：「**单账号失败不影响其他账号**」 |
| 结果汇总分类 | `jet-hub-rpc.ts`：「`inactive`（无资格/活动结束）与 `failed` **分开计数**，因为前者是正常的业务状态、后者才是需要用户关注的问题」 |

### 0.4 一句话判断

> **需求 ①**：抄 DSH 的「设备指纹持久化 + 续期不动 + 每账号互异」结论，**但补上它没有的设备注册表**（分配/复用/冲突检测三件事）。
> **需求 ②**：抄 DSH 的「批量执行器 + 失败隔离 + 四类结果分类 + 幂等看响应体 code」架构，**但要把「运营操作」做成与核心调度链路解耦的可插拔模块**。

## 一、需求 ①：虚拟设备身份（Device Identity）

### 1.1 术语对齐（避免与 DSH 的两个"设备"概念混淆）

⚠️ DSH 代码里出现**两个同名不同义**的"device"，读代码时极易混淆，先分清：

| 概念 | 出处 | 含义 | 与我们有关吗 |
|---|---|---|---|
| **设备指纹 / 虚拟设备身份** | `trae.ts` / `qoder.ts` / `lobsterai.ts` 凭据字段 | 上游产品用来识别"这台机器是不是同一台"的标识 | ✅ **这就是用户需求的本体** |
| **配对设备（paired device）** | `dsh-web/packages/dsh-remote-web-ui/src/gate.ts:81-99`、`pairing.ts` | DSH 自己 Web 服务的「手机扫码远程访问」会话凭证 | ❌ 无关（那是 DSH 的远程访问安全，不是模型接入风控） |

> 我一开始在 `dsh-bridge` / `dsh-web` 里搜 `deviceId`，命中的全是**后者**，与需求无关。**真正相关的是 `deepseek-harness-codearts/src/` 下的凭据字段。**

### 1.2 DSH 各产品的设备标识字段全表（可直接作为我们的字段字典）

| 产品 | 设备标识字段 | 格式 | 用途 | 证据 |
|---|---|---|---|---|
| **trae** | `machine_id` | 32 hex | 设备指纹，标识"这台机器"；**换机器需重新登录** | `trae.ts:108-112` |
| | `device_id` | 16 位纯数字 | 签到设备号；**每个账号必须互不相同** | `trae.ts:116-119` |
| **qoder** | `machine_id` | — | **续期载荷必带**（`{refresh_token, machine_id}`） | `qoder-auth.ts:279`、`qoder.ts:144-164` |
| **lobsterai** | `uuid` | — | 「服务端识别『同一安装』的依据」 | `lobsterai.ts:104-107` |
| | `first_keyfrom` / `latest_keyfrom` | — | 续期 + exchange 必带 | `lobsterai.ts:109-113` |
| **codearts / buddy(workbuddy)** | **无** | — | 无设备指纹字段 | `02` §2.2「持久化的设备指纹」行：codearts ✗、buddy ✗ |

**关键差异**：**只有 3/6 产品需要设备指纹**，且字段格式各不相同。这直接决定了我们的设计——**不能定义一个"通用 device_id"字段，必须是 per-product 的字段字典**。

### 1.3 设备"画像"不止 ID —— 还要一整套环境描述

【代码】`trae-product.ts` 的 TRAE 实例（`trae-product.ts:263-286`）里带着一整套设备环境描述：

```
ideVersion:      '0.1.52'
ideVersionCode:  '20260811'
deviceBrand:     'Apple'
osVersion:       'macOS 15.7.4'
```

【代码】发送时映射为请求头（`trae.ts` 的 `traeOAuthHeaders` 附近）：

```
X-Device-Type: 'macos'
X-OS-Version:  <product.osVersion>
X-Device-Brand: <product.deviceBrand>
Request-Traffic-Type: 'prod'
```

【代码】登录 URL 还要再带 9 个设备参数（`trae-oauth.ts:99-128`）：

```
machine_id / device_id / x_device_id / x_machine_id
x_device_brand / x_device_type / x_os_version / x_app_version / x_app_type
```

> **这些不是"ID"，是"设备画像"**（品牌、系统版本、IDE 版本、应用类型）。风控看的是**整套画像的一致性**，不只是一个 ID。
> **推论**：我们的虚拟设备不能只生成两个 ID，必须生成**一套自洽的画像**——否则「machine_id 是新的，但 os_version 还是老的」本身就是风控信号。

### 1.4 我们的设计：设备注册表（Device Registry）

#### 数据模型

```
# 设备档案（一套自洽的虚拟设备画像）
DeviceProfile:
  id:            dev_xxxx           # 系统生成
  product:       trae               # 归属产品（决定字段字典）
  account_id:    res_xxxx           # 绑定账号（一对一，全局唯一）
  fingerprint:                      # 产品特有字段（per-product 字典）
    machine_id:  <32hex>
    device_id:   <16位数字>
    ...
  persona:                          # 设备画像（产品的静态默认值 + 可选覆写）
    device_brand: Apple
    device_type:  macos
    os_version:   macOS 15.7.4
    app_version:  ...
  created_at / source               # source: generated | imported
```

#### 三条硬约束（直接对应用户原话）

| 用户要求 | 落地机制 |
|---|---|
| **「不允许出现多个账号绑定到同一个设备 ID」** | 注册表建 **`(product, fingerprint_key)` 唯一索引**；分配时生成 → 查索引 → 冲突则重生成（上限 N 次后报错，不静默降级） |
| **「识别本地已登录过账号缓存……需要关联到虚拟设备 ID」** | 扫描到已有账号缓存时，**若缓存内已有设备标识 → 原样复用写入注册表，绝不重新生成**；若缓存无设备标识 → 按新账号走生成流程 |
| **「接入新账号……需要关联到虚拟设备 ID」** | 新账号接入 → 生成**一整套全新画像**（不复用任何已有指纹），写入注册表 |

#### ⚠️ 最重要的一条：导入路径的**冲突处置必须是"拒绝 + 人工决策"，不能自动改**

导入已有缓存时如果发现「缓存里的 device_id 已被本网关另一个账号占用」，**不能自动给缓存账号换一个**：

> 【推断 + 强理由】自动换 = 让那个已登录账号在**上游眼里突然换了设备**。按 `trae.ts:108-112`「同一账号用不同的 `machine_id` 可能会触发风控或要求重新登录」，这会把一个"配置冲突"升级成"账号被风控"。
> **正确处置**：报冲突 → 列出两个冲突账号 → 由用户决定（保留哪个 / 放弃导入哪个）。

#### 设备轮换（Rotation）：抄 DSH 的"代次派生"，不改本体

【代码】`types.ts:61-74` 的 `ProviderAccountEntry.traeCheckinDeviceGeneration`：业务码 **`9074`（签到人数过多）的限流范围是 `device_id` 而非账号**；命中后代次 +1，即可由 `credential.device_id` 派生出一个全新的签到设备号绕开它（`trae.ts` 的 `deriveCheckinDeviceId`）。

【代码】**只存整数代次而不存新设备号**，因为派生结果由 `(device_id, generation)` 唯一决定；且「凭据里的 `device_id` 是设备指纹，动它会牵涉风控」（`02` §5.4）。写入受**只增不减**保护（`account-pool.ts:691-692`）。

> **这个设计非常聪明，直接抄**：
> - 轮换只增一个整数代次，**不改写设备档案本体** → 主设备指纹始终稳定，不会触发"换设备"风控
> - 只增不减 → 防止乱序回调把代次写回小值，让被限流的设备号"复活"

| 能力 | 当前是否需要 | 说明 |

### 1.6 🆕 补充：一条比 DSH 更彻底的路线（2026-09-26，来自 `ZCode-Panel`）

>

### 2.2 三条必须抄的血泪教训（每条都对应 DSH 踩过的真实缺陷）

#### 教训 1：状态接口有两个，用错会得到**看似合理的假数据**

【代码】`credits.ts` 头注释结论 1：

> **必须用 `checkin-activity-status`，不能用 `checkin-status`**。后者返回的是占位数据（`active:false`、`checkin_dates:null`、`claim_button_text:""`），会让人**误判为"活动未开启"**。

> 通用化：**「看起来正常的空响应」比「报错」更危险。** 运营类接口必须确认哪个是权威状态源。

#### 教训 2：幂等判定**必须看响应体 code，不能只看 HTTP 状态**

【代码】`credits.ts` 头注释：

> 幂等：重复领取返回 **HTTP 400 + code 10001**（"今天已签到，请明天再来"）。**判定以响应体 code 为准 —— 不能只看 HTTP 状态。**

> 这一条如果做错，**"已签到"会被当成失败重试**，轻则刷出一堆错误日志，重则触发上游频控。
> 映射到结果分类：HTTP 400 + code 10001 = **`already_done`（成功态）**，不是 `failed`。

#### 教训 3：停用账号**不能参与**批量操作

【代码】`buddy-auth.ts` `refreshAll` 上方注释记录了一个真实缺陷：

> 停用账号仍会出现在 Jet Hub 里并参与积分领取，于是点「一键领取」时用**过期凭据**打腾讯接口，服务端回 **HTML 错误页** → 前端报 `Unexpected token '<'`。

> 两个可抄的点：
> 1. **批量操作必须跳过 `enabled=false` 的账号**（但注意：`buddy-auth.ts` 同时指出「**`enabled` 与续期无关**」——续期该照做，否则停用一段时间后 `refresh_token` 过期，用户重新启用时拿到的是**死凭据，无法自动恢复**。**"是否参与批量运营" 与 "是否参与自动续期" 是两个独立开关，不要合并**）
> 2. **响应解析要防 HTML 错误页**：非 JSON 响应要有明确错误分类，不能让解析异常裸奔

### 2.3 批量执行器设计

#### 结果分类（抄 `jet-hub-rpc.ts`，四类而非两类）

| 类别 | 含义 | 是否需用户关注 |
|---|---|---|
| `success` | 本次真的领到了 | 否 |
| `already_done` | 幂等命中（已签到 / 已领取） | 否 —— **是正常业务状态** |
| `inactive` | 无资格 / 活动结束 | 否 —— 正常业务状态 |
| `failed` | 真的出错 | ✅ **才是需要用户关注的问题** |

> 【代码】`jet-hub-rpc.ts` 汇总函数注释原文：「`inactive`（无资格/活动结束）与 `failed` **分开计数**，因为前者是正常的业务状态、后者才是需要用户关注的问题」。

#### 执行策略

| 项 | 定案 | 依据 |
|---|---|---|
| 并发 | **串行 + 间隔**（不上并发） | 本次探测实测：`08` §9 中约 **1/3 请求触发 429**；批量操作更敏感 |
| 失败隔离 | **单账号失败不影响其他账号** | `buddy-auth.ts` `refreshAll` 注释原文 |
| 重试 | 仅对**网络类/5xx** 退避重试；**业务码不重试** | 幂等语义下重试业务错误无意义 |
| 幂等判定 | **响应体 code 优先于 HTTP 状态** | `credits.ts` 教训 2 |
| 参与范围 | 跳过 `enabled=false`（运营类）；续期类**不看 enabled** | `buddy-auth.ts` 教训 3 |
| 设备注入 | 每个账号**带自己的设备画像**发请求 | 需求 ①；且 `device_id` 本身就是签到限流维度（`9074`） |

#### 抽象接口（伪代码）

```python
class AccountOperation(Protocol):
    name: str                        # daily_checkin / claim_gift / query_balance
    supported_products: set[str]     # 产品白名单（"签到只有中国版有"这类差异在此声明）

    async def execute(self, ctx, account, device: DeviceProfile) -> OpResult: ...

@dataclass
class OpResult:
    category: Literal["success", "already_done", "inactive", "failed"]
    detail: str
```

> 【代码】`credits.ts` 记录了一个**产品能力差异**的实证：签到**只有 CodeBuddy 中国版有**（国际版内核里连 `checkin-status` / `daily-checkin` 的字面量都不存在），但**积分余额查询两边都有**。
> → **`supported_products` 必须 per-operation 声明，不能按产品整体开关。**

### 2.4 🔴 必须报告的一个架构张力（不是 bug，是取舍）

**批量签到 / 领礼包是「调用上游的非模型业务接口」，这与网关现有定位有张力。**

| 侧 | 事实 |
|---|---|
| 网关现有定位 | OpenAI 兼容的**模型转发**层；`Resource` = 厂商 + 账号 + Key（`schemas.py:109-129`），核心链路只做 chat/completions |
| 新增需求 | 调用 `/v2/billing/meter/*` 这类**产品专属业务接口** |
| 张力 | 这类接口**不是 OpenAI 兼容 API 的一部分**，只能 per-product 硬编码；若塞进核心调度链路，会污染「扁平资源模型 / 通用兼容」的架构 |

**我的定案**：**作为独立的可插拔模块（Ops Module），与核心调度链路解耦。**

- 不进 `core/scheduler.py`，不进 `Resource` 主流程
- 独立目录 + per-product 适配器，产品不支持即 `inactive`，不报错
- 复用 `Resource` 的凭据与设备绑定，**但不复用**其调度/限流/租约逻辑

> **另一个必须提的边界**：网关铁律 1 是「纯本地运行、无远程更新」。批量运营是**本地主动发起的出站请求**，与调用模型接口性质相同，**不违反铁律**。但它**扩大了网关的职责边界**（从"模型转发"到"账号运营"），**必须在 PRD 里显式确认**，不能默默加。

## 五、一句话回答

> **需求 ①**：DSH 已经踩过这个坑并把结论写进了注释——**设备指纹必须 per-account 互异、必须持久化、续期时不动**，否则触发风控。抄它的结论，但**补上它没有的设备注册表**（DSH 只靠随机数不撞车，缺"导入已有缓存时复用 + 冲突拒绝"这条路径）。
> **需求 ②**：DSH 已有完整的批量运营模块（`credits.claimAll`），架构可直接抄，其中**三条血泪教训**（权威状态源、幂等看响应体 code、停用账号不参与）必须原样继承。
> **但要注意**：运营操作是**产品专属业务接口**，会扩大网关职责边界，必须做成**与核心调度解耦的可插拔模块**，并在 PRD 里显式确认。
