## 二、v1 被取代的原因（最重要的一节）

v1 的调研过程很扎实（三批独立核验共发现 83 处错误、17 处严重，全部已修正），但**三个任务的框架都偏了**：

| # | v1 的框架 | 偏差在哪 | v2 的更正 |
|---|---|---|---|
| **1** | 「ZCode 的机制**比传闻窄得多**：只归一化 2 个参数，建议**不引入**」 | **字面对、机制严重不完整**。v1 只读了 `packages/model-option-map` 一个包。而**用户最关心的「上下文大小怎么定义不一样」根本不在那个包里** —— 它在 `packages/shared/src/model-config.ts:71`，走的是**另一条 overlay 轨**，且**真的参与请求链路**（驱动 auto-compact 阈值、多模态降级、请求前硬校验）。 | 准确表述：**2 个 DSL 变量 + 8 个能力位（含 `contextWindow`）**，三轨合起来才是完整机制。建议也从「不引入」改为**「引入方言表 + 能力位维度」**。 |
| **2** | 「DSH 插件**不是网关**，不对外暴露 HTTP 端点；重点在**合规风险**」 | **方向对但没答到点上**。用户问的是**资源池怎么搭、聚合模型怎么输出、能否给别的工具用**，v1 把大量篇幅放在「它是不是网关」和合规上，**没有把这套机制本身讲透**。 | v2 拆成两份：`02` 专攻**多产品多账号资源池的机制**（产品注册表字段全表 / 六套协议对照 / 凭据存储 / 选号算法 / ER 图）；`03` 专攻**输出面与可复用性判定矩阵**（逐消费方给「能否复用 / 要补什么」）。合规作为**前提**保留在 §三，不再占正文。 |
| **3** | 「**推荐 `mgw` 本地 CLI 作统一入口，但 CLI 不承载模型流量**」 | **把用户要的东西判掉了**。用户明确要的是「CLI 对接模式」作为一种**可用的对接方式**；v1 直接把它降级为「不承载流量」，等于否决。 | v2 先把「CLI 对接」**拆成两个正交方向**分别给结论：上行 CLI 是真价值（但仅当平台只有 CLI）；下行 CLI 的真实价值是**配置注入 + 模型目录**，不是「更短的路径」——**并给出为什么"更短"不成立的量化论证**（loopback 亚毫秒 vs 上游端到端几百毫秒～数秒，差 2～3 个数量级）。**这比简单否决更接近真相，也更可执行。** |

> **一句话教训**：v1 的偏差不在事实，在**框架** —— 它把「参考项目是什么」答清楚了，但没把「用户要拿它做什么」答清楚。
