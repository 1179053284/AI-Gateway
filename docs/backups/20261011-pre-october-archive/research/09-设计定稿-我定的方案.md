# 09 · 设计定稿 —— 我定的方案

> **本文回答用户第 4 轮的原话**：「至于怎么设计，要结合真实场景需求，不要过度设计同时能达到最好效果……至于是不是 4 类我不知道，**由你定**。」
>
> **定稿日期**：2026-09-24
> **依据**：`08` 的全部实测（WorkBuddy 端到端接入 + 工具侧契约 + 探测可行性）+ `02` 的 DSH 机制 + `06` 的四级归约
> **原则**：**默认值全部自动推导，用户只在需要时覆盖。** 这是"不过度设计"与"达到最好效果"的交点。

---

## 一、白话版：我定了什么

> 本节写给不写代码的人看。下面 §二 起是技术细节。

### 一句话

**网关自己把该知道的都查清楚、把该告诉工具的都说清楚；你在界面上要填的东西，基本不变。**

### 三句话展开

**① 设置项：不新增你日常要填的东西。**

你原来的设置项（启用开关、端点、分组、资源池、参数）**一条都不用多填**。

我实测发现需要的新东西（这个模型能读多少字、能不能看图片、支不支持深度思考、思考强度有几档）**全是"这个模型本身是什么"的客观属性** —— 网关自己从内置模型目录里查出来就行，**不需要你填**。

只有一种情况你才需要动手：**内置目录里查不到这个模型**（比如你接了一个很新的模型）。这时才需要你补。

> **这回答了"是不是 4 类"**：**不是 4 类，也不是很多类 —— 是"你日常填的那一层不增加，系统自动推导的那一层不占用你的注意力"。**

**② 账号存储：照你说的做。**

你说"公共信息一张表，每个产品特有的东西分开存" —— 我查了你让我调研的那个 DSH 插件，**它就是这么做的**，而且踩过 3 个坑。所以我定：**照你的方案，并绕开它踩过的坑**。

**③ 参数不统一：让工具自己翻译，网关把"说明书"给对。**

这是本次实测最大的发现：**工具（比如 WorkBuddy）自己就有参数翻译引擎**，它不需要网关帮它翻译 —— **它需要网关告诉它"这个模型到底支持什么"**。

打个比方：工具是个会说多国语言的翻译官，网关只需要给它一本**准确的词典**，而不是替它说话。

**网关现在的问题是：这本词典一个字都没给。** 而词典的内容网关内部全都有。

### 汇总表

| 事项 | 我定的 | 你要做什么 |
|---|---|---|
| 设置项 | 日常层不增加；能力位由内置目录自动推导 | **不用做** |
| 账号存储 | 公共表 + 产品特有凭据分开（照你的判断） | **不用做** |
| 能力位下发 | `/v1/models` 补字段 + 可导出工具配置文件 | **不用做** |
| 参数归约 | 优先"下发声明让工具翻译"，工具不会时网关兜底 | **不用做** |
| 方言表 | **默认自动探测**，探测失败才手填 | **不用做** |
| 档位表 | 7 档，且**允许厂商有超出这 7 档的档位**（实测发现了 `ultra`） | **不用做** |

## 二、配置维度定稿（回答"是不是 4 类"）

### 2.1 分三层，而不是"几类"

纠结"几类"本身是个伪问题。真正的问题是**这些配置由谁来填**。按这个标准分三层：

| 层 | 内容 | 谁填 | 现状 |
|---|---|---|---|
| **L-A 用户层** | `enabled` / `endpoint` / `group` / `resources[]` / `params{}` | **用户**（界面上填） | 已有（4 类 + Q24-⑥ 的 params） |
| **L-B 目录层** | `vendor` / `display` / `context_window` / `max_output` / `image_input` / `video_input` / `audio_input` / `reasoning` / `effort_levels` / `params_default` / `only_base64_image` | **内置目录自动带入**（`BUILTIN_ENTRIES`） | ✅ **数据已存在**（`enums/matcher.py:67-140`），**只是没下发** |
| **L-C 方言层** | `thinkingLevelMap` / `thinkingFormat` / `maxTokensField` | **探测自动得出**（`08` §9.4 三步探测），失败才手填 | ❌ 现在没有 |

**关键判断**：
- **L-A 不新增** → 符合"不过度设计"，也符合你"不加东西"的直觉。
- **L-B、L-C 不是"新增设置项"，是"系统自己算出来的派生数据"** → 它们**不该占用 UI**，最多在界面上**只读展示**。
- 只有**内置目录查不到**的模型，才需要用户补 L-B（走"自定义模型"入口）。

### 2.2 因此：UI 上只多一样东西（且默认折叠）

```
系统模型详情
├─ 头卡（启用 / 模型名 / 厂商）            ← 现有
├─ 模型属性（只读，来自 L-B）               ← 数据已有，只是展示
├─ 资源池（有序资源 + 资源级推理）           ← 现有
├─ 参数配置（params）                      ← 现有（Q24-⑥）
└─ 高级 · 能力覆盖（默认折叠，通常不用动）    ← 新增，仅 L-B/L-C 推导不准时才用
```

> **"高级·能力覆盖"是唯一的净新增**，且**默认不动**。这是我能在"不过度设计"和"达到最好效果"之间找到的最小交集。

### 2.3 与既有定论的关系（诚实交代）

| 既有定论 | 处置 |
|---|---|
| **Q23-②「维持现状四类、零新增字段」** | **不适用**（已在 `07` 澄清：这不是你的确定决定，且 Q24-⑥ 已推翻过它）。但**结论上我采纳了它的精神**：L-A 用户层**确实不新增**。 |
| **Q24-⑥ `SystemModel.params`** | **保留并加强**（实测证明必须有：`08` §3.3 的 token 预算问题） |
| **Q18-④「调度保持全局」** | **不翻案**。调度（x/y/m/超时/冷却）继续全局唯一一套。 |

## 三、账号存储定稿（照你的判断，绕开 DSH 的坑）

**结论：采纳你的「公共表 + 产品特有分开」——与 DSH 实际做法一致（`08` §十）。**

```
① products        产品注册表    { id, name, kind, auth_mode, endpoint_hints, config_schema }
② accounts        公共账号表    { id, product, nickname, enabled, expires_at, refreshable, credential_ref }
                               ← 只放"跨产品语义一致"的字段
③ credentials     凭据表        key = credential_ref；value = 该产品特有的 JSON
   （另）runtime_state 运行时状态  { account_id, rate_limits, cooldown_until, last_error }
                               ← 绝不与 ②③ 混放
```

**必须绕开的 DSH 三坑**（`08` §9.2）：

| 坑 | 我们的做法 |
|---|---|
| K1 `settings.replace()` 整体替换会冲掉别的字段 | 配置写盘**整份快照 + 读-改-写**，不"只改一个字段就落盘" |
| K2 读滞后的快照 → 并发更新互相覆盖 | 运行时状态读源 = **内存权威副本**，不直接读文件 |
| K3 运行时状态混进凭据本体 | `runtime_state` **单独一张表** |

**落地分两阶段**（避免一次大改）：

| 阶段 | 动作 | 兼容性 |
|---|---|---|
| **一** | 现有 `Resource` **加一列 `product`**（默认空 = 旧行为） | ✅ 向后兼容，旧配置零改动 |
| **二** | `Resource.api_key` 抽成 `credentials` 条目，只留 `credential_ref` | ⚠️ 需迁移脚本 + **双读期** |

> **判断**：**先只做阶段一**。阶段一就能解决"同一厂商多账号靠备注字符串区分"的真实痛点；阶段二的复杂度留到真需要时。

### 3.1 增补：设备身份表（2026-09-24 需求增补，详见 `10`）

需求 ①「每账号一套虚拟设备信息」落地为**独立的第 4 张表**，不塞进 ②③：

```
④ device_profiles  设备档案表  { id, product, account_id, fingerprint{}, persona{}, created_at, source }
                               ← (product, fingerprint_key) 全局唯一；account_id 一对一
```

三条硬约束（详见 `10` §1.4）：

| 约束 | 机制 |
|---|---|
| 不允许两账号共用一个设备 ID | 分配时生成 → 查唯一索引 → 冲突重生成（有上限，不静默降级） |
| 导入已有账号缓存 | 缓存内已有设备标识 → **原样复用，绝不重新生成** |
| 缓存 ID 与已有账号冲突 | **拒绝导入 + 报冲突由用户决策**（自动换 = 让已登录账号在上游眼里"换设备" → 触发风控） |

**为什么单独一张表而不是塞进 `credentials`**：设备指纹在产品侧是**与凭据同级的稳定身份**（`trae-auth.ts:10-14`：续期只改 token，设备字段完全不动），混进凭据会让"续期"误伤"设备身份"。

**DSH 没做而我们补的一点**：DSH 只靠「随机 32hex / 16 位数字撞车概率低」保证互异，**没有注册表、没有导入路径的复用与冲突处理**。

> **完整设计（含 per-product 字段字典、设备轮换代次派生、运营操作框架）见 `10-设备身份隔离与批量运营机制.md`。**

## 四、能力位下发定稿（本次实测最重要的落地项）

### 4.1 缺口（实测确认）

工具需要 **8 个字段**，网关 `/v1/models` **一个都没给**（`08` §6.4）：

```
GET /v1/models 实测返回：
{"id":"glm-5.2","object":"model","created":0,"owned_by":"model-gateway",
 "endpoint":"chat","group":"编程"}          ← 6 个字段，0 个能力位
```

而**网关内部全都有**（`EnumEntry`）：`context_window` / `max_output` / `image_input` / `reasoning` / `effort_levels` / `display` / `vendor`。

### 4.2 映射表（内部字段 → 工具要的字段）

| 工具要的 | 网关已有 | 映射 |
|---|---|---|
| `maxInputTokens` | `context_window` ✅ | 直映射 |
| `maxOutputTokens` | `max_output` ✅ | 直映射 |
| `supportsImages` | `image_input` ✅ | 直映射 |
| `supportsReasoning` | `reasoning` ✅ | 直映射 |
| `thinkingLevelMap` 可用档 | `effort_levels` ✅ | 如 `["low","high","max"]` |
| `name` | `display` ✅ | 直映射 |
| `vendor` | `vendor` ✅ | 直映射 |
| `supportsToolCall` | ❌ **网关没有这个字段** | 需新增（或从目录推导：编程类模型默认 true） |

> **⚠️ `supportsToolCall` 是最要命的一个**：实测 `08` §4.5 M1 —— 工具看到 `supportsToolCall !== true`
> 会**直接把 tools 从请求里删掉**。对编程 Agent 来说，没有工具调用 = 退化成聊天机器人。
> → **必须给，且对支持的模型给 `true`。**

### 4.3 两条下发路径（都需要）

| 路径 | 形态 | 适合 | 状态 |
|---|---|---|---|
| **A · API 下发** | 扩展 `/v1/models`（加非标准字段，保持 OpenAI 兼容） | Trae / Cursor / Cherry Studio 等会调 `/v1/models` 的 | ⏳ 待实测（U3） |
| **B · 文件下发** | `mgw setup` 生成工具可读的 `models.json` | WorkBuddy CLI（**只读文件，不调 `/v1/models`**） | ✅ 已验证 |

> **B 路的坑（`08` §5 O2，已踩中）**：配置文件目录**必须按「产品标识 → `dataFolderName`」解析**
> （WorkBuddy=`.workbuddy`、WorkBuddy AI=`.workbuddy-ai`），**不能靠 `isWorkBuddyProduct()` 区分**
> （它对两者都返回 true），**且要处理 `WORKBUDDY_CONFIG_DIR` 环境变量劫持**。

## 五、参数归约定稿（把 `06` 的方案与实测对齐）

### 5.1 双层，优先级明确

```
【优先 · 声明式】网关下发 caps（thinkingLevelMap / thinkingFormat / 能力位）
                 → 工具用自己的引擎翻译
                 → 网关不介入
        ↓ 工具不带引擎时
【兜底 · 归约式】网关执行 06 的 L0→L3 归约
```

> **不是推翻 `06`，是给它划清适用边界。** 引擎必须有（兜底 + 网关自己也要调上游），**但优先级低于"把声明写好"**。

### 5.2 规范档位：7 档，**且开放可扩展**

```
off < minimal < low < medium < high < xhigh < max
```

**🔴 必须开放**：实测 `deepseek-v4-pro` 的合法值含 **`ultra`**，**超出这 7 档**（`08` §9.2）。

> **规则**：遇到规范序之外的档位 → **不报错，原样透传**（它是厂商的真实能力）。
> 这一条要写进 PRD。

### 5.3 降级：分两层，不要混

| 层 | 谁做 | 规则 |
|---|---|---|
| **① 能力层 clamp** | **工具** | 就近取，**优先向上**（实测 `clamp()`：先往高找、再往低找） |
| **② 方言层降级** | **网关**（仅工具无 clamp 时） | 保守降级，**只降不升** |

**若工具已 clamp，网关不得二次 clamp。**

### 5.4 方言表：探测优先

- 默认走 `08` §9.4 的 **S1 粗筛 + S2 生效验证 + S3 定档**
- **S2 必需** —— 否则会把"上游忽略的字段"配成假方言（本次实测就发现 `thinking.type` 是假的）
- 结果**落盘缓存**，不每次启动都探（探测会触发 429）

## 六、不做什么（避免过度设计）

| 不做 | 为什么 |
|---|---|
| **不做"每模型一套调度参数"** | Q18-④ 保持全局。实测无证据表明需要按模型拆 |
| **不做 L-B/L-C 的用户录入界面**（仅"高级·能力覆盖"折叠入口） | 数据可自动推导/探测，让用户填是过度设计 |
| **不做自定义参数名**（`params` 仍限已知键 + 未知键放行） | Q24-⑥ 已定，实测无推翻理由 |
| **不做 GUI 自动化**（不代用户点界面） | 超出网关职责；`mgw setup` 只写配置文件 |
| **不做多产品账号的阶段二**（凭据实体化） | 阶段一已解决真实痛点，阶段二留到需要时 |
| **不做工具的登录态管理** | `08` §5 O1：工具登录态是工具的事，`mgw setup` **只能写配置，不能替用户登录**。文档必须写明"先登录，再配网关" |
