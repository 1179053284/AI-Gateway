## 一、全局判断：先做什么、不做什么

### 1.1 四条最有价值的结论

| # | 结论 | 为什么它最值钱 |
|---|---|---|
| **V1** | **ZCode 的机制不是「只归一化 2 个参数」，而是「2 个 DSL 变量 + 8 个能力位（含 contextWindow）」三条轨** | 用户最关心的「推理强度怎么设不一样」「上下文大小怎么定义不一样」**都有对应机制**，且都能落到我们网关上（`01` §0、§6） |
| **V2** | **DSH 那套「多产品多账号」的骨架是「产品配置对象 + 凭据/索引分离 + 极简选号」，但它的账号池没有并发租约** | 可抄的是**架构决策**；不可抄的是**并发模型**（我们已有原子 `in_flight`，比它强，不能丢）（`02` §0、§9） |
| **V3** | **「聚合模型输出面」在 DSH 里是进程内 `LlmAdapter`，跨不了进程；我们要复用的是它的 IR / 适配器纪律，不是它的形态** | 直接回答了用户「这种对接方式能否给别的工具用」——**不能，必须自建 HTTP 面**（`03` §0、§6） |
| **V4** | **ZCode 的归一化只做到「把值写进正确字段」，没做到「统一值的语义」** —— 所以它在档位改名时付出了 **25 条手工映射**的代价（同一家厂商内部 12 个模型用 `off`、1 个用 `nothink`） | **这是"每接入一家适配一家"的真正病根**：不统一词汇，就永远在补映射。→ `06` 的四级归约方案（协议族 / 语义槽 / 写入位 / 方言）就是针对这一条设计的（`06` §3·不足 2、§四、§五） |

### 1.2 四条最重要的「不做」

| # | 不做的事 | 理由 |
|---|---|---|
| **N1** | **不引入受限 CEL DSL / 任何表达式引擎** | 我们要的是「方言表」，不是「表达式引擎」。ZCode 那 20 种真实表达式**只落在 6 个字段路径上**（`06` §5.3），降维成「写入位组合 + 值域映射」就不需要引擎了 —— **省掉 `parser.ts`(240) + `compiler.ts`(92) + `evaluator.ts`(214) + `tokenizer.ts` ≈ 700 行 TS**（`01` §11.2 P2） |
| **N2** | **不让 `mgw` CLI 自己跑调度** | 冷却 / `C` / `in_flight` 是**有状态的中枢能力，只能有一份**；CLI 进程内再跑一套 = 容错退化成「每进程各自容错」（`04` §3.4） |
| **N3** | **不做「虚拟模型名 / 策略路由」** | 与既有定论 Q18-③（调度参数全局唯一）及 Q23-②（配置参数范围维持现状四类）有张力，**需先翻案**（`04` §4.3） |
| **N4** | **不把「能力层差异」当「参数不一」去归一化** | `contextWindow` / 模态支持是**事实**，不是**口径**。归一化的目标是让**调用方的意图能被正确翻译**，不是让所有模型"看起来一样"（`06` §九 N4） |

### 1.3 🔴 两个必须立刻报告的问题（不是建议，是缺陷）

| # | 问题 | 证据 | 性质 |
|---|---|---|---|
| **BUG-1** | **`/v1/models` 下发「选中即失败」的模型清单** | 本机实测（2026-09-24）：`/v1/models` 返回 7 个模型；调用任一 → `{"code":"NO_RESOURCE"}`；配置里 `resources` 仅 1 条而 7 个模型的 `resources` 全为空。根因：端点只按 `m.enabled` 过滤（`api/openai_compat.py:42`），**不看该模型有没有可用资源** | **真实可达缺陷**。直接导致「把模型信息给对接软件」这件事**当前做了就是错的** |
| **BUG-2** | **参数注入顺序缺陷（v1 已登记 B1，本次独立复核确认仍在）** | `scheduler.py:229` `apply_model_params` → `:230` `merge_reasoning` → `:231` `inject_reasoning_into_body`；`inject_reasoning_into_body` 在 `spec.effort` 非空时**无条件**写 `body["reasoning_effort"]`（`ir.py:110-111`）→ 用户在 `SystemModel.params` 里配的 `reasoning_effort` 会被**静默覆盖**；`ir.py:52` 的矛盾防护只在 `merge_reasoning` 内部生效，**管不到 `apply_model_params` 写进去的键** | **真实可达缺陷**（静态阅读得出，未运行验证）。ZCode 用 `merge-patch.ts:22-27` 的冲突守卫解决了同类问题 |

> **BUG-1 和 BUG-2 都是「纯缺陷修复」，不需要翻案、不需要改 PRD**，应排在所有能力建设之前。

## 三、本次不纳入考量的范围（用户明确指示）

> **2026-09-24 用户指示**：**「不需要你考虑合规类问题，你再帮我做我个人自用的网关，服务好我就好了。」**
>
> 因此本方案**不设任何合规前置门槛**：`02` / `03` 描述的「授权接入产品账号、使用其内部模型」机制，**直接进入工程评估**，不因条款/风控因素降级或否决。

**但以下「技术性事实」保留**——它们不是合规意见，而是**会直接影响网关能不能稳定跑**的工程约束，删掉等于埋坑：

| 类别 | 具体事实 | 影响 | 出处 |
|---|---|---|---|
| **凭据续期单点** | TRAE 的 PKCE 分支未实现，`trae-oauth.ts:329-335` 明确返回「本实现暂不支持该流程」 | 上游一旦切到 PKCE，**TRAE 登录会整体失效**（不是"风险"，是确定会断） | `02` §4 |
| **账号池并发不成立** | `account-pool.ts` 全文 grep `lease\|reserve\|acquire\|in_flight\|lock\|mutex` **零命中**；`index.ts` 9 个调用点**全传 `modelId=''`** | N 个并发请求会**确定性地**拿到同一个 `candidates[0]`；"额度聚合"在并发下不成立 | `02` §0/§5.4 |
| **设备指纹必须持久化** | TRAE `machine_id`（`trae.ts:108-112` 注释「不同 machine_id 可能触发风控或要求重新登录」）、LobsterAI `uuid`（`lobsterai.ts:104-107`「服务端识别『同一安装』的依据」） | 指纹重新生成 → **需要重新登录**（工程后果，与合规无关） | `02` §4.3 |
| **限流信息不对称** | API 侧配额明确、隐藏风控不可见；CLI 侧 stdout 无结构化错误码 | 失败原因**不可归因** → 影响我们的失败计数 `C` 与冷却判定质量 | `04` §2.1 |
| **上游无版本契约** | 逆向端点随客户端版本漂移，无 deprecation 通知 | 需要**探针 + 快速降级**，不能假设契约稳定 | `04` §2.1 |

> **一句话**：本方案按用户指示**不做合规判断**；上表只保留「会影响功能可用性」的事实。历史取证材料仍在 `_v1-archive/05`、`_v1-archive/06`（**v1 材料，本次未复核**），**如无需要不必读**。
