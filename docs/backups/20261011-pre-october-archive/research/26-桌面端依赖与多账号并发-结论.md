# 26 · 桌面端依赖与多账号并发 · 终局结论（2026-10-02 轮）

> 用户问题原样拆两条：**Q1** 接入的 10 个产品，每个产品下多账号，调用其内部模型是否**必须打开并登录桌面端软件**？还是纯 API 不需要桌面端也能调？**Q2** 能否同时调用同一产品下**多个不同账号**的资源？
> 交付纪律 = 逐产品全覆盖；每产品由**代码分析专家 / 研发工程师 / 通用权威**三角色独立取证 + 一路真机实测（第二轮补推理级）；交叉验证≠叠加，**分歧由主 agent 亲自复研**后裁定；结论一致才允许写「已定论」，其余一律标「未验证」。
> 子报告 8 份在盘（`docs/research/25-appdep-{codeexperts,engineer,authority}-{A,B}.md`、`25-appdep-liveprobe.md`、`25-appdep-headless-inference.md`；`docs/` 在 `.gitignore:21` 内，属既有约定不入库）。

## 0. 结论先行

1. **Q1 答案：10 个产品全部「不需要」在调用期运行厂商桌面端软件。** 6 个产品已在**对应 App 确认 0 进程**时拿到**真实推理 200**（buddy / workbuddy / lobsterai / trae / loomy 五家本轮实测 + cline 上一轮实测），另 4 家（qoder / qodercn / zcode / raccoon）在**凭据面/目录面**已实测无头可用（raccoon 因凭据过期天然红）。桌面端进程与调用路径**完全不相交**。
2. 但「不需要进程」≠「什么都不需要」。两个产品需要客户端的**离线产物**（🔴 **要产物、不要进程**，判 D3）：
   - `qoder` / `qodercn`：推理请求体要 **COSY 签名 + 加密**（DSH 用客户端 `qoder_auth_wasm.wasm` 292KB 的导出函数产出 `{url,headers,body}`）；该 wasm 由插件**自己的 Node 进程**加载（`WebAssembly.instantiate`），**与 Qoder App 是否运行无关**；社区已有**纯 Python 复刻**（RSA+AES-CBC+MD5，`github.com/fengyinxia/qoder2api`：「完全不依赖 wasm」）→ 属可复刻算法，非结构性不可行。另发现一条**官方无头通道**：Qoder CLI + PAT（`docs.qoder.com/zh/cli/authentication`、`--list-models` = 当前账号可用模型；本机 `~/.qoder-cn/.auth/machine_id`、`~/.qoder-cn/.models/<账号>/catalog-v6`、`~/.qoder-cn/.bin/runtime-info-darwin-arm64-*` 即其无头运行的盘上产物）。
   - `zcode`：推理要三件产物 —— **一次性阿里云验证码 param**（网页 SDK，需一台 headful 真 Chrome，**不是 ZCode 壳**）+ **官方身份 system 块**（cliPrefix+stable，注入到 `system` 前两块）+ **首轮 user 数组最前的 `<system-reminder>` 日期块**，另 `X-Device-Mid` 必带。DSH 原话「纯 Node，不需要 ZCode 实例运行」「上游实测 curl 同样 200」。
3. **Q2 答案：能。** 已在**网关派发层**实测成立：同产品两账号做成两条资源并列进同一系统模型池，两路并发请求**分别落到不同账号**并双双 200（日志 `final=t-buddy-2/acct=buddy-a7f1c09f` 与 `final=t-buddy-1/acct=buddy-00fdd61f`）；撤证可红（停掉 t-buddy-2 后同一对并发立刻塌成同账号）。同账号 2 并发也不互斥、无 429。
4. **多账号的真正价值不是「并发上限」，而是额度与风控分摊**：并发能力在实现上无账号级互斥（全仓请求路径零锁），真正约束是**每号凭据独立 + 设备身份唯一**，以及若干**产品侧的并发/账号策略**（见 §4，trae 最尖锐）。
5. 现在把「多账号资源池」挡住的是**我们自己的接线缺口**，不是厂商：33 条产品资源未被任何系统模型引用（无推理入口）+ 6 条实现/归因缺陷（§5）。

## 1. 判定口径（本轮统一词汇，避免角色间各说各话）

**D 类 = 调用期是否需要厂商桌面端进程**
- D0 完全不需要 App（连首登录都不经 App）
- D1 首登录需一次人工（浏览器/手机即可，**不必在桌面端内**），调用期不需要 App 进程
- D2 **调用期必须有 App 进程**（短时 token 只由 App 保活 / 请求须经 App 本地端口 / 凭据只活在 App 会话）→ **本轮 10 产品无一判 D2**
- D3 需要 App 的**离线产物**（签名算法/WASM/身份块/密文凭据），但**不要进程**
- D4 未知或被风控拦，无法定论

**三条最容易被混为一谈、本轮逐条拆开的区分**
- ①「凭据是怎么来的」≠「调用时要不要 App」：10 产品的登录全部由**网关自己的** OAuth/设备码/扫码/外链流程完成；代码里出现的 `127.0.0.1` **全部**是网关为收登录回跳自己绑的端口（`accounts/callback_server.py:64` 只绑回环），**没有一处连接厂商 App 的本地端口或 IPC**。
- ②「伪装成桌面端的字符串常量」≠「依赖桌面端」：`raccoon` 的 `X-Client-Platform: desktop-macos`、`lobsterai` 的 `platform=win32`、`buddy` 的 `X-IDE-*`/`User-Agent: CodeBuddyIDE/1.106.1` 都是硬编码字面量（准入条件，不是进程依赖）。
- ③「运维路径碰 App 数据目录」≠「推理路径依赖 App」：`upstream/zcode/dataroot.py:176-232` 的 `kill_zcode`/`launch_command` **唯一调用点是 `cli_zcode.py:108-122`（`mgw zcode launch`）**，推理链零引用 —— 这条若读错就会把 zcode 误判成 D2，并把一条不存在的依赖写进架构。

**C 类 = 同产品多账号并行**：C0 可并行无干扰 / C1 可并行但要求每号设备身份唯一稳定 / C2 存在会话互踢或并发上限 / C3 未知。

## 4. 对「资源池调用逻辑」的直接影响（这是本轮的用途）

**4.1 池的形态可以完全后台化** —— 账号 = 一条 Resource（`account_ref` 指本地账号目录，凭据不进 `config.yaml` 的 Key 字段），N 账号 = 池内 N 条并列条目；无 App 依赖 ⇒ 网关可长期无人值守跑，`x=max_active_per_model` 是**生效集宽度**（溢出生效集才参与切换），不是并发上限；要多号真并行，**x 需按号数抬**（现网 x=2，实测双号已足证形态正确）。

**4.2 trae 是池里唯一带官方账号策略风险的一家**（我已亲自复核官方社区答复）：单账号同时在线设备数**上限约 2 台**、**同一设备登录多账号会触发风控、24h 后解锁**、Pro 也不例外（[forum.trae.cn/t/topic/6057](https://forum.trae.cn/t/topic/6057)、[/t/topic/2825](https://forum.trae.cn/t/topic/2825)）。工程含义三条：① 每号必须有**稳定且互异**的 `machine_id`/`device_id`（绝不能全池共用一个指纹 —— 那正是风控触发形态）；② 该身份现在**根本没下发**（`protocol.py:245-250` 只读凭据本体，导入号的设备字段在 `meta.json`；实测不下发仍 200，说明**当下**不是准入判据，但这是把运气当契约）；③ API 调用是否计入「设备」未证 ⇒ 池内 trae 号数与频率应保守，先补下发、再观察错误码。

**4.3 必须按产品做出站塑形，否则工具端必失败**（本轮实测出来的两条硬判据）：`buddy`/`workbuddy` **拒绝非流式**（`400 code=11101 Non-stream chat request is currently not supported`）⇒ 对这两家要把 `stream:false` 改成「上游强制流式 + 本地聚合」（trae/lobsterai 已是同类做法）；`workbuddy` 还要求**首条消息必须是 system**（`11128`）。`raccoon` 思考档位只有 `extra_body.thinking.{type}` 一条有效通道；`lobsterai` 不带 `X-LobsterAI-Client-Capabilities` 会少一个模型。

**4.4 凭据寿命决定池的「可自动化边界」**，必须分三档处置：
- 可无头续期：buddy / workbuddy / lobsterai / trae / cline / raccoon（`auto_renew` 2h 腿已接，能力位 `refresh=True`）；
- **不可续期**：loomy（14 天，必须人工扫码/短信）、zcode（静态凭据）→ 到期即终态 401，池需要的是**「到期预警 + 人工重登队列」**，而不是无限 fallback（否则表现为「资源突然全红」）；
- 有争议：qoder 系本仓有 refresh 端点，社区观察标 `refreshable:false` ⇒ **未验证**，实测前不要把 qoder 号的续期当可靠依赖。

**4.5 额度必须参与选号（本轮拿到动因实证）**：loomy 积分耗尽**不报错、静默改扣永久积分** ⇒ 既有「失败 N 次换号」对 loomy 完全无效（不会失败）。这正是 `docs/research/24 §D2` 的暂缓项，现在有实测动因，建议切到「后台任务刷余额 → 写 `ResourceState` → 选路只读作次级排序键（快到期优先）」，**绝不在请求期发网络查余额**（`20 §C2` 的插法仍不抄）。

**4.6 zcode 的并行天花板是我方造的，不是厂商**：① 验证码 mint「常驻一台 headful 浏览器 + 复用单页 + `pageBusy` 串行」⇒ 多号并行会在 mint 处排队；② `3012` 有**账号级惩罚梯度**（24h 内第 3 次起封 24h、5 次停用）⇒ 池必须做 **per-account 熔断**；本仓现状是 zcode **产品级全局熔断 30min 连坐**（`quota.py:745+` + 读时重判），一个号撞风控会把 16 个号一起按住，且转发路径遇 3012 **无护栏**（`upstream/zcode/out.py:35-44` F-4 已登记）。

## 5. 当前真正挡路的自家缺口（修完才能把 §2 的「未测」变「已测」）

1. **33 条产品资源未被任何系统模型引用** ⇒ `/v1/chat/completions` 无入口（第二轮证明配上映射即 200）。
2. `POST /admin/api/resources/test` 对产品资源**恒 400**（`api/admin.py:411-415` + `main.py:396` 要求 `api_key` 非空，而产品资源凭据不住那里）⇒ 34 条资源无法做连通性验证。
3. **catalog 谎报来源**：厂商 401 回退兜底表时 `source.kind` 仍报 `account`「实时目录」（raccoon 实测；`api/admin_accounts.py:1247`）。
4. **zcode 出站发不出**：`ZcodeOut._headers` 先走 `resolve_context()`，而 16/16 导入号无顶层 `credentials.json` ⇒ 未发请求即抛「无凭据」，兜底的 `outbound_credentials` 永远轮不到（**我已复核：盘上 16 号 0 个顶层凭据 + `product_out.py:104-108` 的抛错在 `out.py:121` 之前**）。测试盲区在 `tests/integration/test_zcode_out.py` 用 tmp 造顶层凭据。
5. **trae 设备头不下发**（§4.2）+ **lobsterai 导入号的 uuid 不下发**（uuid 被 `store.py:709-711` 剥进 `meta.json`，而 `protocol.keyfrom_body` 只从凭据读 ⇒ refresh 请求体与目录 query 不含 uuid，与 `registry.py:96-104` 记的「每次续期原样回传」不符）。
6. **失败归因不诚实**：厂商 401/400 被压成 `NO_RESOURCE`/503 且错误串截断（raccoon、cline 两例），把「号失效」显示成「没资源」，直接误导池的排障。

## 6. 需用户拍板的决策点（附我的建议，均**未擅自执行**）

- **P1 现网建映射**：为 10 产品在界面建系统模型映射（写 `config.yaml`）⇒ 把「凭据级可用」变成「推理级可用」。**建议做**：buddy/workbuddy/lobsterai/trae/loomy 已有推理级 200 背书，纯配置动作。
- **P2 zcode 直连前提 D1 裁决**：单变量四组测法（A 无 captcha 无身份块 → 预期 3007；B 有身份块无 captcha → 预期 3007；C 完整身份块 + 合格 captcha → **200 即直连成立定 D3**；D 只留 cliPrefix → 预期 3012 复现 body 判据）。**建议只做 A/B/C、跳过主动制造 3012 的 D 组**，且用牺牲号、组间留间隔（§4.6 的阶梯惩罚是真实风险）。另需先修 §5.4 才测得到真链路。
