## 本次实测新增的工程决策：出站代理策略

**现象**：E2E-13 重启后两次 chat 请求各挂满 60s（curl -m 60 与尝试超时相等，重试窗口为零）；同期厂商直连 curl 正常（代理 4s / 直连 11.8s），httpx 复现两条路径均 ReadTimeout 后又三连全通——商汤服务端存在间歇性挂起（推测多后端节点中有坏节点）。

**根因**：网关出站原为 `trust_env=False`（无视环境代理直连公网厂商）。本机网络环境下直连商汤不稳定（11.8s~挂起），而系统代理（Clash 127.0.0.1:7890）路径快且稳。

**修复**（model_gateway/adapters/openai_out.py）：
- 公网厂商 base_url → `trust_env=True`（环境代理可用则走——不稳定的直连之外多一条可靠路径）
- 本机/私网/`*.local`/`*.internal` 目标 → `trust_env=False`（INT 假厂商、局域网自建接入不受代理干扰）
- 图片下载同策略（按下载 URL 判定）

**回归**：全量 pytest 141/141 通过；网关重启后 chat 0.96s（E2E-13 复测）。

## 附：真实超时 → 冷却 → 503 全链路（计划外收获）

别名测试期间撞上商汤两个连续挂起窗口，意外实测了超时处置链路（此前仅 INT 模拟）：

```
请求#1（aborted）: 上游 60s 尝试超时 → C=1（跨请求累计）；curl 同刻断开 → 事件 aborted
请求#2（failed）:  上游 60s 尝试超时 → C=2 ≥ y=2 → 冷却（plan 模式 18000s）
                   → 切换 → 模型仅 1 资源 → NO_RESOURCE 503（60.078s，仅 1 次尝试——y 先于 m 判定，符合规格）
资源状态（admin/api/status）: {status: cooldown, C: 2, cooldown_remaining_ms: 16935731,
                              last_error: '[network] timeout: '}
503 错误体: {message: '[network] timeout: ；原因：无可用资源；已尝试：sensenova/k-main/sensenova-6.8-flash-lite×1（[network] timeout: ）',
            type: gateway_error, code: NO_RESOURCE, system_model: sensenova-6.8-flash-lite}
重启后（冷却重置，符合设计）: 别名 6.7 请求 → 200（5.47s，路由 6.8 资源）
```

结论：超时分类（RETRYABLE）、y 跨请求累计、y 先于 m、plan 长冷却、统一无资源错误体——全链路与规格一致。
